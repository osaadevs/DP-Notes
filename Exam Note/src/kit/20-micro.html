Microservices: drawing rules and a worked scenario

The rules that make the picture correct, then a new scenario sorted into the slot table. The next page draws it.
Kit
Microservices

Drawing rules

  1. Draw top to bottom: clients → gateway → services → databases → broker.
  2. Every client arrow goes into the gateway, never straight to a service.
  3. One database under each service. No database is joined to two services.
  4. Label the gateway with its jobs: auth check, routing, rate limiting.
  5. Label at least one event on the broker with a real name from the scenario.
  6. External systems in dashed boxes at the edge, joined to the one service that uses them.
  7. Shared infrastructure as a row of small boxes with "used by every service".

How much to draw by marks

4 mClients, gateway, the services with their own DBs, broker.
5 m+ labelled event(s), auth service, the external systems, the infrastructure row.

Check

☐ one service per functional requirement ☐ a DB per service, none shared ☐ all clients enter through the gateway ☐ broker drawn with a named event ☐ external systems dashed ☐ every box labelled

EventsOrderPlaced, PaymentSucceeded, RiderLocationUpdated
External (dashed)Card payment gateway · Maps API · SMS / email provider

Six bullets in the question gave six services. Notification gets no client arrow: it only listens to events on the broker and sends messages through the external SMS / email provider. The Maps API joins Delivery Tracking the same way the card gateway joins Payment (left off the drawing to keep it clear; add it in the exam if there's room).

2.2 ScalabilityRun more copies of only the busy boxes: Order and Delivery Tracking at dinner time, not User or Restaurant. Keep them stateless behind the gateway so any copy can take any request.
2.2 Fault isolationIf Notification fails, orders still go through: Order just publishes OrderPlaced to the broker and Notification catches up later. Timeouts and circuit breakers on the solid arrows.
2.2 DeploymentEach service box has its own pipeline, so Payment can be updated without redeploying Order (blue-green or canary).
2.3 ArchitectureRead the diagram aloud: gateway, six services with their own databases, broker for events, identity service, registry and monitoring.
2.4 ConsistencySaga across Order → Payment → Restaurant: if payment fails, Order cancels the order (compensation). Each box writes only its own DB; others update from events (eventual consistency).
2.5 SecurityGateway + Identity check every token (OAuth2 / JWT); roles for customer, restaurant, rider; encrypted traffic between services (mTLS); card data handled by the external payment gateway as tokens, never stored by Payment.
