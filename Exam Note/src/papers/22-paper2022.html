Travel booking website: air tickets, hotels and taxis from third-party web services.
Facade + Adapter
25 marks
QUESTION 1 · 25 MARKSDevelop a website for travellers to book foreign trips. Users need to book an air ticket, a hotel and a taxi. When the user requests them, the system collects data from different web services and sends the details to the user. The Hotel sub-system connects to web services provided by different hotels (third party); the Air ticket sub-service connects to airline web services; the Taxi sub-service connects to taxi web services. These web services were developed by third parties, so their method signatures can differ.
1.1Draw a diagram to depict the above scenario.5 marks

Label the facade and the adapters. That shows the examiner where your patterns sit before you name them.

1.2What design pattern can be employed for the sub-systems that combine air tickets, hotels and taxis? Explain your reasons.4 marks

I would use the Facade pattern (structural). It provides one unified, simpler interface to a set of sub-systems.

A TravelBookingFacade with one method, bookTrip(request), calls the AirTicketService, HotelService and TaxiService in the right order and returns one combined itinerary. Reasons: (1) the traveller does one action instead of three; (2) the website depends on one class instead of three sub-systems, so coupling is low; (3) the call order and the combining of results are written once; (4) if a sub-system changes, only the facade changes.

1.2.1Challenges with this pattern?3 marks
  • The facade can grow into a God class as more services (car hire, insurance) are added.
  • It is a single point of failure: if the facade or one service is down, the whole booking fails.
  • Partial bookings: the flight is booked but the hotel fails.
1.2.2Mechanism to overcome them?3 marks
  • Split into smaller facades (FlightFacade, StayFacade); the facade only delegates.
  • Run the facade as stateless copies behind a load balancer; timeouts, retries and a fallback provider for each service.
  • Compensating actions: cancel the flight if the hotel fails, or reserve all three first and confirm together.

2022 · Question 1 (cont.)

Connecting each sub-system to third-party web services with different signatures.
Adapter
10 marks
1.3What design patterns can be employed for connecting the sub-system with different third-party web services?4 marks

I would use the Adapter pattern (structural). It converts the interface of a class into another interface the client expects, so classes with incompatible interfaces can work together.

The HotelService owns one interface, HotelProvider (search(), book()). Each hotel's web service gets its own adapter (HiltonAdapter, ShangriLaAdapter…) that implements HotelProvider and translates the call into that hotel's own SOAP / REST / SDK method. Airlines and taxis are done the same way. Reasons: the third-party services can't be modified; the sub-system code stays the same whichever provider is used; a new provider is just a new adapter (Open/Closed).

1.3.1Challenges with this pattern?3 marks
  • Many adapters to write and maintain, one per provider.
  • Different data formats (XML vs JSON, currencies, date formats) and error codes.
  • A provider changes its API version, or is slow or unavailable.
1.3.2Mechanism to overcome them?3 marks
  • One common interface; a Factory or registry picks the adapter from configuration.
  • A common data object (DTO) and a mapper inside each adapter; unit-test every adapter.
  • Only that adapter changes when an API changes (version adapters); timeouts, retries, caching and fall back to another provider.

Adapter code for one provider not asked, but adds weight to 1.3

public interface HotelProvider {                 // Target
    List<Room> search(String city, LocalDate in, LocalDate out);
}
public class HiltonAdapter implements HotelProvider {  // Adapter
    private final HiltonSoapApi api = new HiltonSoapApi(); // Adaptee
    public List<Room> search(String city, LocalDate in, LocalDate out) {
        String xml = api.findRooms(city, in.toString(), out.toString());
        return RoomMapper.fromHiltonXml(xml);   // translate the result
    }
}

2022 · Question 2

Supermarket pay calculation for different employee categories.
Template Method
25 marks
QUESTION 2 · 25 MARKSA supermarket has different pay calculations for executive employees, temporary staff and daily workers. Executives: basic salary, bonus and executive allowances. Daily workers: 8 hours per day; extra hours earn overtime; more than 200 hours earns an attendance allowance. Temporary staff: called when required and paid a daily allowance for the requested dates. All employees contribute 8% to the Employee Provident Fund.
2.1Draw a diagram to depict the above scenario.4 marks
2.2What design pattern(s) can be employed? Explain the reasons for your selection.6 marks

I would use the Template Method pattern (behavioural). It defines the skeleton of an algorithm in a superclass and lets subclasses redefine certain steps without changing the structure.

Every category follows the same calculation order: work out the earnings → gross pay → deduct EPF 8% → net pay. The EPF deduction and the net calculation are the same for everyone; only the earning components differ (bonus, overtime, attendance allowance, daily allowance). So an abstract SalaryCalculator has a final calculateNetSalary() that fixes the order and does the common parts, and each category overrides only its own components.

Reasons: (1) the common EPF and net logic is written once; (2) every category is calculated in the same, enforced order, so results are consistent; (3) a new category (e.g. part-time) is one new subclass (Open/Closed). Supporting patterns: a Factory creates the right calculator from the employee's category, and the payroll run can be a Singleton so it runs once at a time.

Class diagram, challenges, and the "code duplication" statement.
Template Method
25 marks
2.3Draw a class diagram for the above design pattern.5 marks
public final double calculateNetSalary() {            // template method
    double gross = basicPay() + allowances() + overtime();
    return gross - gross * 0.08;                     // EPF 8%, same for everyone
}
2.4What challenges will you face?3 marks
  • The order of steps is rigid: a category that needs a different sequence doesn't fit.
  • The number of subclasses grows with every new category.
  • Rates and limits (8%, 200 hours, 8 hours/day) change over time.
  • A subclass might override a common step by mistake.
2.5Mechanism to overcome them?3 marks
  • Hook methods with default 0 for optional parts (bonus, overtime), so subclasses override only what they need.
  • Shared middle classes (e.g. HourlyPaid) for categories that share rules.
  • Read rates from external configuration through a Singleton ConfigManager.
  • Make the template method final and the common steps private.
2.6"Code duplication can be achieved from the used design pattern in the above scenario." Do you agree? Explain.4 marks

I disagree. Template Method is used to avoid code duplication. The parts every employee shares (the order of steps, the EPF 8% deduction, the net salary formula) are written once in the abstract SalaryCalculator. Each subclass contains only what is different for its category. Without the pattern, each category would copy the whole calculation and the EPF logic.

A small amount of duplication can remain if two subclasses override a step in the same way (e.g. two categories with the same overtime rule). The fix is to move that shared code up into the parent or into a shared middle class.

2022 · Question 3

Email spam filter made of sub-filters.
Chain of Responsibility
25 marks
QUESTION 3 · 25 MARKSDesign an email spam filter. Multiple sub-spam filters are available depending on the different components of the email, such as the email sender, the time it was sent, its content and its attachments.
3.1Sketch a diagram and explain the different components of the email spam filter.4 marks

The mail server receives the email and passes it to the first filter. The sender filter checks blacklists and domain reputation. The time filter flags odd sending hours and bursts. The content filter checks keywords, links and language patterns. The attachment filter checks file types and scans for viruses. Any filter can mark the email as spam and stop; if all pass, it is delivered to the inbox.

3.2What design pattern can you follow? Explain the reasons.5 marks

I would use the Chain of Responsibility pattern (behavioural). It avoids coupling the sender of a request to its receivers by giving more than one object a chance to handle it; the handlers are chained and the request is passed along.

Each sub-filter is a handler that extends an abstract SpamFilter and holds a link to the next filter. Reasons: (1) the mail server only knows the first filter, so it is decoupled from the filters; (2) each filter has one responsibility; (3) filters can be added, removed or reordered without changing the others; (4) the chain can be built from configuration at runtime.

2022 · Question 3 (cont.)

Prioritising the filters, extending the chain, and High Availability / Disaster Recovery.
Chain of Responsibility
25 marks
3.3How do you prioritise the different components? Explain your prioritisation criteria.6 marks
CriterionWhat it means here
Cost / speedCheap checks first (sender blacklist, sent time take microseconds); expensive ones last (content analysis, virus scanning of attachments). Most spam is stopped before the expensive filters run.
Rejection rateThe filter that catches the most spam goes early, saving work for the others.
Severity / securityA dangerous attachment (malware) may be moved earlier because the risk is high.
AccuracyFilters with few false positives come before risky ones, so good mail isn't lost.

Resulting order: Sender → Time → Content → Attachment. The order is kept in configuration so it can be tuned using real statistics.

3.4What would be your suggestion if more sub-components need to be added?5 marks

Write a new class that extends SpamFilter and implements only its own check, for example LinkReputationFilter or LanguageFilter. Insert it into the chain with setNext(), or list it in the configuration file that builds the chain. The mail server and the existing filters don't change, which follows the Open/Closed principle. Each new filter is unit-tested on its own, and a fallback "deliver to inbox" handler stays at the end.

class LinkReputationFilter extends SpamFilter {
    protected boolean isSpam(Email e) { return LinkDb.hasBadLink(e.getBody()); }
}
sender.setNext(time).setNext(content).setNext(new LinkReputationFilter()).setNext(attachment);
3.5How can you extend this design to achieve High Availability (HA) and Disaster Recovery (DR)?5 marks

HA: the filters don't keep state, so the whole chain can run on several servers behind a load balancer, with health checks and automatic restart. Incoming mail goes into a message queue so nothing is lost if a server dies. If one filter times out (e.g. the virus scanner), a backup handler skips or retries it instead of blocking all mail.

DR: blacklists, rules and the configuration are backed up and replicated to a second region. A defined RPO/RTO, automatic failover to the DR site, and regular DR drills.

2022 · Question 4

Five short scenarios. Name the pattern, explain it, give two reasons.
5 × 5 marks
25 marks
4.1Online cake ordering: users select options such as decorations and colour. Prices and delivery times differ depending on the selections.5 marks

Decorator (structural). A Cake interface has getPrice() and getDeliveryDays(). PlainCake is the base. Each option (FondantDecoration, ChocolateColour, FlowerTopping) is a decorator that wraps the cake and adds its own price and extra delivery days. Reasons: any mix of options is built at runtime without a subclass per combination (no class explosion), and a new option is just a new decorator.

Cake c = new FlowerTopping(new Fondant(new PlainCake())); → price = 2,500 + 800 + 600; days = 1 + 1 + 0.

4.2Develop a scalable and extensible product-based framework for future needs of the cake ordering system.5 marks

Factory Method (creational). A Product interface (cakes, cupcakes, gift boxes…) and a ProductFactory.create(type) that returns the right product. Client code works only with Product. Reasons: new product types are added as new classes registered with the factory, so the framework grows without changing existing code (Open/Closed), and creation logic is kept in one place. The Decorator from 4.1 can still wrap whatever the factory returns.

4.3Payroll system: salary calculation should be run by only one user, and all other connections to the salary system stopped.5 marks

Singleton (creational) with a lock. SalaryCalculationManager has a private constructor and a static getInstance(), so only one calculation engine exists. Its runPayroll(user) is synchronized and sets a running flag; while it is set, other logins and connections are refused or queued. Reasons: one controller means no two payroll runs at once (no double payments or inconsistent data), and access is controlled in one place. Note that the Singleton limits objects; the lock is what blocks other users.

4.4LMS: when users read large content, load only a couple of pages rather than the entire document.5 marks

Proxy, a virtual proxy (structural). DocumentProxy implements the same Document interface as LargeDocument. getPage(n) loads only the requested page (and maybe the next) and caches it; the full document is never loaded unless needed. Reasons: fast opening, low memory and bandwidth, and the reader code doesn't change because the interface is the same.

4.5An LMS that needs different modules to be created depending on the user's needs.5 marks

Factory Method (creational). A Module interface implemented by QuizModule, ForumModule, AssignmentModule, VideoModule. ModuleFactory.create(userNeed) returns the right one. Reasons: the LMS doesn't need to know concrete module classes (loose coupling), and new modules are added without changing the existing code.
