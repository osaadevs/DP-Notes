QUESTION 1 · 25 MARKS Overtime = Basic × OT hours / (30 × 8) · Attendance allowance: absent > 3 days → none; 1–3 days → 50% of basic; 0 days → 75% of basic · Gross = Basic + Attendance + Overtime · EPF employee = Gross × 0.08 · EPF employer = Gross × 0.12 · ETF = Gross × 0.03 · No pay = Basic × no-pay days / 30 · Tax = (Gross − 100,000) × 0.06 · Total deduction = EPF employee + No pay + Tax · Net = Gross − Total deduction · Total EPF = EPF employee + EPF employer.
Permanent employees use all of these; for executive employees there is no overtime and no no-pay.
1.1Draw a diagram to indicate the above scenario.4 marks
1.2What design pattern can be employed for the sub-systems that calculate different salary components for different employees? Reasons.5 marks

I would use the Template Method pattern (behavioural). It defines the skeleton of an algorithm in a superclass and lets subclasses redefine certain steps without changing the structure.

The calculation always runs in the same order: overtime and allowance → gross → deductions → net (dashed boxes in 1.1 are 0 for executives). An abstract SalaryCalculator has a final calculateNetSalary() containing that order and every common formula. overtime(), attendanceAllowance() and noPay() are hook methods. PermanentSalary uses the standard formulas; ExecutiveSalary overrides overtime() and noPay() to return 0. Reasons: shared formulas exist once; the same order is enforced; a new type is one subclass.

The design in code supports 1.2, write it if time allows

public abstract class SalaryCalculator {
  protected double basic;
  protected int otHours, absentDays,
                noPayDays;

  public final double calculateNetSalary() {
    double gross = basic
        + attendanceAllowance() + overtime();
    double epfEmp = gross * cfg("epf.emp");
    double taxable =
        gross - cfg("tax.threshold");
    double tax = Math.max(0,
        taxable * cfg("tax.rate"));
    return gross - (epfEmp + noPay() + tax);
  }
  // hooks with the standard formulas
  protected double overtime() {
    return basic * otHours / (30 * 8); }
  protected double noPay() {
    return basic * noPayDays / 30; }
  protected double attendanceAllowance() {
    if (absentDays == 0)
      return basic * 0.75;
    if (absentDays <= 3)
      return basic * 0.50;
    return 0; }
}
class PermanentSalary
    extends SalaryCalculator {}
class ExecutiveSalary
    extends SalaryCalculator {
  protected double overtime() { return 0; }
  protected double noPay()    { return 0; }
}

1.3Challenges with the selected pattern?4 marks
  • The order is fixed; an employee type that needs a different sequence doesn't fit.
  • Rates and thresholds change (8%, 12%, 3%, 100,000, 6%), and hard-coded values need a redeploy.
  • Subclasses multiply as new employee types appear.

1.4Mechanism to overcome them?4 marks
  • Hooks with default bodies for optional components; Strategy if a whole step must vary.
  • All rates in external configuration (1.5).
  • Shared middle classes for types with common rules.
  • Template method final; common formulas private.
1.5Many of the parameters can change over time. How would you improve configurability? State the configuration.4 marks

Move every rate and threshold out of the code into external configuration, a database table or a properties file. A Singleton ConfigManager loads it once; the calculator reads values through cfg(key). An admin screen updates them; each change is versioned with an "effective from" date and audited, so old payslips can be recalculated with the old rates. No recompile or redeploy is needed.

1.6During salary calculation no other user should be logged in and no other process should run. Which pattern and why?4 marks

Singleton, combined with a lock. PayrollEngine has a private constructor and a static getInstance(), so there is only one calculation controller in the system. Its synchronized runPayroll() sets a running flag; the login service and other processes check PayrollEngine.getInstance().isRunning() and are refused or queued until it finishes. Why: one controlling object means two calculations can't run at the same time, and the lock gives one place that blocks everyone else, so the data stays consistent.

Each service has its own database. Clients (POS terminals, head office web, mobile app) go through an API gateway. Services publish events to a message broker ("SaleCompleted" → Inventory reduces stock → Purchasing reorders when below the level). Everything runs in containers on Kubernetes.

2.4Methods to maintain data consistency in the proposed architecture?4 marks
  • Database per service, so there are no shared transactions; accept eventual consistency.
  • Saga pattern: a sale reduces stock; if the payment fails, a compensating action puts the stock back. Coordinated by events or by an orchestrator.
  • Event-driven updates through Kafka/RabbitMQ, with a transactional outbox and idempotent consumers so a repeated event does no harm.
  • CQRS read models for chain-wide reports. Two-phase commit only where it is essential.
2.5How would you achieve security?4 marks
  • OAuth2 / OpenID Connect at the gateway with JWT; roles for cashier, branch manager, buyer, head office (RBAC).
  • Mutual TLS between services; least-privilege database users.
  • HTTPS everywhere, card data handled to PCI-DSS, secrets in a vault.
  • Rate limiting, input validation, audit logs.
2.6Why is it essential to provide the same hardware configurations and options for each microservice platform?4 marks

Identical environments (containers and infrastructure-as-code) make deployment, scaling and failover predictable: any node can run any service, and performance is the same everywhere. Capacity planning, automation, monitoring and troubleshooting are simpler, it avoids "works on my machine", and a failed node can be rebuilt exactly for disaster recovery. (Exception: special nodes such as GPUs for ML.)

QUESTION 3 · 25 MARKSA restaurant has different flavours of coffee. For example, Irish Coffee is hot coffee, Irish whiskey and sugar, topped with cream; Nitro Coffee is cold-brew coffee infused with nitrogen, served on tap, with a creamy texture.
3.1Considering the many combinations that exist for coffee, what is the proposed design pattern?5 marks

I would use the Decorator pattern (structural). It attaches additional responsibilities to an object dynamically by wrapping it, which is a flexible alternative to subclassing.

The base coffees (HotCoffee, ColdBrew) are concrete components. Every ingredient (Whiskey, Sugar, Cream, Nitrogen) is a decorator that wraps a coffee and adds its own price and description. Irish Coffee = new Cream(new Sugar(new Whiskey(new HotCoffee()))); Nitro Coffee = new Nitrogen(new ColdBrew()). Reasons: the number of combinations is huge (n ingredients → 2ⁿ subclasses), so wrapping avoids class explosion; new recipes are made at runtime; a new ingredient is one new class (Open/Closed).

Integrating other vendors' websites, logging, and HA / DR.
Adapter · Singleton
25 marks
3.3The restaurant must connect to different websites to show events organised by different entities. They were developed with different technologies by different vendors. How do you integrate them?5 marks

Use the Adapter pattern (structural). The restaurant system owns one interface, EventSource with getEvents(), returning a common Event object (title, date, venue). Each website gets its own adapter (RssEventAdapter, JsonApiEventAdapter, HtmlScraperAdapter) that calls that site in its own technology and converts the result into Event. The restaurant site just loops over a list of EventSource. Reasons: the vendors' systems can't be changed; the restaurant code doesn't depend on any vendor; a new vendor is just a new adapter. A Facade (EventFeed.getAllEvents()) can then merge all sources into one list.

3.4If you must implement a logging mechanism, which design pattern can you use? Give logical reasons.5 marks

Use the Singleton pattern for the logger. Reasons: (1) all parts of the system must write to the same log file; several logger objects would open the file several times and produce duplicate or interleaved lines; (2) one instance owns the file handle, so the format and order are consistent; (3) a global access point (Logger.getInstance()) from anywhere; (4) less memory. log() is synchronized so threads don't mix lines. (Adding logging around existing services without changing them can be done with a logging Proxy that calls this Singleton.)

public final class Logger {
  private static final Logger INSTANCE =
      new Logger();
  private final PrintWriter out;
  private Logger() {
    out = Files.openAppend("app.log"); }
  public static Logger getInstance() {
    return INSTANCE; }
  public synchronized void log(String m) {
    out.println(LocalDateTime.now()
        + " " + m);
  }
}
3.5How can you extend this design to achieve High Availability (HA) and Disaster Recovery (DR)?5 marks

HA: run the ordering application as several stateless copies behind a load balancer, with health checks and auto-restart; the database is replicated with automatic failover. Event adapters use timeouts, retries and a cache of the last events, so a vendor site being down doesn't break the page. A single logger instance per server ships logs to a central, replicated log store, so the Singleton isn't a single point of failure. DR: regular backups, the database replicated to a second region, agreed RPO/RTO, automated failover, infrastructure-as-code to rebuild, and DR drills.

4.1Fantasy cricket: the user selects a maximum of five batsmen, five bowlers and one wicketkeeper; there should be one captain. How would you use an extended Singleton to achieve this?5 marks

An extended Singleton is a Multiton: the class controls how many objects can exist, but the limit is N per key instead of 1. Player has a private constructor; the only way to get one is addPlayer(role, name), which counts the players of that role and throws an exception once the limit (5 batsmen, 5 bowlers, 1 wicketkeeper) is reached. Captain is a plain Singleton (exactly one).

public static synchronized Player addPlayer(
        String role, String name) {
  team.putIfAbsent(role, new ArrayList<>());
  int n = team.get(role).size();
  if (n >= LIMIT.get(role))
    throw new IllegalStateException(
        "Max " + role + " reached");
  Player p = new Player(role, name);
  team.get(role).add(p);
  return p;
}
4.2A banking system with different types of accounts: Current, Saving and Children accounts.5 marks

Factory Method (creational). An Account interface with deposit(), withdraw(), calculateInterest(). CurrentAccount (overdraft, no interest), SavingAccount (interest) and ChildrenAccount (withdrawal limit, guardian) implement it. AccountFactory.createAccount(type) returns the right one. Reasons: the bank code works only with Account (loose coupling), creation logic is in one place, and a new account type (FixedDeposit) is added without changing existing code.

Exceptions by priority, loading part of a document, and authorization options.
Chain · Proxy
15 marks
4.3An exception-handling system that can handle different priorities depending on the problem.5 marks

Chain of Responsibility (behavioural). Each handler deals with the exceptions of its own priority and passes the rest to the next: LowPriorityHandler (validation errors: show a message) → MediumPriorityHandler (payment or timeout errors: retry) → HighPriorityHandler (system failures: log and alert the admin) → DefaultHandler (generic error page). Reasons: the code that throws doesn't need to know who handles it; handlers can be added or reordered; it works like nested try/catch blocks.

4.4LMS: when users read large content, load only a couple of pages rather than the entire document.5 marks

Proxy, a virtual proxy (structural). DocumentProxy and LargeDocument both implement Document. The reader holds the proxy; getPage(n) loads only that page from storage and caches it, and the full document is never loaded unless needed. Reasons: fast opening, low memory and bandwidth; same interface, so the reader code doesn't change.

4.5A website with different authorization options, depending on the user's need.5 marks

Proxy, a protection proxy (structural). Each protected service (ReportService, AdminService) sits behind a proxy with the same interface. The proxy checks the user's role and permissions, logs the access and only then forwards the call. Reasons: security is in one place and the real services stay clean; access rules change without touching the services. If authorization is a series of checks (login → role → permission → 2FA), combine with a Chain of Responsibility.
