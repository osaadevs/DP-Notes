QUESTION 1 · 25 MARKSA supermarket introduces a self-checkout kiosk. Customers scan items, apply optional add-ons (gift-wrap, eco-bag, express packing) and pay. The kiosk operates in the states Idle, Scanning, Payment and Completed. An item's price can have dynamic add-ons without subclasses for every combination. 1.1Identify suitable design patterns with reasons for: (a) managing kiosk states, (b) applying optional add-ons and calculating the final price dynamically, (c) ensuring only one tax calculator instance.6 marks
(a) kiosk statesStateThe kiosk behaves differently in each state (scanning is ignored when Completed, paying is refused when Idle). Each state is its own class that handles the actions and decides the next state, so there is no if/else on a status flag, and a new state is just a new class.
(b) add-onsDecoratorEach add-on wraps the item and adds its own cost and description, so any combination is built at runtime without 2ⁿ subclasses. A new add-on is a new class (Open/Closed).
(c) one tax calculatorSingletonA private constructor and a static getInstance() give one shared instance, so every counter uses the same rate and rules, and a rate change applies everywhere at once.

Kiosk states with an example transition, and the Singleton in the pricing flow.
State · Singleton
9 marks
1.4Explain how you would incorporate the kiosk states (Idle → Scanning → Payment → Completed) using a design pattern. Provide an example transition.5 marks

Use the State pattern. Kiosk is the context and holds a KioskState. IdleState, ScanningState, PaymentState and CompletedState implement scanItem(), checkout(), pay() and cancel(). The kiosk passes every button press to its current state, and the state calls kiosk.setState(next) to move on.

Example transition: in ScanningState, the customer presses Checkout. checkout() adds up the items' getCost(), adds tax through the Singleton, stores the total and calls kiosk.setState(new PaymentState()). If the customer presses Pay while still Idle, IdleState.pay() refuses: "scan items first".

public class ScanningState implements KioskState {
    public void scanItem(Kiosk k, CheckoutItem i) { k.addItem(i); }      // stay
    public void checkout(Kiosk k) {
        double total = TaxCalculator.getInstance().applyTax(k.subtotal());
        k.setTotal(total);
        k.setState(new PaymentState());                                     // transition
    }
    public void pay(Kiosk k, double amt) { System.out.println("Press checkout first"); }
}
1.5Describe how the Singleton tax calculator can be integrated into the pricing flow.4 marks

Each scanned item is wrapped with its add-ons, so item.getCost() is already the final item price. When the kiosk moves to the Payment state it adds up the item costs and calls TaxCalculator.getInstance().applyTax(subtotal). Because every counter calls getInstance(), they all get the same calculator with the same rate and rules, so tax is consistent across the store. When the rate changes, it is updated once (from configuration) and every counter uses it immediately.

public final class TaxCalculator {
  private static final TaxCalculator INSTANCE
      = new TaxCalculator();
  private double rate = Config.get("vat");
  private TaxCalculator() { }
  public static TaxCalculator getInstance() {
    return INSTANCE; }
  public double applyTax(double subtotal) {
    return subtotal * (1 + rate); }
}

3.4Explain how you would handle the membership check → availability check → fine check.5 marks

With Chain of Responsibility. An abstract BorrowCheck holds a link to the next check. MembershipCheck, AvailabilityCheck and FineCheck each implement only their own test. The chain is built once in this order and every request goes to the first check. If a check fails, the chain stops and returns the reason ("membership expired", "book not available", "pending fine Rs. 200"); if all pass, the borrow goes ahead. A new rule (e.g. BorrowLimitCheck) is one new class added with one link.

public abstract class BorrowCheck {
  private BorrowCheck next;
  public BorrowCheck linkWith(BorrowCheck n) {
    next = n;
    return n;
  }
  public String check(Request r) {
    String err = test(r);
    if (err != null) return err;   // stop
    return next == null ? null
                        : next.check(r);
  }
  protected abstract String test(Request r);
}
class MembershipCheck extends BorrowCheck {
  protected String test(Request r) {
    return r.getUser().isMember() ? null
        : "Membership expired";
  }
}
// AvailabilityCheck, FineCheck: same shape

BorrowCheck chain = new MembershipCheck();
chain.linkWith(new AvailabilityCheck())
     .linkWith(new FineCheck());
String err = chain.check(request);
if (err == null) borrowService.issue(request);
else System.out.println(err);

The validation flow, the OrderID generator, and how all four patterns fit together.
Chain · Singleton
10 marks
3.4Briefly outline how a design pattern can be used for the validation flow (inventory → fraud → delivery area).5 marks

Chain of Responsibility (pipeline form). An abstract Validator holds next; InventoryCheck, FraudCheck and DeliveryAreaCheck each implement check(order). The chain is built once in this order and the order service sends each order to the first validator. A failed check stops the chain and rejects the order with a reason; if all pass, payment starts. Cheap checks go first (inventory) and the expensive fraud scoring later. A new check (e.g. AddressFormatCheck) is one class and one link, and nothing else changes.

abstract class Validator {
  private Validator next;
  Validator linkWith(Validator n) {
    next = n; return n; }
  boolean validate(Order o) {
    if (!check(o)) return false;
    return next == null
        || next.validate(o);
  }
  abstract boolean check(Order o);
}
Validator v = new InventoryCheck();
v.linkWith(new FraudCheck())
 .linkWith(new DeliveryAreaCheck());
3.5Explain how you will design an OrderID generator and how it integrates with payment processing.5 marks

An eager Singleton: private constructor, one static final instance, and a thread-safe AtomicLong counter, so two orders placed at the same moment can never get the same ID. Integration: the first step of the template method PaymentProcessor.handlePayment() calls OrderIdGenerator.getInstance().nextId() and stores the ID on the order, then validate → process → send receipt (which prints the ID). Every payment type (card, PayPal, COD) inherits that step, so all share the one generator. For HA across several servers, the counter is backed by a database sequence.

public final class OrderIdGenerator {
  private static final OrderIdGenerator
      INSTANCE = new OrderIdGenerator();
  private final AtomicLong counter =
      new AtomicLong(1000);
  private OrderIdGenerator() { }
  public static OrderIdGenerator
      getInstance() { return INSTANCE; }
  public String nextId() {
    return "ORD-"
        + counter.incrementAndGet();
  }
}
