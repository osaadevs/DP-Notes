Coffee shop with optional ingredients, different profit per coffee, and one shared logger.
Decorator + Singleton
25 marks
QUESTION 1 · 25 MARKSIn a coffee shop, customers order a base coffee and add optional ingredients (milk, sugar, chocolate). The price depends on the base type and the selected additions. You need a flexible way to calculate the price dynamically without a complex hierarchy of subclasses for every combination of coffee and ingredients.
1.1What is the best design pattern for the above scenario?5 marks

The Decorator pattern (structural). It attaches additional responsibilities to an object dynamically by wrapping it, which is a flexible alternative to subclassing.

The base coffee is a concrete component; Milk, Sugar and Chocolate are decorators. Each decorator implements the same Coffee interface, holds the coffee it wraps, adds its own price and description, and passes the rest of the call inwards. Reasons: (1) no class explosion: 3 ingredients would need 2³ = 8 subclasses per base coffee, here it's one class per ingredient; (2) the price is worked out at runtime from whatever the customer picks; (3) a new ingredient is a new class and nothing existing changes (Open/Closed); (4) each decorator has one responsibility.

1.2Define a Coffee interface with getCost() and getDescription().5 marks
// Component: every coffee and every
// decorator has these two methods
public interface Coffee {
    double getCost();
    String getDescription();
}
1.3Create a BasicCoffee class implementing the Coffee interface.5 marks
// Concrete component: the base coffee
public class BasicCoffee implements Coffee {
    public double getCost() {
        return 200.0;
    }
    public String getDescription() {
        return "Basic coffee";
    }
}

The decorators that make 1.2 and 1.3 work, the profit extension, and the logger.

Show the decorators too adds strength to 1.1–1.3

public abstract class CoffeeDecorator
        implements Coffee {
    protected Coffee coffee;    // wrapped
    public CoffeeDecorator(Coffee c) {
        coffee = c; }
    public double getCost() {
        return coffee.getCost(); }
    public String getDescription() {
        return coffee.getDescription(); }
}
public class Milk extends CoffeeDecorator {
    public Milk(Coffee c) { super(c); }
    public double getCost() {
        return coffee.getCost() + 80; }
    public String getDescription() {
        return coffee.getDescription()
               + ", milk"; }
}
// Sugar +20, Chocolate +120: same shape
Coffee c = new BasicCoffee();
c = new Sugar(new Milk(c));
c.getCost();   // 200 + 80 + 20 = 300
1.4If there is a different profit for each coffee, how would you extend the above design?5 marks

Option A: add getProfit() to the Coffee interface. Each base coffee returns its own margin; each decorator returns coffee.getProfit() plus its add-on profit. Selling price = getCost() + getProfit().

Option B (better, Open/Closed): add a new ProfitMargin decorator that wraps the finished drink and adds a percentage. No existing class changes, and each coffee can get a different rate: new ProfitMargin(espresso, 0.25), new ProfitMargin(latte, 0.35). The rates can be read from configuration.

public class ProfitMargin
        extends CoffeeDecorator {
    private final double rate;
    public ProfitMargin(Coffee c, double r) {
        super(c);
        rate = r;
    }
    public double getCost() {
        return coffee.getCost() * (1 + rate);
    }
}
1.5A logger must write all logs to the same file or output stream; multiple instances would cause duplicate or inconsistent output. Propose a design pattern.5 marks

Use the Singleton pattern (creational). It ensures a class has only one instance and provides a global point of access to it. The Logger has a private constructor and a static getInstance(), so every class gets the same logger, which owns the one file handle. Reasons: no duplicate or interleaved lines, one consistent format and order, less memory, and easy access from anywhere. log() is synchronized so lines from different threads don't mix.

public final class Logger {
  private static volatile Logger instance;
  private final PrintWriter out;
  private Logger() {
    out = Files.openAppend("app.log"); }
  public static Logger getInstance() {
    if (instance == null) {
      synchronized (Logger.class) {
        if (instance == null)
          instance = new Logger();
      }
    }
    return instance;
  }
  public synchronized void log(String m) {
    out.println(m); }
}

2.4Methods to maintain data consistency in the proposed architecture?5 marks
  • Database per service, so no shared transactions; we accept eventual consistency (search may show a book as available for a second).
  • Saga for borrowing: reserve the copy → record the loan → update the user's history. If a step fails, compensating actions undo the earlier ones (release the copy).
  • Event-driven updates with a transactional outbox and idempotent consumers.
  • CQRS: the search index is a read model rebuilt from events; the Borrowing service is the source of truth for availability at checkout.
2.5How would you achieve security in the proposed architecture?5 marks
  • Users: login with OAuth2 / OpenID Connect at the gateway, which issues JWT tokens. Roles: member, librarian, admin (only librarians add or update books).
  • Service to service: mutual TLS (service mesh), short-lived tokens, each service only allowed to call what it needs.
  • Data: HTTPS everywhere, personal data and borrowing history encrypted at rest, secrets in a vault, least-privilege DB users.
  • Attacks: rate limiting on search, input validation, a web application firewall, audit logs.

Document workflow: Draft → Moderation → Published → Archived.
State
25 marks
QUESTION 3 · 25 MARKSDraft: created and editable; can move to Moderation. Moderation: under review; approved → Published, or rejected → back to Draft. Published: final, can't be edited; can only move to Archived. Archived: stored permanently, no further transitions.
3.1Define the state diagram for the above scenario.5 marks

Start dot, a rounded box per state, every arrow labelled with its event, and a bullseye after Archived because it is final.

3.2What is the best design pattern for this scenario? Provide reasons.5 marks

The State pattern (behavioural). It allows an object to change its behaviour when its internal state changes; the object appears to change its class.

Reasons: (1) the document has a fixed set of four states, and the same action behaves differently in each: edit() works in Draft but is refused in Published, approve() only works in Moderation; (2) without the pattern, every method would need an if/else on a status field, growing with each state; (3) each state class holds its own rules and decides the next state, so illegal moves (Archived → Draft) are refused cleanly; (4) a new state (e.g. "Under Legal Review") is a new class, and nothing else changes (Open/Closed).

3.4Explain the use of interfaces (OOP concept) in the above design.5 marks
  • DocumentState is a contract: every state must implement every event (edit, submit, approve, reject, archive), so nothing is forgotten.
  • Document holds a DocumentState reference and calls state.submit(this) without knowing which state it is: polymorphism, programming to an interface.
  • New states plug in without changing Document (Open/Closed, Dependency Inversion); states can be swapped at runtime and mocked in tests.

2024 · Question 4

E-commerce checkout: standard steps, exceptions, abstract classes, authorization levels.
Template · Chain · Proxy
25 marks
QUESTION 4 · 25 MARKSA standard checkout process: Validate cart (valid items, enough stock) → Process payment (credit card, PayPal, cash on delivery) → Arrange delivery (varies: domestic or international) → Send confirmation (email or SMS).
4.1Draw a diagram to depict the above scenario.5 marks
4.2What is the best design pattern for this case? Explain.5 marks

The Template Method pattern (behavioural). The checkout always has the same four steps in the same order; only payment and delivery differ. An abstract CheckoutProcess has a final checkout(order) that runs validate cart → process payment → arrange delivery → send confirmation. Validate cart and send confirmation are written once; processPayment() and arrangeDelivery() are abstract and implemented by subclasses such as DomesticCheckout and InternationalCheckout. Reasons: the order is enforced for every order, common steps aren't duplicated, and a new delivery type is just a subclass. (To avoid a subclass for every payment × delivery pair, the payment can be a separate object created by a Factory.)

2024 · Question 4 (cont.)

Exceptions, abstract classes and authorization levels.
Chain · Template · Proxy
15 marks
4.3An exception-handling system is to be included. How would you handle the different types of exceptions?5 marks

Use Chain of Responsibility. Each handler deals with one type of exception and passes the rest on: OutOfStockHandler (tell the customer, suggest alternatives) → PaymentFailedHandler (retry or offer another method) → DeliveryErrorHandler (re-schedule, notify the courier) → SystemErrorHandler (log, alert the admin, show a friendly error). Ordered by how common and how severe they are. Reasons: the checkout code doesn't need to know who handles each error; a new type of exception is a new handler; it works like try/catch.

abstract class CheckoutErrorHandler {
  protected CheckoutErrorHandler next;
  public void handle(CheckoutException e) {
    if (canHandle(e)) resolve(e);
    else if (next != null) next.handle(e);
  }
  abstract boolean canHandle(
      CheckoutException e);
  abstract void resolve(
      CheckoutException e);
}
4.4How can abstract classes be used in the above scenario?5 marks
  • CheckoutProcess is abstract because it must hold real code (the fixed order in the final checkout(), and the common steps validate cart and send confirmation) and declare abstract steps (processPayment(), arrangeDelivery()) that each subclass must write.
  • It can't be instantiated on its own, because a "general" checkout makes no sense; only DomesticCheckout or InternationalCheckout can be created.
  • An interface couldn't do this: it can't enforce the order or share the common code. Subclasses are used through the abstract type (polymorphism), and final stops them changing the order.
  • CheckoutErrorHandler in 4.3 is also abstract: it holds the shared next link and passing logic.
4.5How would you incorporate different levels of authorization?5 marks

Protection Proxy. Sensitive operations (refunds, price changes, viewing all orders) sit behind proxies with the same interface; the proxy checks the user's role (customer, support agent, manager, admin) before forwarding, and logs the access. If an action needs approval that escalates with the amount (support can refund up to 5,000, a manager up to 50,000, above that an admin), use a Chain of Responsibility of approvers, each handling its level and passing larger requests up. Roles come from the JWT token issued at login (RBAC).
