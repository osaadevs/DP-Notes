QUESTION 1 · 25 MARKS A city installs electric vehicle (EV) charging points. A charging session can be in these states: Available, Reserved (a driver booked it in the app), Charging, Payment due and Completed. Any point can also go Faulty, and then it accepts nothing until a technician resets it. What the point does when a driver taps "start", "stop" or "pay" depends on its current state.
The charging hardware comes from two vendors that the city cannot modify: Vendor A's charger offers startCharge(double kW) / halt(); Vendor B's offers beginSession(int port, String mode) / endSession(int port). The session software expects start() and stop().
1.1Explain why the State pattern is appropriate for a charging session.4 marks

A session has a fixed set of well-defined states, and the same action behaves differently in each: "start" begins charging when Reserved (for that driver) but is refused when Faulty; "pay" only works in Payment due. Without the pattern, every method needs a growing if/switch on the status. With State, each state is a class holding its own rules and deciding the next state, so invalid actions are refused cleanly, transitions are explicit, and a new state (e.g. Overstay with an idle fee) is just a new class.

1.2Draw a state diagram for a charging session.5 marks

"Any state → Faulty" can be drawn as one note, or arrows from the main states, labelled fault().

public class ChargingSession {
    private SessionState state = new AvailableState();
    private final Charger charger;          // the adapter from 1.5
    private double kWh;

    public ChargingSession(Charger c) { charger = c; }
    public void setState(SessionState s) { state = s; }
    public Charger getCharger() { return charger; }

    // every request is handed to the current state
    public void reserve(Driver d) { state.reserve(this, d); }
    public void start()           { state.start(this); }
    public void stop()            { state.stop(this); }
    public void pay(double amt)    { state.pay(this, amt); }
    public void fault()           { setState(new FaultyState()); }
}
1.5The session software must work with both vendors' chargers. Provide a solution using design pattern knowledge, with code for one vendor.6 marks

Use the Adapter pattern. The session software depends on one target interface it owns, Charger with start() and stop(). VendorAAdapter and VendorBAdapter implement Charger, each holding that vendor's class (the adaptee) and translating the call: Vendor A needs a power level in kW; Vendor B needs a port and a mode. ChargingState just calls session.getCharger().start() and never knows the vendor. Why: the hardware software can't be modified, the state classes stay the same for every vendor, and a third vendor is one more adapter (Open/Closed).

public interface Charger {     // target
  void start();
  void stop();
}
public class VendorBAdapter
        implements Charger {
  private final VendorBCharger hw;
  private final int port;
  public VendorBAdapter(VendorBCharger hw,
                        int port) {
    this.hw = hw; this.port = port; }
  public void start() {
    hw.beginSession(port, "FAST"); }
  public void stop() {
    hw.endSession(port); }
}

ScalabilityFlight Search takes far more traffic than booking (many searches per booking, spikes during sales), so it scales out on its own with a cache of fares and availability; Check-in scales in the hours before departures; Loyalty stays small.

2.3Propose a suitable microservices architecture.5 marks

Services, each with its own database: Flight/Inventory (schedules, seats), Search (read-optimised index built from flight events, CQRS), Booking, Payment (gateway adapters for cards and wallets), Check-in (boarding passes), Loyalty, Notification. Web, mobile and travel-agent clients go through an API gateway. Booking calls Flight/Inventory synchronously to hold seats, and publishes events to Kafka ("BookingConfirmed" → Loyalty adds miles, Notification sends the e-ticket; "FlightDelayed" → Notification alerts passengers). Kubernetes, registry, config and monitoring.

2.4How would you keep data consistent, for example so that two passengers can't get the same seat?5 marks
  • Database per service; the Flight/Inventory service is the single owner of seat data and holds seats with a local ACID transaction or an optimistic lock (version number), so the same seat can't be sold twice.
  • Saga for booking: hold seat (with a 15-minute expiry) → take payment → confirm booking → issue ticket. If payment fails, a compensating action releases the seat.
  • Transactional outbox and idempotent consumers, so a repeated "PaymentSucceeded" never books twice.
  • Eventual consistency for search results and loyalty miles, which can lag a few seconds.
2.5How would you secure passenger data and communication between services?5 marks
  • Users: OAuth2 / OpenID Connect at the gateway with JWT; roles for passenger, travel agent, airport staff, admin.
  • Data: passport and payment data encrypted at rest and in transit; card data to PCI-DSS through the payment provider; personal data handled under privacy laws; secrets in a vault.
  • Service to service: mutual TLS via a service mesh, least-privilege access (Loyalty can't read passport numbers).
  • Rate limiting and bot protection on search, a WAF, audit logs and alerts.

3.5Discuss two challenges of the design used for the extras and how you would handle them.4 marks
  • Many small classes and long wrapping chains (new A(new B(new C(room)))) are hard to read and debug. → A builder (or the factory) assembles the chosen extras in one place; each decorator logs what it adds.
  • Order and duplicates matter: a percentage discount applied before or after extras gives different totals, and breakfast could be added twice. → Fix the wrapping order in the builder and reject duplicate extras.
  • (Also acceptable: identity checks fail because the outer object isn't a DeluxeRoom; performance cost of many layers is small but grows.)
QUESTION 4 · 25 MARKS An online store automates returns. A return request is checked in order: valid receipt → within 14 days → item condition → refund limit. The checks must be easy to change and extend.
Every refund follows the same steps: validate the request → calculate the amount → issue the refund → notify the customer. Issuing the refund differs for card, cash on delivery (bank transfer) and store credit.
For auditing, every refund must be written to one central audit log in order, with no duplicate entries. The returns service must keep working even if a server or a data centre fails.
4.1Identify suitable design patterns, with reasons, for: (a) the return checks, (b) the refund steps, (c) the audit log.6 marks
(a) return checksChain of ResponsibilityReceipt → 14 days → condition → limit as linked handlers; a failure stops the request with a reason; checks can be reordered or added without touching the others.
(b) refund stepsTemplate MethodA final processRefund() fixes the four steps; only issueRefund() differs per refund method, so the process is standard and shared steps are written once.
(c) audit logSingletonOne AuditLogger instance owns the log and writes entries in order through one synchronized method, so there are no duplicates or interleaving.
4.2Write the abstract class for the refund steps, and one subclass.5 marks
public abstract class RefundProcess {
  public final void processRefund(
          ReturnRequest r) {
    if (!validate(r)) return;
    double amt = calculate(r);
    issueRefund(r, amt);       // varies
    notifyCustomer(r, amt);
    AuditLogger.getInstance()
        .log("Refund " + r.getId()
             + " " + amt);
  }
  protected boolean validate(
          ReturnRequest r) {
    return r.isApproved(); }
  protected double calculate(
          ReturnRequest r) {
    return r.getItemPrice(); }
  protected abstract void issueRefund(
          ReturnRequest r, double a);
  private void notifyCustomer(
          ReturnRequest r, double a) {
    Mailer.send(r.getEmail(),
                "Refunded " + a); }
}
public class StoreCreditRefund
        extends RefundProcess {
  protected double calculate(
          ReturnRequest r) {
    // 10% bonus for taking store credit
    return r.getItemPrice() * 1.10; }
  protected void issueRefund(
          ReturnRequest r, double a) {
    Wallet.of(r.getCustomer()).add(a); }
}

4.3Outline how the return checks would be implemented.5 marks

An abstract ReturnCheck holds a link to the next check and a check(request) that returns a failure reason or passes the request on. ReceiptCheck, WithinDaysCheck, ConditionCheck and RefundLimitCheck each test one thing. The chain is built once (the order can come from configuration) and every request goes to the first check. If all pass, the refund process from 4.2 starts. A new rule, such as SerialNumberCheck for electronics, is one new class with one link.

abstract class ReturnCheck {
  private ReturnCheck next;
  ReturnCheck then(ReturnCheck n) {
    next = n; return n; }
  String check(ReturnRequest r) {
    String fail = test(r);
    if (fail != null) return fail;
    return next == null ? null
                        : next.check(r);
  }
  abstract String test(ReturnRequest r);
}
class WithinDaysCheck extends ReturnCheck {
  String test(ReturnRequest r) {
    return r.daysSincePurchase() <= 14
        ? null : "Older than 14 days"; }
}
4.4Write the audit log class and explain why it prevents duplicate or out-of-order entries.4 marks
public final class AuditLogger {
  private static final AuditLogger
      INSTANCE = new AuditLogger();
  private final AtomicLong seq =
      new AtomicLong();
  private AuditLogger() { }
  public static AuditLogger getInstance() {
    return INSTANCE; }
  public synchronized void log(String e) {
    AuditStore.append(
        seq.incrementAndGet(), e);
  }
}

The private constructor means no other logger object can exist; every refund calls the same getInstance(). Because there is one object, there is one writer and one sequence counter, and log() is synchronized, so two refunds at the same moment are written one after the other with increasing sequence numbers, never twice and never interleaved. (For several servers, AuditStore is a replicated, append-only store.)

4.5How would you extend the design for High Availability and Disaster Recovery?5 marks

HA: the check chain and refund classes keep no state, so the returns service runs as several copies behind a load balancer, with health checks and automatic restart (Kubernetes). Requests go through a message queue so none are lost if a copy dies. The database is replicated with automatic failover. Each server's Singleton logger writes to a shared, replicated audit store, so the logger isn't a single point of failure, and a refund is made idempotent (refund ID checked) so a retry never pays twice. DR: regular backups, the database and audit log replicated to a second region, agreed RPO/RTO, automated failover, infrastructure-as-code to rebuild, and regular DR drills.
