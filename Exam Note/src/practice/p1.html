QUESTION 1 · 25 MARKS QuickBite is a food delivery app. A customer's order moves through these stages: Placed → Confirmed by the restaurant → Preparing → Out for delivery → Delivered. An order can be Cancelled only before it is out for delivery. What a customer can do (cancel, track, rate) depends on the current stage.
QuickBite works with many restaurants. Each restaurant already uses its own point-of-sale system from a different vendor: one accepts orders through pushOrder(xml), another through createTicket(json). QuickBite cannot change these systems.
When a customer taps "Place order", the app must check the restaurant, take the payment, assign a rider and send notifications. The mobile team wants one simple call for this instead of talking to four services.
1.1Identify a suitable design pattern, with reasons, for each of: (a) the order stages, (b) sending orders to the restaurants' different systems, (c) the single "Place order" call.6 marks
(a) order stagesStateThe order behaves differently in each stage: cancel is allowed while Placed, Confirmed or Preparing but refused once out for delivery; rating only works after Delivered. Each stage becomes a class that knows its allowed actions and its next stage, so there are no if/else checks on a status field.
(b) restaurant systemsAdapterThe restaurants' systems have incompatible methods and can't be changed. One adapter per vendor converts QuickBite's sendOrder(order) into pushOrder(xml) or createTicket(json); a new vendor is just a new adapter.
(c) one "Place order"FacadeOrderFacade.placeOrder() calls restaurant check → payment → rider → notification in the right order, so the mobile app depends on one class instead of four services.

public interface OrderState {
  void confirm(Order o);
  void startPreparing(Order o);
  void dispatch(Order o);
  void deliver(Order o);
  void cancel(Order o);
}
public class Order {           // context
  private OrderState state =
      new PlacedState();
  public void setState(OrderState s) {
    state = s; }
  // every request goes to the state
  public void confirm() {
    state.confirm(this); }
  public void dispatch() {
    state.dispatch(this); }
  public void cancel() {
    state.cancel(this); }
  // startPreparing(), deliver(): same
}
public class OutForDeliveryState
        implements OrderState {

    System.out.println(
      "Already confirmed"); }
  public void startPreparing(Order o) {
    System.out.println(

1.5Give one challenge of the "Place order" design in (c) and how you would overcome it.3 marks

Challenge: if one service fails half way (payment succeeded but no rider is free), the order is left half done, and the facade becomes a single point of failure. Fix: compensating actions inside the facade (refund the payment, tell the restaurant to cancel), timeouts and retries for each service, and run the facade as several stateless copies behind a load balancer. (Other valid answer: the facade growing into a God class → split it into OrderFacade and TrackingFacade, delegating only.)

QUESTION 2 · 25 MARKS A private hospital group with five branches wants a new system built as microservices. Key functional requirements: Patient management (register patients, medical history, profiles) · Appointments (book, reschedule, cancel channelling sessions with doctors) · Doctors & staff (schedules, availability, specialities) · Pharmacy (prescriptions, stock, dispensing) · Laboratory (test orders and results) · Billing (invoices, insurance claims, payments) · Notifications (SMS reminders, results ready).
2.1Draw a diagram to depict the microservices scenario.5 marks
2.2How can the hospital implement and manage this architecture to achieve scalability, fault isolation and continuous deployment?5 marks
ScalabilityScale each service on its own: Appointments peaks in the morning when channelling opens, so it auto-scales; Lab and Pharmacy scale per branch; Billing stays small. Stateless services on Kubernetes with auto-scaling and caching of doctor schedules.
Fault isolationEach service has its own process and database. If Notification fails, appointments are still booked and SMS messages wait in the queue; if Billing is down, doctors still see patients. Circuit breakers, timeouts, retries, bulkheads.
Continuous deploymentA repository and CI/CD pipeline per service, automated tests, Docker images, blue-green releases at night, versioned APIs, so Pharmacy can be updated without touching Appointments.
Manage itAPI gateway, service registry, config server, central logging, metrics and tracing; one team per service.
2.3Propose a suitable microservices architecture.5 marks

One service per capability, each with its own database: Patient, Appointment, Doctor/Staff, Pharmacy, Laboratory, Billing (with an insurance adapter), Notification. Web portal, mobile app and branch counters go through an API gateway (authentication, routing). Services use REST when they need an answer now (Appointment asks Doctor "is Dr. Perera free at 10:00?") and publish events to a message broker otherwise ("LabResultReady" → Notification sends an SMS; "PrescriptionIssued" → Pharmacy prepares it). Containers on Kubernetes across the branches, plus a service registry, config server and monitoring.

2.4What methods can maintain data consistency across the services?5 marks
  • Database per service, so no shared transactions; accept eventual consistency where safe (notification history).
  • Saga for an appointment: reserve the doctor's slot → take the booking fee → confirm. If payment fails, a compensating action frees the slot.
  • Events through a broker with a transactional outbox and idempotent consumers, so a repeated "PrescriptionIssued" doesn't dispense twice.
  • CQRS read models for a patient's full history view; stronger consistency for medication stock and billing.
2.5How would you secure patient data and communication between services?5 marks
  • Users: OAuth2 / OpenID Connect at the gateway with JWT; strict roles (doctor, nurse, pharmacist, cashier, patient), so a cashier can't read lab results.
  • Patient data: encrypted at rest and in transit, access to records logged (audit trail), data kept to health-data privacy rules, secrets in a vault.
  • Service to service: mutual TLS (service mesh), short-lived tokens, least-privilege database users per service.
  • Rate limiting, input validation, a web application firewall, and alerts on unusual access (one user opening hundreds of records).
QUESTION 3 · 25 MARKS A company builds a smart home app. Homes have lights, door locks, air conditioners and cameras from different manufacturers; some speak Zigbee (zbSwitch(id, on)), others Bluetooth (btWrite(mac, cmd)), and the app can't change the devices' software.
An "Away mode" button must turn off all lights, lock every door, set the AC to eco and arm the cameras, all in one tap.

3.3Write Java for the component that stops guests controlling anything except lights.5 marks
public interface Device {
  String getType();       // "LIGHT", "LOCK"…
  void turnOn();
  void turnOff();
}
public class DeviceProxy implements Device {
  private final Device real;
  private final User user;
  public DeviceProxy(Device d, User u) {
    real = d; user = u; }
  public String getType() {
    return real.getType(); }
  public void turnOn() {
    check();
    AuditLog.record(user, real, "ON");
    real.turnOn();
  }
  public void turnOff() {
    check();
    AuditLog.record(user, real, "OFF");
    real.turnOff();
  }
  private void check() {
    if (user.isGuest()
        && !real.getType().equals("LIGHT"))
      throw new AccessDeniedException(
          "Guests can only control lights");
  }
}
3.4Explain which SOLID principles your design follows.5 marks
  • Single Responsibility: each adapter only translates for one vendor; the proxy only checks access; the facade only coordinates.
  • Open/Closed: a new device brand is a new adapter, and a new scene ("Night mode") is a new facade method; existing classes don't change.
  • Liskov Substitution: a DeviceProxy or any adapter can be used anywhere a Device is expected.
  • Interface Segregation: Device is small; a camera-only action (arm()) goes in a separate Armable interface rather than forcing lights to implement it.
  • Dependency Inversion: the facade and hub depend on the Device abstraction, not on Zigbee or Bluetooth classes.
QUESTION 4 · 25 MARKS A university's online exam platform runs every exam through the same process: authenticate the student → load the paper → conduct the exam → evaluate → publish results. Evaluation differs by exam type: MCQ exams are auto-marked, essay exams are marked by a lecturer with a rubric, and programming exams run hidden test cases.
Question objects (MCQ, essay, coding) are created depending on what the lecturer adds. When a student submits, the answer script goes through checks in order: time limit → file format → plagiarism; more checks will be added later.
Departments may switch on optional proctoring features (webcam monitoring, screen recording, AI flagging) for any exam, in any combination.
4.1Identify suitable patterns, with reasons, for: (a) the common exam process, (b) creating question objects, (c) submission checks, (d) optional proctoring features.8 marks
(a) exam processTemplate MethodThe five steps are fixed in a final runExam(); only evaluate() differs, so the order is enforced and the common steps are written once.
(b) question objectsFactory MethodQuestionFactory.create(type) returns MCQ, Essay or Coding questions, so the editor never uses new and new types are easy to add.
(c) submission checksChain of ResponsibilityTime limit → format → plagiarism as linked handlers; any failure stops it; more checks are one class and one link each.
(d) proctoringDecoratorEach feature wraps the exam session and adds its monitoring, in any combination at runtime, without a subclass per mix.
4.2Write the abstract class for the exam process using the pattern from (a).5 marks
public abstract class ExamProcess {
    public final void runExam(Student s) {      // template method: order is fixed
        if (!authenticate(s)) return;
        Paper p = loadPaper();
        Script script = conduct(s, p);
        double mark = evaluate(script);             // the step that differs
        publish(s, mark);
    }
    private boolean authenticate(Student s) { return Auth.verify(s); }   // common
    private Paper loadPaper() { return PaperStore.current(); }       // common
    protected Script conduct(Student s, Paper p) { return Exam.run(s, p); } // hook
    protected abstract double evaluate(Script script);
    private void publish(Student s, double m) { Results.save(s, m); }  // common
}
4.3Write a ProgrammingExam subclass.3 marks
public class ProgrammingExam extends ExamProcess {
    protected double evaluate(Script script) {
        int passed = TestRunner.runHiddenTests(script.getCode());
        return passed * 100.0 / TestRunner.TOTAL;      // percentage of tests passed
    }
}
4.4Outline how the submission checks would be implemented so new checks can be added easily.5 marks

An abstract SubmissionCheck holds a next link and a check(script) method. TimeLimitCheck, FormatCheck and PlagiarismCheck each test one thing. The chain is built once (cheap checks first, the expensive plagiarism scan last) and every submission goes to the first check. A failure stops the chain with a reason ("submitted 3 minutes late"); passing all means the script is accepted. A new rule (e.g. WordCountCheck) is one new class added with one link; nothing else changes.

abstract class SubmissionCheck {
  private SubmissionCheck next;
  SubmissionCheck then(SubmissionCheck n) {
    next = n; return n; }
  boolean check(Script s) {
    if (!test(s)) return false;
    return next == null || next.check(s);
  }
  abstract boolean test(Script s);
}
SubmissionCheck c = new TimeLimitCheck();
c.then(new FormatCheck())
 .then(new PlagiarismCheck());
4.5Explain how the proctoring features can be added without changing the existing exam classes.4 marks

Use the Decorator pattern. An ExamSession interface (start(), end()) is implemented by BasicExamSession. An abstract ProctoringDecorator implements ExamSession and holds the session it wraps. WebcamMonitor, ScreenRecorder and AiFlagging each add their own behaviour in start()/end() and then call the wrapped session. A department that wants webcam + AI flagging gets new AiFlagging(new WebcamMonitor(new BasicExamSession())). No exam class changes, and a new feature is one new decorator (Open/Closed).
