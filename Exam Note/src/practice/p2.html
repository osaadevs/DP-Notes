QUESTION 1 · 25 MARKS GoLanka is a ride-hailing app. A trip goes from Requested → Driver assigned → In progress → Completed. A trip can be Cancelled while Requested or Driver assigned, but not once it is in progress. A passenger chooses a vehicle type when booking (Tuk, Car or Van), and each type has its own base fare and capacity.
The final fare is the base fare plus any extras that apply to that trip, in any combination: surge pricing, highway toll, night charge, extra luggage. The company does not want a class for every combination.
Surge multipliers and night rates are changed by the operations team during the day, and every part of the system must use the same current values.
1.1Identify suitable design patterns, with reasons, for: (a) trip stages, (b) creating vehicle types, (c) fare extras, (d) the shared current rates.8 marks
(a) trip stagesStateCancel is allowed only in the first two stages, and "start trip" only after a driver is assigned. Each stage is a class with its own rules and next stage, so there is no if/else on a status field.
(b) vehicle typesFactory MethodVehicleFactory.create(type) returns a Tuk, Car or Van from the passenger's choice; booking code never uses new, and adding "Bike" is one class.
(c) fare extrasDecoratorEach extra wraps the fare and adds its amount, so any combination is built per trip at runtime without 2⁴ = 16 subclasses.
(d) shared ratesSingletonOne FareConfig instance holds the current surge and night rates, so every service reads the same values; an update applies everywhere at once.
1.2Define a Fare interface with getAmount() and getBreakdown(), a BaseFare class, and one extra.6 marks
public interface Fare {
  double getAmount();
  String getBreakdown();
}
public class BaseFare implements Fare {
  private final Vehicle v;
  private final double km;
  public BaseFare(Vehicle v, double km) {
    this.v = v; this.km = km; }
  public double getAmount() {
    return v.getBaseRate() * km; }
  public String getBreakdown() {
    return v.getType() + " " + km + "km"; }
}
public abstract class FareExtra
        implements Fare {
  protected final Fare fare;   // wrapped
  public FareExtra(Fare f) { fare = f; }
}
public class NightCharge extends FareExtra {
  public NightCharge(Fare f) { super(f); }
  public double getAmount() {
    return fare.getAmount() * (1 +
      FareConfig.getInstance().nightRate());
  }
  public String getBreakdown() {
    return fare.getBreakdown()
           + " + night"; }
}
Fare f = new NightCharge(new Toll(
           new BaseFare(car, 12)));

1.4Explain how the shared rates object is created and used safely when many requests arrive at the same time.6 marks

FareConfig is a Singleton: private constructor, a private static volatile instance, and a public static getInstance() using double-checked locking, so two threads arriving at once can't create two objects. The rates themselves are held in thread-safe fields (volatile, or an AtomicReference to an immutable Rates object), so a reader never sees half an update. The operations team updates the rates through update(), which swaps in a new object in one step. Every SurgeCharge and NightCharge decorator reads FareConfig.getInstance() when it calculates, so every fare uses the same current values.

public final class FareConfig {
  private static volatile FareConfig inst;
  private volatile Rates rates =
      Rates.loadFromDb();
  private FareConfig() { }
  public static FareConfig getInstance() {
    if (inst == null) {
      synchronized (FareConfig.class) {
        if (inst == null)
          inst = new FareConfig();
      }
    }
    return inst;
  }
  public double nightRate() {
    return rates.night; }
  public void update(Rates r) {
    rates = r; }     // one atomic swap
}
QUESTION 2 · 25 MARKS A bank is replacing its core online banking system with microservices. Key functional requirements: Customer management (KYC, profiles, login devices) · Accounts (savings, current, fixed deposits, balances) · Transactions (transfers between accounts and to other banks, bill payments) · Loans (applications, approvals, repayment schedules) · Fraud detection (real-time checks on transactions) · Notifications (SMS/email alerts for every transaction).
2.1Draw a diagram to depict the scenario.5 marks
2.2How can the bank implement and manage microservices to achieve scalability, fault isolation and continuous deployment?5 marks
ScalabilityTransactions and Fraud carry the load on salary day and month-end, so they auto-scale independently; Loans stays small. Stateless services on Kubernetes; balance reads cached.
Fault isolationOwn process and database per service. If Notification fails, transfers still work and alerts queue up; if the Loans service fails, payments are unaffected. Circuit breakers, timeouts, bulkheads; a fraud-check timeout falls back to a safe rule (hold large transfers).
Continuous deploymentPipeline per service with automated and security tests, canary releases to a small share of customers, versioned APIs, quick rollback. Changes are audited for regulators.
Manage itAPI gateway, service registry, config server, central logging, metrics and tracing (follow one transfer across services).
2.3Propose a suitable microservices architecture.5 marks

Services, each with its own database: Customer (KYC, devices), Account (balances, account types), Transaction (transfers, bill payments; talks to other banks through a CEFTS/SWIFT adapter), Loan, Fraud (real-time scoring, ML), Notification. Mobile and web banking go through an API gateway with strong authentication. Transaction calls Fraud synchronously (it needs an answer before the money moves) and publishes events to Kafka ("TransferCompleted" → Notification sends an SMS; Account updates statements). Kubernetes, service mesh, registry, config and monitoring, deployed across two data centres.

2.4How would you maintain data consistency, especially for money transfers?5 marks
  • Database per service, so no distributed transactions across services by default.
  • Saga for a transfer: debit the sender → credit the receiver → record the transaction. If the credit fails, a compensating action reverses the debit. An orchestrator in the Transaction service tracks each step.
  • Idempotency keys on every transfer request, so a retried request never debits twice; a transactional outbox for events.
  • Money movements inside one account database use normal ACID transactions; balances are strongly consistent, while alerts and statements are eventually consistent.
  • Daily reconciliation jobs to catch any mismatch.
2.5How would you secure customer data and service-to-service communication?5 marks
  • Customers: OAuth2 / OpenID Connect with multi-factor authentication (OTP), device binding, short-lived JWTs, automatic logout.
  • Data: encryption at rest and in transit, card data to PCI-DSS, keys in a hardware security module or vault, data masking in logs.
  • Service to service: mutual TLS through a service mesh, least privilege per service (Notification can't read balances).
  • Monitoring: rate limits, a WAF, fraud alerts, full audit trail for regulators.
QUESTION 3 · 25 MARKS An insurance company approves claims by amount: an Agent can approve up to Rs. 50,000, a Supervisor up to Rs. 500,000, a Manager up to Rs. 2,000,000, and anything above goes to the Claims Board. New approval levels may be added.
Every claim is processed in the same order: register → assess → approve → pay → notify. Assessment differs for vehicle, health and property claims (a vehicle claim needs a garage estimate; a health claim needs hospital bills checked; a property claim needs a site visit).
Payments are made through the bank's old mainframe system, which only offers TRNPAY(String acctNo, long cents, String refCode). The claims system expects pay(Claim c).
3.1Identify the design patterns, with reasons, for: (a) approval by amount, (b) the processing order, (c) the mainframe payment.6 marks
(a) approval levelsChain of ResponsibilityThe claim is passed up Agent → Supervisor → Manager → Board until a level with a high enough limit approves it; the sender doesn't need to know who approves, and new levels are new handlers.
(b) processing orderTemplate MethodA final process() fixes register → assess → approve → pay → notify; only assess() differs by claim type, so the order is enforced and common steps are written once.
(c) mainframeAdapterMainframePaymentAdapter implements PaymentService.pay(Claim) and converts it into TRNPAY(acct, cents, ref); the mainframe can't be changed.

3.3Write Java showing how a claim of Rs. 750,000 is processed through the approval levels.6 marks
public abstract class Approver {
  protected Approver next;
  private final double limit;
  protected Approver(double limit) {
    this.limit = limit; }
  public Approver setNext(Approver n) {
    next = n; return n; }

  public void approve(Claim c) {
    if (c.getAmount() <= limit) {
      System.out.println(getClass()
        .getSimpleName() + " approved "
        + c.getAmount());
    } else if (next != null) {
      next.approve(c);     // pass it up
    }
  }
}
class Agent extends Approver {
  Agent() { super(50_000); } }
class Supervisor extends Approver {
  Supervisor() { super(500_000); } }
class Manager extends Approver {
  Manager() { super(2_000_000); } }
class ClaimsBoard extends Approver {
  ClaimsBoard() {
    super(Double.MAX_VALUE); } } // fallback

// client
Approver chain = new Agent();
chain.setNext(new Supervisor())
     .setNext(new Manager())
     .setNext(new ClaimsBoard());
chain.approve(new Claim(750_000));
// Agent: no → Supervisor: no
// → "Manager approved 750000.0"
3.4Every approval level must log the claim, record its decision and log the result. How would you enforce this?3 marks

Combine Template Method with the chain: make approve() in Approver final and have it call logReceived() → decide(c) (abstract, written by each level) → logResult(), then pass the claim on if not approved. Levels only write decide(), so none can skip the logging.

3.5Show how the claims system can pay through the mainframe without changing either system.4 marks

Adapter. PaymentService is the target interface the claims system already uses. MainframePaymentAdapter implements it, holds the mainframe client (adaptee), and translates: rupees → cents, claim → account number and reference code, and the mainframe's return code → an exception on failure. The pay() step in the template calls paymentService.pay(c) and never sees the mainframe.

class MainframePaymentAdapter
      implements PaymentService {
  private final Mainframe mf;
  public void pay(Claim c) {
    long cents =
      Math.round(c.getAmount() * 100);
    int rc = mf.TRNPAY(c.getAccountNo(),
                       cents, c.getRef());
    if (rc != 0) throw new
      PaymentException("code " + rc);
  }
}
QUESTION 4 · 25 MARKSFor each case, explain the design pattern you would suggest and why, and give a simple class diagram or code outline.
4.1A hospital system: patient records must only be opened by doctors and nurses assigned to that patient, and every access must be recorded.5 marks

Protection Proxy (structural). PatientRecordProxy implements the same PatientRecord interface as the real record. view() first checks the user's role and whether they are assigned to the patient, writes an audit entry, and only then forwards to the real record; otherwise it refuses. Reasons: sensitive data is never reached directly; the security rule is in one place; the record class stays free of security code.

4.2A reporting module exports the same report as PDF, Excel or CSV, depending on what the user selects; more formats will be added.5 marks

Factory Method (creational). A ReportExporter interface with export(report); PdfExporter, ExcelExporter and CsvExporter implement it. ExporterFactory.create(format) returns the right one from the user's choice. Reasons: the report screen depends only on the interface, creation logic is in one place, and a new format (JSON) is one new class.

class ExporterFactory {
  static ReportExporter create(String f) {
    switch (f) {
      case "PDF":   return new PdfExporter();
      case "EXCEL":
        return new ExcelExporter();
      case "CSV":   return new CsvExporter();
      default: throw new
        IllegalArgumentException(f);
    }
  }
}
4.3A vending machine behaves differently when it is idle, has a coin inserted, is dispensing, or is out of stock.5 marks

State (behavioural). VendingMachine (context) holds a MachineState; IdleState, HasCoinState, DispensingState and OutOfStockState implement insertCoin(), selectItem(), dispense() and refund(). Inserting a coin in Idle moves to HasCoin; in OutOfStock the coin is refunded. Reasons: the same button behaves differently by state, the if/else on a status flag disappears, and each state controls its own transitions. Stateless states can be shared Singletons.

4.4An application sends SMS through an old gateway class with sendText(number, text). A new provider offers dispatch(Message m, int priority). Hundreds of calls to sendText() exist.5 marks

Adapter (structural). Keep SmsGateway with sendText() as the target. NewProviderAdapter implements it, holds the new provider (adaptee), builds a Message from the number and text, and calls dispatch(m, NORMAL). Reasons: the hundreds of existing calls don't change (no risk to tested code), the provider's API isn't ours to change, and switching providers later means one new adapter.

class NewProviderAdapter
      implements SmsGateway {
  private final NewSmsProvider p;
  NewProviderAdapter(NewSmsProvider p) {
    this.p = p; }
  public void sendText(String no,
                       String text) {
    p.dispatch(new Message(no, text), 1);
  }
}
4.5A pizza shop: customers choose a base pizza and add toppings (cheese, chicken, olives, extra sauce) in any combination; the price must be calculated automatically.5 marks

Decorator (structural). Pizza interface with getPrice() and getDescription(); PlainPizza is the base; Cheese, Chicken, Olives and ExtraSauce extend an abstract ToppingDecorator that holds a Pizza. Each topping adds its price and passes the rest of the call on. Reasons: no subclass per combination, toppings are picked at runtime, and new toppings don't change existing classes.

Pizza p = new PlainPizza();     // 1200
p = new Cheese(p);              // +300
p = new Chicken(p);             // +450
p = new Olives(p);              // +150
p.getPrice();                    // 2100

class Cheese extends ToppingDecorator {
  Cheese(Pizza p) { super(p); }
  public double getPrice() {
    return pizza.getPrice() + 300; }
}
