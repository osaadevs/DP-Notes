SOLID principles

Five rules for designing classes that are easy to change. Lecture 12, new this year, so it may appear.
Principles
Overview
PrincipleIn plain wordsAsk yourselfPatterns that follow it
Single ResponsibilityA class should have only one reason to change.Can I describe the class without "and"?Facade (work stays in the subsystems), Decorator (one extra each), State (one class per state), Chain (one check per handler)
Open / ClosedOpen for extension, closed for modification.Can I add behaviour without editing tested code?Decorator, Factory, Template, State, Chain, Adapter, Strategy: all add new classes instead of editing old ones
Liskov SubstitutionA subclass must work anywhere the parent works, without surprises.Can I swap in the child safely?Template subclasses, State classes, Proxy, Decorator: all must be safe substitutes
Interface SegregationDon't force a class to implement methods it doesn't use. Prefer small interfaces.Is any class stuck with empty or throwing methods?Adapter (narrow Target), role interfaces like Workable, Eatable
Dependency InversionHigh-level code should depend on abstractions, not concrete classes.Does business logic new a concrete class?Factory (returns interfaces), Facade / Adapter / Proxy behind interfaces, Dependency Injection (Spring)

S: Single Responsibility

// BAD: Order changes for 4 different reasons
public class Order {
  double calculateTotal() { ... } // rules
  void saveToDatabase() { ... }  // storage
  void printInvoice() { ... }    // display
  void sendEmail() { ... }       // messaging
}
// GOOD: one job each
class Order           // business rules
class OrderRepository // saves to the DB
class InvoicePrinter  // prints invoices
class EmailService    // sends emails
// OrderService (a facade) uses all four

Test: "If the database changes, should Order change?" If yes, responsibilities are mixed. Warning sign: "this class calculates orders and saves them and sends emails".

O: Open / Closed

// BAD: edit this for every new type
double discount(String t, double a) {
  if (t.equals("REGULAR")) return a * 0.05;
  if (t.equals("PREMIUM")) return a * 0.10;
  if (t.equals("VIP"))     return a * 0.20;
  return 0;   // STUDENT? edit again
}
// GOOD: add a class, change nothing
interface DiscountStrategy {
  double calculate(double amt);
}
class VipDiscount
      implements DiscountStrategy {
  public double calculate(double a) {
    return a * 0.20; }
}
// new StudentDiscount = new class only

Same idea for payments: a PaymentMethod interface, and CryptoPayment is added as a new class without touching the PaymentProcessor.

SOLID: L, I, D

And how to use SOLID to strengthen any pattern answer.
Principles
L · I · D

L: Liskov Substitution

// VIOLATION: Square extends Rectangle
Rectangle r = new Square();
r.setWidth(5);
r.setHeight(10);
r.getArea();   // expected 50, got 100

// VIOLATION: Penguin extends Bird
class Penguin extends Bird {
  void fly() {
    throw new UnsupportedOperationException();
  }
}
// FIX: model the right abstraction
interface Shape { double getArea(); }
class Rectangle implements Shape { ... }
class Square    implements Shape { ... }

abstract class Bird { abstract void eat(); }
interface Flyable { void fly(); }
class Sparrow extends Bird
              implements Flyable { ... }
class Penguin extends Bird { ... }

Don't only ask "is it a kind of?" Ask "can the child keep every promise the parent makes?" No stricter inputs, no weaker results, no surprise exceptions.

I: Interface Segregation

// BAD: a fat interface
interface Worker {
  void work(); void eat(); void sleep();
}
// Robot must throw on eat() and sleep()

// GOOD: small role interfaces
interface Workable  { void work(); }
interface Eatable   { void eat(); }
interface Sleepable { void sleep(); }
class Human implements Workable,
    Eatable, Sleepable { ... }
class Robot implements Workable { ... }

Java's own examples: Comparable, Runnable, Iterable, AutoCloseable.

D: Dependency Inversion

// BAD: tied to MySQL, can't mock it
class UserService {
  private MySQLDatabase db =
      new MySQLDatabase();
}

// GOOD: depend on an interface,
// inject it through the constructor
class UserService {
  private final UserRepository repo;
  UserService(UserRepository r) {
    repo = r; }
}
new UserService(new PostgresUserRepo());

Dependency Inversion is the principle. Dependency Injection is the technique (pass dependencies in from outside; Spring does it for you).

Add one SOLID line to any pattern answer cheap extra marks

Decorator, Factory, Strategy, State, Chain"…which follows the Open/Closed principle: new types are new classes, existing code is not modified."
Facade, Chain handlers, Decorator"…each class has a single responsibility."
Template subclasses, State, Proxy"…any subclass can replace the parent (Liskov)."
Adapter Target, role interfaces"…clients only see the small interface they need (Interface Segregation)."
Factory, any interface-based design"…the client depends on an abstraction, not a concrete class (Dependency Inversion)."
SOLID vs patterns vs frameworks: SOLID are principles ("how should I design classes?"), patterns are proven solutions to recurring problems, frameworks are reusable infrastructure (Spring applies Dependency Inversion through injection). Using a pattern doesn't guarantee SOLID; it depends on how you apply it. And SOLID isn't "more interfaces everywhere": adding abstraction to a 2-line calculator is over-engineering (YAGNI).
