An object behaves differently depending on which state it is in. Each state gets its own class.

The idea

Press "mute" on a TV remote. If the TV is on, it mutes. If it's off, nothing happens. Same button, different result, because of the state.

Without the pattern, every method is a big if (state == ON) … else if (state == OFF) …, and it grows with every new state. With State, each state is a class that knows what to do for each action and which state comes next. The main object (the context) just says "current state, you handle this".

The parts

PartJobDocument workflow (2024 Q3)
ContextHolds the current state, passes every request to it, has setState()Document
State «interface»One method per event; every state must have them allDocumentState
Concrete statesThe behaviour for that state; they call context.setState(next) to move onDraftState, ModerationState, PublishedState, ArchivedState

Designing it in 5 steps

  1. Draw the state diagram (states and events).
  2. Make the state table: state + event → what happens + next state.
  3. State interface = one method per event.
  4. One class per state implementing it.
  5. The context delegates: state.submit(this).

Don't mix it up

  • vs Chain: State asks "how should I behave now?" and the object delegates to its current state. Chain asks "who handles this?" and the request moves along handlers.
  • vs Strategy: same structure, but the client picks a strategy and it doesn't change itself. States switch themselves.

W1 Name it and say why 2–5 marks

I would use the State pattern, which is a behavioural pattern. It allows an object to change its behaviour when its internal state changes; the object appears to change its class.

Reasons: (1) the document has a fixed set of states and the same action behaves differently in each (edit works in Draft but is refused in Published); (2) it removes the if/else on a status field from every method; (3) each state's rules and transitions live in one class, and a new state is just a new class (Open/Closed).

Mapping: context = Document · state interface = DocumentState · concrete states = Draft, Moderation, Published, Archived.

W3 · Java
public interface DocumentState {
  void edit(Document d, String text);
  void submit(Document d);
  void approve(Document d);
  void reject(Document d);
  void archive(Document d);
}
public class Document {          // CONTEXT
  private DocumentState state =
      new DraftState();
  private String content = "";
  void setState(DocumentState s) { state = s; }
  public void edit(String t) {
    state.edit(this, t); }
  public void submit()  { state.submit(this); }
  public void approve() { state.approve(this); }
  public void reject()  { state.reject(this); }
  public void archive() { state.archive(this); }
}
public class ModerationState
        implements DocumentState {
  public void approve(Document d) {
    d.setState(new PublishedState()); }
  public void reject(Document d) {
    d.setState(new DraftState()); }
  public void edit(Document d, String t) {
    System.out.println("Under review"); }
  public void submit(Document d) {
    System.out.println("Already submitted"); }
  public void archive(Document d) {
    System.out.println("Publish first"); }
}
// Draft: edit ok, submit → Moderation
// Published: archive → Archived only
// Archived: everything refused

State: smart parking

Quiz 1, the lecturer's own State question: why, state diagram, UML, context code, then an Adapter twist.

Answers

Q1 Why State is appropriate 4m

A parking session has a fixed set of well-defined states (Available, Reserved, Occupied, Payment Due, Closed), and the same action behaves differently in each: enter() is allowed when Reserved but refused when Closed, and pay() only works in Payment Due. Without the pattern every method needs a growing if/switch on the status. With State, each state's rules live in one class, transitions are explicit, invalid actions are refused cleanly, and a new state (e.g. Overstay) is just a new class.

public class ParkingSession {
  private ParkingState state =
      new AvailableState();
  private String vehicleNo;
  private double fee;

  public void setState(ParkingState s) {
    state = s; }
  public void reserve() { state.reserve(this); }
  public void enter()   { state.enter(this); }
  public void exit()    { state.exit(this); }
  public void pay(double amt) {
    state.pay(this, amt); }
}

Q5 Legacy payment machine

The vendor's machine can't be modified, so use an Adapter. LegacyPaymentAdapter implements the PaymentProcessor interface the system expects and calls the vendor's method inside. PaymentDueState.pay() calls processor.pay(amount); if it succeeds it moves the session to Closed. Code: tab 04, W4.

Self-checkout kiosk states · 2025 Q1.1(a), 1.4, 5m

How to incorporate the states, with an example transition

State pattern. Kiosk is the context and holds a KioskState. IdleState, ScanningState, PaymentState and CompletedState implement scanItem(), checkout(), pay() and cancel().

Example: in ScanningState, pressing Checkout adds up the decorated items' getCost(), adds tax with TaxCalculator.getInstance() (Singleton) and moves to PaymentState. In IdleState, pay() is refused: "scan items first".

public class ScanningState
        implements KioskState {
  public void scanItem(Kiosk k,
                       CheckoutItem i) {
    k.addItem(i); }        // stay here
  public void checkout(Kiosk k) {
    double total = TaxCalculator
        .getInstance()
        .applyTax(k.subtotal());
    k.setTotal(total);
    k.setState(new PaymentState());
  }
  public void pay(Kiosk k, double a) {
    System.out.println("Checkout first"); }
}

Use of interfaces in this design 2024 Q3.4, 5m

  • DocumentState is a contract: every state must implement every event, so nothing is forgotten.
  • The context calls state.submit(this) without knowing which state it has: polymorphism, programming to an interface.
  • New states plug in without changing Document (Open/Closed, Dependency Inversion).
  • States are interchangeable at runtime and easy to mock in tests.

W5 Challenges → fix

  • Many classes (one per state) → only use it when states are finite and behaviour really differs.
  • Transitions spread across classes → keep the state diagram and table as documentation; validate in setState().
  • A new event changes every state → abstract base state with default "invalid action" methods.
  • Many state objects → share stateless states as Singletons.
Mistakes that lose marks: the context still has if (state == …) · state diagram without a start dot or event labels · no setState() in the context · association instead of realisation from the states to the interface · transitions to states that aren't in the scenario.
