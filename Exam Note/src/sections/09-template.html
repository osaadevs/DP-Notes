Template Method

The parent class fixes the steps and their order. Each subclass fills in only the steps that are different for it.
Behavioural
Understand

Spot it: the question says…

all types follow the same overall processhowever, step 2 is different for each type standardise the common workflow while allowing custom behaviourevery level must follow the same procedure enforce the proceduresalary components with a few deviationscopy-pasted algorithm with small differences

The idea

Card, PayPal and cash-on-delivery payments all do the same three things in the same order: validate, process, send a receipt. Only "process" really differs.

So you write the order once, in a final method in an abstract parent class. The common steps are written there too. The step that differs is left abstract, and each subclass writes only that step. Like a recipe card: same steps for every cake, only the filling changes.

This is the Hollywood principle: "don't call us, we'll call you". The parent calls the child's steps.

The four kinds of method know these

KindModifierJob
Template methodpublic finalCalls the steps in a fixed order. Final, so no subclass can change the order.
Common stepprivate or concreteWritten once, shared by all.
Primitive stepprotected abstractEach subclass must write it.
Hookprotected with a defaultSubclass may override it if it wants (e.g. wantsEmail() returns true).

OOP ideas used "explain how abstract classes are used"

Inheritance (subclasses extend the parent) · abstract class and abstract methods (the parent can't be created on its own and forces subclasses to write the varying steps) · method overriding · final (locks the order) · access modifiers (protected steps, private common steps) · polymorphism (the parent calls whichever subclass version exists).

Why an abstract class and not an interface? Java interfaces can hold code (default and static methods), so "interfaces have no implementation" is not the reason. The reasons: a default method can't be final, so any class could override the template and change the order; an interface can't have protected steps or instance fields (the order, the amount); an abstract class has all three. Details: "Template Method: salary code, interfaces vs abstract classes".

Don't mix it up

  • vs Strategy: Template varies some steps using inheritance, fixed at compile time. Strategy swaps the whole algorithm as an object at runtime.
  • vs Factory Method: a factory method is often just one step inside a template method.
  • vs Chain: Template is one object running fixed steps. Chain passes a request between objects.

Mistakes that lose marks

  • Template method not marked final.
  • Making every step abstract (then nothing is shared).
  • Using an interface for the base class (its default template method can't be final).
  • The client calling the steps one by one.
  • Drawing dashed (implements) arrows. Subclasses extend, so solid lines.

Template Method: write

The payment workflow from 2025 Q4. Swap the steps for the ones in your question.
Behavioural
Write

W1 Name it and say why 2–5 marks

I would use the Template Method pattern, which is a behavioural pattern. It defines the skeleton of an algorithm in a superclass and lets subclasses redefine certain steps without changing the algorithm's structure.

Reasons: (1) every payment type follows the same order (validate → process → receipt) and the final template method enforces it; (2) the common steps are written once, so there is no duplicated code; (3) a new payment type only writes processPayment(), so it is easy to extend (Open/Closed) and behaviour is consistent across types.

Mapping: abstract class = PaymentProcessor · template method = handlePayment() (final) · common steps = validate(), sendReceipt() · varying step = processPayment() · concrete classes = CreditCard, PayPal, CashOnDelivery processors.

W3 · Java (2025 Q4.2: abstract PaymentProcessor · Q3.3: CreditCardPaymentProcessor)
public abstract class PaymentProcessor {

  // TEMPLATE METHOD: fixed order, final
  public final void handlePayment(Order o) {
    if (!validate(o)) {
      System.out.println("Invalid details");
      return;
    }
    processPayment(o);
    sendReceipt(o);
  }

  // common step (subclass may extend it)
  protected boolean validate(Order o) {
    return o.getAmount() > 0
        && o.getCustomer() != null;
  }
  // the step that differs
  protected abstract void
      processPayment(Order o);

  // common step
  protected void sendReceipt(Order o) {
    System.out.println("Receipt sent");
  }
}
public class CreditCardPaymentProcessor
        extends PaymentProcessor {

  // adds a card check to the common one
  protected boolean validate(Order o) {
    return super.validate(o)
        && CardValidator.isValid(o.getCardNo());
  }

  // only the varying step is written here
  protected void processPayment(Order o) {
    System.out.println("Charging card for "
        + o.getAmount());
    BankGateway.charge(o.getCardNo(),
                       o.getAmount());
  }
}

// CLIENT
PaymentProcessor p =
    new CreditCardPaymentProcessor();
p.handlePayment(order);
// validate → process → receipt

Template Method: salary questions

2022 Q2 and 2023 Q1 were both 25-mark payroll questions. One design answers both.
Behavioural
Answers

Which pattern, and why 2022 Q2.2 6m · 2023 Q1.2 5m

Template Method. Every employee's salary is worked out in the same order: gross → EPF → deductions → net. The EPF, tax and net formulas are the same for everyone. Only some components differ (overtime, allowances, no-pay). So calculateNetSalary() is a final template method in an abstract SalaryCalculator, the common formulas are written there once, and each employee type overrides only its own components. 2023's deviation is easy: ExecutiveSalary overrides overtime() and noPay() to return 0. The 2023 formulas map straight onto the hooks: overtime() = basic × OT hours / (30 × 8), noPay() = basic × days / 30, attendance allowance in allowances(): the paper gives absent 0 → 75%, more than 1 and less than 3 → 50%, more than 3 → none, which leaves exactly 1 and exactly 3 days unspecified. Assumption (state it in the answer): 1 to 3 absent days → 50%.

Class diagram · 2022 Q2.3 5m

hooks return 0 by default; subclasses override only what differs
public abstract class SalaryCalculator {
  protected double basic;
  protected int otHours, absentDays, noPayDays;

  public final double calculateNetSalary() {
    double gross = basic + allowances()
                 + overtime();
    double epf = gross * Config.get("epf");
    // assumed: no tax at or below 100,000
    double tax = Math.max(0,
                 (gross - 100000) * 0.06);
    return gross - (epf + noPay() + tax);
  }
  // hooks: default 0, override if needed
  protected double allowances() { return 0; }
  protected double overtime()   { return 0; }
  protected double noPay()      { return 0; }
}

Challenges → mechanism Q2.4–2.5 / Q1.3–1.4

Rigid order: one type needs a different sequenceHooks for optional steps; if the order truly differs, use Strategy.
Many subclasses as types growShared middle classes (e.g. HourlyPaid); keep steps small.
Rates change (EPF, tax)Read them from a Singleton config (tab 01 answers).
A subclass overrides a common stepMake the template final and common steps private/final.

"Code duplication can be achieved from this pattern." Agree? 2022 Q2.6, 4m

No, as worded. Template Method avoids duplication: the common formulas (EPF 8%, tax, net) exist once in the superclass, and subclasses contain only their differences. A little duplication can remain if two subclasses override a step the same way; the fix is to move that code up into the parent or into a shared middle class.

Online course completion Quiz 6, 2 + 8 + 3 + 4m

Why Template Method: every course follows the same completion order, and it must be enforced, but two steps differ per course (programming: coding challenge marked by automated tests; design: portfolio marked by an instructor with a rubric). The abstract class fixes the order in a final completeCourse(), writes the common steps once, and leaves the two varying steps abstract.

public abstract class OnlineCourse {
  protected final String studentId;
  protected OnlineCourse(String studentId) {
    this.studentId = studentId; }
  public final void completeCourse() {
    if (!validateRegistration()) return;
    deliverFinalAssessment();
    double score = evaluatePerformance();
    generateCertificate(score);
  }
  private boolean validateRegistration() {
    return Registry.isEnrolled(studentId); }
  protected abstract void
      deliverFinalAssessment();
  protected abstract double
      evaluatePerformance();
  private void generateCertificate(double s) {
    if (s >= 50) System.out.println(
        "Certificate " + studentId); }
}
public class ProgrammingCourse
        extends OnlineCourse {
  public ProgrammingCourse(String id) {
    super(id); }
  protected void deliverFinalAssessment() {
    System.out.println("Coding test"); }
  protected double evaluatePerformance() {
    return AutoTests.run(studentId); }
}
public class DesignCourse
        extends OnlineCourse {
  public DesignCourse(String id) {
    super(id); }
  protected void deliverFinalAssessment() {
    System.out.println("Submit portfolio"); }
  protected double evaluatePerformance() {
    return Instructor.rubric(studentId); }
}

E-commerce checkout 2024 Q4.2, 4.4, 10m

Template Method. CheckoutProcess has a final checkout(): validate cart → process payment → arrange delivery → send confirmation. Validate cart and send confirmation are common; payment and delivery (domestic / international) vary.

Use of abstract classes: CheckoutProcess is abstract because it holds real code (common steps and the fixed order) plus abstract steps. It can't be instantiated; subclasses supply the varying parts.

Support procedure Quiz 7 Q4, 4m

Every support level must log the request → attempt to solve → log the resolution. Put a final handle() in the abstract SupportHandler that does exactly that and calls an abstract attemptToSolve(). L1, L2, L3 and Specialist only write attemptToSolve(), so no level can skip the logging. This is Template Method inside a Chain of Responsibility (code in tab 08).

2023 Q1 salary subclasses base class: "Template Method: salary questions"

public class PermanentSalary
    extends SalaryCalculator {
  public PermanentSalary(double basic,
      int otHours, int absentDays,
      int noPayDays) {
    this.basic = basic;
    this.otHours = otHours;
    this.absentDays = absentDays;
    this.noPayDays = noPayDays; }
  protected double overtime() {
    return basic * otHours / (30 * 8); }
  protected double noPay() {
    return basic * noPayDays / 30; }
  // ASSUMPTION: 1 and 3 absent days -> 50%
  protected double allowances() {
    if (absentDays == 0) return basic * 0.75;
    if (absentDays <= 3) return basic * 0.50;
    return 0; }
}
// executives: no overtime, no no-pay
public class ExecutiveSalary
    extends PermanentSalary {
  public ExecutiveSalary(double basic,
                         int absentDays) {
    super(basic, 0, absentDays, 0); }
  protected double overtime() { return 0; }
  protected double noPay()    { return 0; }
}
// STUB: rates from configuration
final class Config {
  static double get(String key) {
    return key.equals("epf") ? 0.08 : 0; }
}
double net = new PermanentSalary(
    80000, 10, 0, 0).calculateNetSalary();

For 2023, ExecutiveSalary extends PermanentSalary so it keeps the attendance allowance and only drops overtime and no-pay (the 2022 executive in the class diagram adds a bonus in allowances() instead). Employer EPF (12%) and ETF (3%) are employer costs; they go into "Total EPF" and payroll reports, not into the employee's deductions.

Interface or abstract class for the template?

interface Course {
  default void completeCourse() { // code is
    deliverFinalAssessment();      // allowed
    evaluatePerformance();
  }
  // "final default" won't compile
  void deliverFinalAssessment();
  double evaluatePerformance();
}
class BadCourse implements Course {
  // legal: skips the order completely
  public void completeCourse() { }
  public void deliverFinalAssessment() { }
  public double evaluatePerformance() {
    return 100; }
}

Since Java 8 an interface can contain code: default methods (overridable bodies) and static methods; since Java 9, private helper methods too. So an interface could hold a default completeCourse(). It is still the wrong choice for Template Method because:

  • a default method can't be final, so an implementing class can override it and change or skip steps;
  • interface methods are public or private, never protected, so the steps would be callable by any client;
  • an interface has no instance fields (only constants), so it can't hold studentId or basic.

An abstract class has a final template, protected steps and fields. Use an interface for a can-do contract shared by unrelated classes; an abstract class for an is-a family with shared code.
