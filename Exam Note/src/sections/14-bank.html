"How can you extend this design to achieve High Availability and Disaster Recovery?" 2022 Q3.5 · 2023 Q3.5, 5m

High Availability = the system keeps running when a part fails (little or no downtime).

  • Run each component as several stateless copies behind a load balancer, with health checks and automatic restart (e.g. by an orchestrator such as Kubernetes).
  • No single point of failure: a Singleton or Facade on one server becomes replicas.
  • Database replication / clusters with automatic failover.
  • Timeouts, retries and circuit breakers; a fallback handler at the end of a Chain.

Disaster Recovery = getting back after a big failure (data centre lost).

  • Regular backups, and the database replicated to a second region.
  • Agreed RPO (how much data we can lose) and RTO (how fast we must be back).
  • Automated failover to the DR site; infrastructure-as-code to rebuild quickly.
  • DR drills to test it regularly.

Tie it to the pattern: "Because each filter / handler / service is stateless, extra copies can run on several servers…" makes the answer fit the question.

"Many parameters change over time. Improve configurability." 2023 Q1.5, 4m

Move every rate, limit and threshold out of the code into external configuration (a database table or a properties / YAML file). A Singleton ConfigManager loads it and every class reads from there. An admin screen changes values; changes are versioned and audited with an "effective from" date; no recompiling or redeploying. Example settings: epf.employee=0.08, tax.threshold=100000. Interface or abstract class? "explain the use of interfaces / abstract classes"

InterfaceAbstract class
MeaningA contract: what a class can doA partial parent: what a class is
ContainsMethod signatures (plus default methods)Fields, finished methods and abstract methods
Keywordimplements, a class can have manyextends, only one parent
Used inDecorator Component, Adapter Target, Proxy Subject, State, Factory ProductTemplate Method base, Decorator base, Chain handler

Why they help (write this): the client depends on the abstraction, not the concrete class, so different implementations can be swapped through polymorphism. New classes plug in without changing the client (Open/Closed, Dependency Inversion), and tests can use mocks. An abstract class is chosen when shared code or a fixed order must live in the parent.

Pros and cons of using design patterns in general

  • + Proven solutions, so fewer design mistakes
  • + Shared vocabulary for the team
  • + Loose coupling, reuse, flexibility
  • + Easier to maintain and extend
  • − More classes and more abstraction
  • − Learning curve for new developers
  • − Overuse is over-engineering
  • − Ask: "is it worth the extra abstraction?"

"Why not just use inheritance for everything?"

Inheritance fixes behaviour at compile time. Every combination needs its own subclass (class explosion), the hierarchy becomes rigid, and a change in the parent ripples into every child. So prefer composition: Decorator, State, Strategy and Adapter all hold another object instead of inheriting from it, and can change at runtime.

Challenges that fit almost any pattern design use when the pattern's own W5 isn't enough

ChallengeMechanism to overcome it
More classes, more complex to understandClear naming, a class diagram in the documentation, only use the pattern where change is likely.
Harder to debug (calls pass through layers)Logging at each layer, unit tests for each class.
Performance overheadUsually negligible; cache results; keep chains and wrappers short.
Single point of failure (Singleton, Facade, Proxy)Stateless replicas behind a load balancer; standby copy.
Third-party parts changeKeep them behind an interface or Adapter so only one class changes.
Values change oftenExternal configuration read by a Singleton ConfigManager.
