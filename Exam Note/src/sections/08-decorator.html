Decorator

Add optional extras to an object by wrapping it, layer by layer, instead of making a subclass for every combination.
Structural
Understand

Spot it: the question says…

optional add-ons / extras / toppings / ingredientswithout creating subclasses for every combination price depends on the base type and the selected additionsinstead of modifying the class directly students may optionally addcalculate the price dynamically

The idea

A coffee can have milk, sugar and chocolate in any mix. With subclasses you'd need CoffeeWithMilkAndSugar and so on: 2ⁿ classes (3 extras → 8, 10 → 1,024). That's class explosion.

Instead, each extra is a small wrapper. It looks like a Coffee, holds the coffee inside, adds its own price and text, and passes the call inwards. Stack wrappers at runtime to get any combination.

How a call runs

getCost() on Sugar asks Milk, which asks BasicCoffee. The answer comes back out: 200 → 280 → 300.

The fourth part, the abstract Decorator, is always <Component>Decorator (CoffeeDecorator, AddOnDecorator). It is a Component (implements it) and has a Component (a field holding the wrapped object).

Don't mix it up

  • vs Proxy: same interface, but Proxy controls access (one layer). Decorator adds features (many layers).
  • vs Adapter: Adapter changes the interface. Decorator keeps it.
  • vs inheritance: inheritance fixes combinations at compile time. Decorator builds them at runtime.

Mistakes that lose marks

  • Decorator doesn't implement the Component.
  • Decorator makes its own base instead of taking it in the constructor.
  • Not calling the wrapped object, so earlier extras are lost.
  • Inheritance drawn instead of the has-a diamond.

W1 Name it and say why 2–6 marks

I would use the Decorator pattern, which is a structural pattern. It attaches additional responsibilities to an object dynamically by wrapping it, which is a flexible alternative to subclassing.

Reasons: (1) no class explosion: n add-ons would need 2ⁿ subclasses, here it's one class per add-on; (2) runtime flexibility: the customer picks any mix of add-ons while ordering; (3) Open/Closed: a new add-on is a new class, and the base coffee and existing add-ons don't change; (4) each decorator has one responsibility.

Mapping: Component = Coffee «interface» · concrete component = BasicCoffee · decorator = CoffeeDecorator «abstract» · concrete decorators = Milk, Sugar, Chocolate.

the diamond sits on the decorator: it has a Coffee inside
W3 · Java (this is what 2024 Q1.2–1.3 and 2025 Q1.2–1.3 asked for)
// 1. COMPONENT: "define a Coffee interface"
public interface Coffee {
    double getCost();
    String getDescription();
}

// 2. CONCRETE COMPONENT: "create BasicCoffee"
public class BasicCoffee implements Coffee {
    public double getCost() { return 200.0; }
    public String getDescription() {
        return "Basic coffee"; }
}

// 5. CLIENT: wrap at runtime
Coffee c = new BasicCoffee();
c = new Milk(c);
c = new Sugar(c);
c.getDescription(); // Basic coffee, Milk, Sugar
c.getCost();        // 200 + 80 + 20 = 300.0
// 3. ABSTRACT DECORATOR: is-a + has-a
public abstract class CoffeeDecorator
        implements Coffee {
    protected Coffee coffee;      // wrapped
    public CoffeeDecorator(Coffee c) {
        this.coffee = c; }
    public double getCost() {
        return coffee.getCost(); }
    public String getDescription() {
        return coffee.getDescription(); }
}

// 4. CONCRETE DECORATOR: add, then pass on
public class Milk extends CoffeeDecorator {
    public Milk(Coffee c) { super(c); }
    public double getCost() {
        return coffee.getCost() + 80; }
    public String getDescription() {
        return coffee.getDescription()
               + ", Milk"; }
}
// Sugar (+20), Chocolate (+120): same shape

W4 "If there are different profits for each coffee, how would you extend the design?" 2024 Q1.4, 5m

Option A: add getProfit() to the Coffee interface. Each base coffee returns its own margin, and each decorator returns coffee.getProfit() + addOnProfit. Selling price = getCost() + getProfit().

Option B (better, keeps Open/Closed): a new ProfitMargin decorator wraps the finished drink and adds a percentage. No existing class changes. Different coffees get different rates: new ProfitMargin(irish, 0.30).

public class ProfitMargin
        extends CoffeeDecorator {
    private double rate;
    public ProfitMargin(Coffee c, double r) {
        super(c);
        rate = r;
    }
    public double getCost() {
        return coffee.getCost() * (1 + rate);
    }
}

Self-checkout kiosk: CheckoutItem and GroceryItem 2025 Q1.2–1.3, 10m

public interface CheckoutItem {
    double getCost();
    String getDescription();
}
public class GroceryItem
        implements CheckoutItem {
    private String name;
    private double price;
    public GroceryItem(String n, double p) {
        name = n; price = p;
    }
    public double getCost() { return price; }
    public String getDescription() {
        return name; }
}
public class GiftWrap
        extends AddOnDecorator {
    public GiftWrap(CheckoutItem i) {
        super(i); }
    public double getCost() {
        return item.getCost() + 150; }
    public String getDescription() {
        return item.getDescription()
               + " + gift wrap"; }
}
// usage
CheckoutItem it = new GroceryItem(
        "Rice 5kg", 1200);
it = new EcoBag(it);
it = new GiftWrap(it);

Code complexityMany small classes; hard to see one object's full feature set.
DebuggingA call passes through many wrappers; the bug can be in any layer.
PerformanceAn extra object and call per layer; small, but it grows.
Readabilitynew A(new B(new C(x))) is hard to read, and order changes the result.

W5 Challenges → fix

  • Many small classes → one job per decorator; a builder assembles common combinations.
  • Debugging → log in each decorator; test each one on its own.
  • Order matters (discount then tax ≠ tax then discount) → fix the wrapping order in the builder.
  • Performance → negligible for short chains; cache the total.
