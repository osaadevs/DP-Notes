Facade

One simple front door to a group of complicated classes. The client talks to the front door only.
Structural
Understand

Spot it: the question says…

one simple interface for borrowing books by internally calling inventory, payment, notification and login combine air tickets, hotels and taxissingle entry point hide the complexity of the subsystemscomplex subsystem calls scattered everywhere

The idea

Some jobs need many classes called in the right order: log in, check stock, charge a fee, send a message. If every client does that itself, each one depends on all those classes, and any change breaks them all.

A facade puts one method in front, like borrowBook(), which makes the calls in the right order. Like a waiter: you order from them and never deal with the chef, the cashier and the kitchen staff yourself.

Without vs with

Without facadeWith facade
Client talks toLogin, Inventory, Payment, Notification…one class
Couplinghigh, many dependencieslow
A service changesevery client breaksonly the facade changes
Call orderrepeated in each clientwritten once

The parts

PartJobLibrary example
FacadeKnows which subsystem does what, calls them in order. Only delegates.LibraryFacade.borrowBook()
Subsystem classesDo the real work. They don't know the facade exists.LoginService, InventoryService, PaymentService, NotificationService
ClientCalls only the facade.librarian screen / mobile app

Rules from the slides

  • A facade doesn't add new functionality. It only gives a simpler way in.
  • Clients can still use the subsystems directly if they need something advanced.
  • A big system can have more than one facade, one per area (BookingFacade, PaymentFacade).

Don't mix it up

  • vs Adapter: Adapter converts one interface into another so the client can use it. Facade makes a new, simpler interface over many classes. Adapter = translator, Facade = simplifier.
  • vs Factory: Factory creates objects. Facade coordinates objects that already exist.

W1 Name it and say why 2–5 marks

I would use the Facade pattern, which is a structural pattern. It provides one unified, simpler interface to a set of interfaces in a subsystem, so the subsystem is easier to use.

Reasons: (1) the client depends on one class instead of four services, so coupling is low; (2) the call order is written once inside the facade instead of being repeated in every screen; (3) if a service changes, only the facade changes and the clients don't; (4) it is easier to use and test, because you can mock the facade.

Mapping: Facade = LibraryFacade with borrowBook() · subsystems = LoginService, InventoryService, PaymentService, NotificationService · client = LibraryApp.

class LoginService {
  boolean verify(String user) { ... }
}
class InventoryService {
  boolean isAvailable(String book) { ... }
  void reserve(String book) { ... }
}
class PaymentService {
  void chargeFee(String user) { ... }
}
class NotificationService {
  void send(String user, String msg) { ... }
}

// CLIENT: one call
LibraryFacade library = new LibraryFacade();
library.borrowBook("U001", "B123");
// FACADE: one simple method, calls in order
public class LibraryFacade {
  private LoginService login =
      new LoginService();
  private InventoryService inventory =
      new InventoryService();
  private PaymentService payment =
      new PaymentService();
  private NotificationService notifier =
      new NotificationService();

  public boolean borrowBook(String user,
                            String book) {
    if (!login.verify(user)) return false;
    if (!inventory.isAvailable(book))
        return false;
    inventory.reserve(book);
    payment.chargeFee(user);
    notifier.send(user, "Borrowed " + book);
    return true;
  }
}

Answers

Travel booking: air ticket, hotel and taxi 2022 Q1.1–1.2, 15m

1.1 Diagram: draw the scenario diagram from tab 00 (traveller → website → TravelBookingFacade → air / hotel / taxi services → third-party APIs through adapters).

1.2 Pattern for the sub-system that combines them: Facade. TravelBookingFacade.bookTrip(request) calls the AirTicketService, HotelService and TaxiService and returns one itinerary. The traveller does one action, the complexity of three services is hidden, and the website depends on one class only.

1.2.1 Challenge1.2.2 Mechanism to overcome it
The facade grows into a God class as more services are added.Split it into smaller facades per area (FlightFacade, StayFacade). Keep it delegating only, no business logic (SRP).
One service fails (taxi API down) and the whole booking fails. The facade is a single point of failure.Timeouts, retries and a fallback provider for each service. Run the facade as several stateless copies behind a load balancer (HA).
Partial booking: the flight is booked but the hotel fails.Compensating actions: cancel the flight if the hotel fails (the saga idea), or reserve everything first and confirm all at the end.

1.3 (connecting to the different third-party web services) is Adapter: see tab 04, answers.

One interface for borrowing Quiz 3 Q5

Use a Facade. LibraryFacade.borrowBook(userId, bookId) calls, in order: LoginService.verify() → InventoryService.isAvailable() and reserve() → PaymentService.chargeFee() → NotificationService.send(). The librarian screen calls only the facade, so it doesn't depend on four services, and a change in any service is handled inside the facade. (Code: W3.)

Slide questions

Can you still access the subsystems directly? Yes. The facade is a convenience, not a lock.

Must there be only one facade? No. A large system can have several, one per area, which also avoids a God class.

Does the facade add functionality? No. It only wraps existing features behind a simpler entry point.

W5 Challenges → fix use for any "challenges" part

ChallengeHow to handle it
Becomes a God class (too big)Several smaller facades; the facade only delegates.
Single point of failure / bottleneckKeep it stateless and run several copies behind a load balancer. If one is enough, make it a Singleton.
Can hide useful features of the subsystemsStill allow direct access for advanced clients.
Subsystems have incompatible interfaces (third-party)Put Adapters under the facade (tab 04).
Extra layer, not worth it for tiny systemsOnly use it when several clients repeat the same call sequence.
Mistakes that lose marks: putting business logic in the facade (it only delegates) · drawing arrows from the subsystems back to the facade (they don't know it) · calling it creational · confusing it with Adapter (converts an interface) or Proxy (same interface, controls access).

Facade: banking example

The lecture's main example: a customer uses one BankService instead of three account subsystems.
Structural
Example

Class diagram

before: Customer → every account · after: Customer → BankService only
// SUBSYSTEM: common account interface
public interface IAccount {
  void deposit(double amount);
  void withdraw(double amount);
  double getBalance();
}
public abstract class AbstractAccount
    implements IAccount {
  protected double balance;
  public void deposit(double a) {
    balance += a; }
  public void withdraw(double a) {
    if (a > balance) throw new
        IllegalStateException("Funds");
    balance -= a; }
  public double getBalance() {
    return balance; }
}
public class SavingAccount
    extends AbstractAccount { }
public class CheckingAccount
    extends AbstractAccount { }
public class InvestmentAccount
    extends AbstractAccount { }
// (each can override withdraw() with
//  its own rules; kept simple here)

// CLIENT: knows only the facade
BankService bank = new BankService();
bank.openAccount("SAVING", "John");
bank.openAccount("CHECKING", "Alice");
bank.deposit("John", 5000);
bank.transferMoney("John", "Alice", 1000);
System.out.println(
    bank.getBalance("John"));   // 4000.0
// FACADE: one entry point, only delegates
public class BankService {
  private final Map
      accounts = new HashMap<>();

  public void openAccount(String type,
                          String accNo) {
    IAccount a;
    switch (type) {
      case "SAVING":
        a = new SavingAccount(); break;
      case "CHECKING":
        a = new CheckingAccount(); break;
      default:
        a = new InvestmentAccount();
    }
    accounts.put(accNo, a);
  }
  public void deposit(String no, double amt) {
    find(no).deposit(amt); }
  public void withdraw(String no, double amt) {
    find(no).withdraw(amt); }
  public void transferMoney(String from,
      String to, double amt) {
    find(from).withdraw(amt);   // fails first
    find(to).deposit(amt);      // if no funds
  }
  public double getBalance(String accNo) {
    return find(accNo).getBalance(); }
  private IAccount find(String accNo) {
    IAccount a = accounts.get(accNo);
    if (a == null) throw new
        IllegalArgumentException(accNo);
    return a;
  }
}

Why this is a Facade

Facade = BankService. Subsystem = IAccount and the three account classes. Client = the customer's app. transferMoney() coordinates two accounts in the right order (withdraw, then deposit), so the client never has to. The facade adds no new banking rule; the rules stay in the accounts.

The library subsystems written out, Facade vs Factory Method, and the OOP terms.

Complete code · theory
// Library subsystems for the W3 LibraryFacade.
// STUB data: in-memory sets stand in for the
// real user database, catalogue, payment
// gateway and SMS/email service.
class LoginService {
  private final Set users =
      Set.of("U001", "U002");
  boolean verify(String user) {
    return users.contains(user); }
}
class InventoryService {
  private final Set onShelf =
      new HashSet<>(Set.of("B123", "B456"));
  boolean isAvailable(String book) {
    return onShelf.contains(book); }
  void reserve(String book) {
    onShelf.remove(book); }
}
class PaymentService {
  void chargeFee(String user) {
    System.out.println("Fee charged: " + user); }
}
class NotificationService {
  void send(String user, String msg) {
    System.out.println(user + ": " + msg); }
}

Facade vs Factory Method lecture table

PurposeFactory: creates objects. Facade: coordinates existing objects behind a simple interface.
GroupFactory: creational. Facade: structural.
ReturnsFactory: an object. Facade: the result of a workflow.
ExamplecreateCreditCardPayment() vs transferMoney().

"Factory decides which object to create. Facade decides what to do with several objects."

OOP and SOLID in the Facade code name the concept → class/member → effect

ConceptWhereEffect
Encapsulationprivate service fields in LibraryFacade; private Map accounts and find() in BankServiceThe subsystems and their call order are hidden; the client sees only the public methods.
AbstractionborrowBook(), transferMoney()One meaningful operation replaces several low-level calls.
Compositionthe facade holds its services as fieldsIt reuses existing classes without inheriting from them.
PolymorphismMap<String, IAccount>, find(accNo).deposit(amt)The facade treats all account types the same through the interface.
Loose couplingclient depends only on LibraryFacade / BankServiceChanging a subsystem changes the facade, not every client.
SRP (watch it)the facade only orders callsBusiness rules stay in the subsystems; a facade that gains rules becomes a God class.
DIP (improve)services created with new inside the facadePass them in through the constructor (as interfaces) so they can be swapped or mocked.

Other lecture examples

Netflix "Play": one click; behind it authentication, subscription check, recommendation, CDN selection, video decoder, subtitles, analytics. Multi-agent systems: the client talks to one facade that coordinates many agents (collector, preprocessor, analyser, predictor, reporter). Wedding planner / waiter: one person deals with all the suppliers.
