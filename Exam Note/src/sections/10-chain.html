Chain of Responsibility

A request is passed along a line of handlers. Each one either deals with it or hands it to the next.
Behavioural
Understand

Spot it: the question says…

several levels of support / escalationapproval limits: team leader, manager, director, CEO a sequence of checks that must occur in order and be easy to extendmultiple sub-filters handle different prioritiesexception handlingmultiple handlers hard-coded in sequence

The idea

Without the pattern, the sender has a long if-else: "if it's a password issue send it to L1, else if it's an install issue send it to L2…". The sender knows every handler, and adding a level means editing it.

With the chain, each handler only knows the next one. The sender gives the request to the first handler and doesn't care who finally deals with it. Like a hospital: nurse → doctor → specialist, each passing on what they can't treat. Java's try/catch works the same way.

Two ways a chain runs

1. Escalation: the first handler that can handle the request does, and the chain stops. Support levels, expense approval, exceptions by priority.

2. Pipeline of checks: every handler checks the request; any failure stops it, and passing all means accepted. Membership → availability → fines; inventory → fraud → delivery area; spam sub-filters.

The chain ends when a handler deals with the request, or when the end is reached. Add a fallback handler at the end so nothing goes unhandled.

The parts

PartJobSupport desk (Quiz 7)
Handler «abstract»Holds a next link, has setNext() and handle()SupportHandler
Concrete handlersDeal with the request if they can, otherwise pass it onL1Support, L2Support, L3Support, SpecialistSupport

ClientBuilds the chain once, sends every request to the first handlerSupportDesk

How to order the chain asked as "prioritise"

  • Cost / speed: cheap, fast checks first, so expensive ones run less often.
  • Rejection rate: checks that catch the most go early.
  • Severity / security: dangerous cases first (e.g. a malware attachment).
  • Accuracy: low false-positive checks before risky ones.
  • Business priority and availability of the handler.

Don't mix it up

  • vs State: Chain asks "who will handle this request?" and the request moves along handlers. State asks "how should I behave now?" and the object hands work to its current state.
  • vs Decorator: decorators all run and add to the result. In a chain, usually one handler takes the request.

Chain of Responsibility: write

The support desk from Quiz 7, with the logging procedure enforced (Quiz 7 Q4).
Behavioural
Write

W1 Name it and say why 2–5 marks

I would use the Chain of Responsibility pattern, which is a behavioural pattern. It avoids coupling the sender of a request to its receiver by giving more than one object a chance to handle it. The handlers are chained, and the request is passed along until one handles it.

Reasons: (1) the support desk sends every request to L1 and doesn't need to know who solves it; (2) each level has one responsibility; (3) levels can be added, removed or reordered without changing the client or the other levels (Open/Closed); (4) a fallback at the end means nothing goes unhandled.

Mapping: request = SupportRequest · handler = SupportHandler «abstract» with next · concrete handlers = L1, L2, L3, Specialist · client = SupportDesk.

W2 Class diagram

the "next" link is a self-association on the Handler
W3 · Java (Quiz 7 Q3: a database connectivity request goes through the chain)
public abstract class SupportHandler {
  protected SupportHandler next;

  public SupportHandler setNext(
          SupportHandler n) {
    this.next = n;
    return n;   // allows chaining
  }

  // fixed procedure (Template Method, Q4)
  public final void handle(SupportRequest r) {
    log("received " + r.getType());
    boolean solved = attemptToSolve(r);
    log(solved ? "RESOLVED" : "escalated");
    if (!solved && next != null) {
      next.handle(r);      // pass it along
    }
  }
  protected abstract boolean
      attemptToSolve(SupportRequest r);

  private void log(String msg) {
    System.out.println(
      getClass().getSimpleName() + ": " + msg);
  }
}
public class L1Support extends SupportHandler {
  protected boolean attemptToSolve(
          SupportRequest r) {
    return r.getType() == PASSWORD_RESET
        || r.getType() == ACCOUNT_BLOCKED;
  }
}
// L2Support, SpecialistSupport, SupportRequest:
// "Chain: complete code"
public class L3Support extends SupportHandler {
  protected boolean attemptToSolve(
          SupportRequest r) {
    return r.getType() == DB_CONNECTIVITY
        || r.getType() == PERFORMANCE;
  }
}

// CLIENT: build once, send to the first
SupportHandler chain = new L1Support();
chain.setNext(new L2Support())
     .setNext(new L3Support())
     .setNext(new SpecialistSupport());
chain.handle(new SupportRequest(
    DB_CONNECTIVITY, "App can't reach MySQL"));
// L1 escalated → L2 escalated → L3 RESOLVED

Chain: the spam filter question, OOP and SOLID

2022 Q3 (25 marks), all five parts answered, then the OOP terms.
Behavioural
Answers

3.1 Diagram and components · 4m

solid = passed, go on · dashed = marked as spam, stop

Components: the mail server (client) receives the email and passes it to the first filter. Sender filter (blacklist, domain reputation), time filter (odd hours, bursts), content filter (keywords, links, NLP), attachment filter (file types, virus scan). Any filter can mark it SPAM and stop; if all pass, it goes to the inbox.

3.2 Pattern and reasons 5m

Chain of Responsibility. Each sub-filter is a handler with a link to the next one. The email passes Sender → Time → Content → Attachment. Reasons: the mail server is decoupled from the filters (it only knows the first); each filter has one responsibility; filters can be added, removed or reordered without changing the others; the chain can be configured at runtime.

3.3 Prioritising the components 6m

  • Cost and speed: cheap checks first (sender blacklist, sent time); expensive ones last (content NLP, attachment virus scan).
  • Rejection rate: the filter that catches the most spam early saves work for the rest.
  • Severity: a malware attachment may be moved first for security.
  • Accuracy: filters with few false positives before risky ones.

So a sensible order is: Sender → Time → Content → Attachment.

3.4 Adding more sub-components 5m

Write a new class that extends SpamFilter (e.g. LinkReputationFilter) and link it in with setNext(), or list it in a config file that builds the chain. Existing filters and the mail server don't change (Open/Closed).

3.5 High Availability and DR 5m

HA: the filters are stateless, so run the chain on several servers behind a load balancer; a backup handler skips a filter that times out; a message queue so no mail is lost. DR: blacklists and rules backed up and replicated to a second region, with automatic failover.

OOP and SOLID in the Chain code name the concept → class/member → effect

The 2025 "checks in order" questions, exceptions, authorization, and the challenges.
Behavioural
Answers

Checks that must run in order 2025 Q4.4 inventory → fraud → delivery · Q3.4 membership → availability → fines, 5m

Chain of Responsibility in the pipeline form. Each check is a handler. If it fails, the chain stops and returns the reason ("membership expired"); if it passes, the request goes to the next check. A new check (e.g. BorrowLimitCheck) is one new class and one new link.

public abstract class Validator {
  private Validator next;
  public Validator linkWith(Validator n) {
    this.next = n;
    return n;
  }
  public boolean validate(Order o) {
    if (!check(o)) return false; // stop
    return next == null || next.validate(o);
  }
  protected abstract boolean check(Order o);
}
class InventoryCheck extends Validator {
  protected boolean check(Order o) {
    return Stock.available(o); }
}
// FraudCheck, DeliveryAreaCheck, stubs:
// "Chain: complete code"

// CLIENT
Validator v = new InventoryCheck();
v.linkWith(new FraudCheck())
 .linkWith(new DeliveryAreaCheck());
if (v.validate(order))
  processor.handlePayment(order);

Exceptions with different priorities 2023 Q4.3 · 2024 Q4.3

Chain of handlers ordered by severity: ValidationErrorHandler (low: show a message) → PaymentErrorHandler (retry or offer another method) → SystemErrorHandler (log, alert the admin) → DefaultHandler (generic error page). Each one handles the types it knows and passes the rest on, just like nested try/catch blocks.

W5 Challenges → fix from the slides

ChallengeHow to handle it
No guarantee the request is handled (falls off the end)A default / fallback handler at the end (Specialist, manual review).
Debugging is trickyLog at every handler (who received it, who handled it); unit-test each handler.
Long chains are slow; unnecessary handlers runOrder by priority (cheap and likely first); skip handlers using request info; keep the chain short.
Order matters; cycles if mis-linkedBuild the chain in one place (builder or config) and check for cycles.

Mistakes: the client calling every handler itself (that's the if-else approach) · forgetting the next != null check · no fallback handler · drawing links between concrete handlers instead of the self-association on Handler.

public enum IssueType {
  PASSWORD_RESET, ACCOUNT_BLOCKED,
  INSTALLATION_ERROR, DB_CONNECTIVITY,
  PERFORMANCE, OTHER }

public class SupportRequest {
  private final IssueType type;
  private final String description;
  public SupportRequest(IssueType t,
                        String d) {
    type = t; description = d; }
  public IssueType getType() {
    return type; }
  public String getDescription() {
    return description; }
}
// the handlers use the constants directly:
// import static IssueType.*;
public class L2Support
    extends SupportHandler {
  protected boolean attemptToSolve(
      SupportRequest r) {
    return r.getType()
        == INSTALLATION_ERROR;
  }
}
public class SpecialistSupport
    extends SupportHandler {
  // fallback: rare problems end here
  protected boolean attemptToSolve(
      SupportRequest r) {
    return true; }
}

class FraudCheck extends Validator {

    return !FraudService.isSuspicious(o); }
}
class DeliveryAreaCheck extends Validator {
  protected boolean check(Order o) {

    return true; } }

  static boolean isSuspicious(Order o) {
    return o.getAmount() > 1_000_000; } }

  static boolean delivers(String c) {
    return true; } }

Spam filter handler 2022 Q3.2 / 3.4

public abstract class SpamFilter {
  private SpamFilter next;
  public SpamFilter setNext(SpamFilter n) {
    next = n; return n; }
  // true = deliver, false = spam (stop)
  public boolean isClean(Email e) {
    if (isSpam(e)) return false;
    return next == null || next.isClean(e);
  }
  protected abstract boolean isSpam(Email e);
}
public record Email(String sender,
    java.time.LocalTime sentAt,
    String body, List attachments) { }
class SenderFilter extends SpamFilter {
  private final Set blacklist =
      Set.of("spam@bad.com");   // demo data
  protected boolean isSpam(Email e) {
    return blacklist.contains(e.sender()); }
}
class AttachmentFilter extends SpamFilter {
  protected boolean isSpam(Email e) {
    return e.attachments().stream()
        .anyMatch(f -> f.endsWith(".exe")); }
}
// TimeFilter, ContentFilter: same idea
SpamFilter chain = new SenderFilter();
chain.setNext(new TimeFilter())
     .setNext(new ContentFilter())
     .setNext(new AttachmentFilter());

Expense approval lecture group activity

public class ExpenseRequest {
  private final double amount;
  private final String description;
  public ExpenseRequest(double a, String d) {
    amount = a; description = d; }
  public double getAmount() { return amount; }
  public String getDescription() {
    return description; }
}
public abstract class ExpenseApprover {
  protected ExpenseApprover next;
  public void setNextApprover(
      ExpenseApprover n) { next = n; }
  public final void approveRequest(
      ExpenseRequest r) {
    if (canApprove(r)) processRequest(r);
    else if (next != null)
      next.approveRequest(r);
    else System.out.println(
        "Cannot be approved");
  }
  protected abstract boolean
      canApprove(ExpenseRequest r);
  protected abstract void
      processRequest(ExpenseRequest r);
}
public class TeamLeaderApprover
    extends ExpenseApprover {
  private static final double LIMIT = 1000;
  protected boolean canApprove(
      ExpenseRequest r) {
    return r.getAmount() <= LIMIT; }
  protected void processRequest(
      ExpenseRequest r) {
    System.out.println("Team Leader "
        + "approved " + r.getAmount()); }
}
// ManagerApprover    LIMIT = 5000
// DirectorApprover   LIMIT = 20000
// CEOApprover: canApprove() returns true
//   (same code, different LIMIT and name)

ExpenseApprover t = new TeamLeaderApprover();
ExpenseApprover m = new ManagerApprover();
ExpenseApprover d = new DirectorApprover();
ExpenseApprover c = new CEOApprover();
t.setNextApprover(m);
m.setNextApprover(d);
d.setNextApprover(c);
t.approveRequest(
    new ExpenseRequest(3500, "Meeting"));
// Manager approved 3500.0

Exceptions by type and priority 2023 Q4.3 · 2024 Q4.3

public abstract class ErrorHandler {
  private ErrorHandler next;
  public ErrorHandler setNext(
      ErrorHandler n) {
    next = n; return n; }
  public void handle(Exception e) {
    if (canHandle(e)) process(e);
    else if (next != null) next.handle(e);
  }
  protected abstract boolean
      canHandle(Exception e);
  protected abstract void
      process(Exception e);
}
class ValidationErrorHandler
    extends ErrorHandler {
  protected boolean canHandle(Exception e) {
    return e instanceof
        IllegalArgumentException; }
  protected void process(Exception e) {
    System.out.println("Please check: "
        + e.getMessage()); }
}
class PaymentErrorHandler
    extends ErrorHandler {
  protected boolean canHandle(Exception e) {
    return e instanceof PaymentException; }
  protected void process(Exception e) {
    System.out.println("Payment failed, "
        + "try another method"); }
}
class DefaultHandler extends ErrorHandler {
  protected boolean canHandle(Exception e) {
    return true; }               // fallback
  protected void process(Exception e) {
    System.out.println("Logged, admin "
        + "alerted: " + e); }
}
class PaymentException
    extends RuntimeException { }
// checkout
ErrorHandler h = new ValidationErrorHandler();
h.setNext(new PaymentErrorHandler())
 .setNext(new DefaultHandler());
try { checkout.run(); }
catch (Exception e) { h.handle(e); }
