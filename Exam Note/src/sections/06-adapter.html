Adapter

A translator class that lets your code use a class whose methods don't match what your code expects.
Structural
Understand

Spot it: the question says…

legacy systemsupplied by an external vendor, can't modifythe new scanner provides readBarcode() instead of scanBook() hundreds of calls to the old methodthird-party web services with different method signatures websites developed by different vendors and technologiesincompatible interfaces

The idea

Your system calls scanBook() in hundreds of places. The new scanner only has readBarcode(). You can't change the scanner (vendor code) and you don't want to change hundreds of calls.

So you write one small class that looks like the old scanner (it has scanBook()) and inside it calls readBarcode(). Like a travel plug adapter: the socket and the plug stay as they are, and the adapter sits between them.

Why not just change the code? Quiz 3 Q1

  • Hundreds of call sites: a huge change with a high risk of new bugs, full re-testing and downtime.
  • Tested, working code should stay closed for modification (Open/Closed).
  • The vendor class can't be changed: no source code, a licence or contract, or other systems depend on it.

The parts "identify the participants" is asked directly

PartJobBarcode scanner (Quiz 3)
ClientThe existing code. Uses the Target interface only.LibrarySystem
TargetThe interface the client expects.BarcodeScanner with scanBook()
AdapteeThe existing class with the useful behaviour but the wrong interface.NewBarcodeScanner with readBarcode()
AdapterImplements Target, holds an Adaptee, translates each call.ScannerAdapter

Flow: client calls scanBook() → it goes to ScannerAdapter → the adapter calls NewBarcodeScanner.readBarcode() → the result comes back. Only the adapter knows the adaptee exists.

W1 Name it and say why 2–5 marks

I would use the Adapter pattern, which is a structural pattern. It converts the interface of a class into another interface the client expects, so classes with incompatible interfaces can work together.

Reasons: (1) the new scanner is reused without modifying it (it is vendor code); (2) the hundreds of existing scanBook() calls stay unchanged, so there is no risk to tested code (Open/Closed); (3) the client depends only on the Target interface, so another scanner later is just another adapter.

Mapping: Client = LibrarySystem · Target = BarcodeScanner (scanBook()) · Adaptee = NewBarcodeScanner (readBarcode()) · Adapter = ScannerAdapter.

W2 Class diagram

the adapter implements the target and points to the adaptee
W3 · Java
// 1. TARGET: what the library code expects
public interface BarcodeScanner {
    String scanBook();
}
// 2. ADAPTEE: vendor class, we can't change it
public class NewBarcodeScanner {
    public String readBarcode() {
        return "978-0134685991";
    }
}
// 3. ADAPTER: is a Target, wraps Adaptee
public class ScannerAdapter
        implements BarcodeScanner {
    private final NewBarcodeScanner scanner;
    public ScannerAdapter(NewBarcodeScanner s) {
        this.scanner = s;
    }
    public String scanBook() {
        // translate the call
        return scanner.readBarcode();
    }
}
// 4. CLIENT: only this line changes
BarcodeScanner sc =
    new ScannerAdapter(new NewBarcodeScanner());
// all the old calls stay the same
String isbn = sc.scanBook();

Adapter: past questions answered

Same pattern every time: one interface your system owns, one adapter per outside system.
Structural
Answers

Third-party travel web services 2022 Q1.3, 10m

Pattern: Adapter, one per provider. HotelService talks to one interface it owns, HotelProvider. HiltonAdapter, ShangriLaAdapter and so on each translate that interface into the provider's own SOAP / REST / SDK calls. Airlines and taxis are done the same way.

1.3.1 Challenge1.3.2 Mechanism
Many adapters to write and maintainA common interface for all of them; pick the adapter from configuration with a Factory or registry.
Different data formats (XML vs JSON) and error codesOne common data object (DTO) and a mapper inside each adapter; unit-test each adapter.
A provider changes its API versionOnly that one adapter changes; version the adapters.
A provider is slow or downTimeouts, retries, caching, and fall back to another provider.

Event websites from different vendors 2023 Q3.3, 5m

The restaurant owns one interface, EventSource with getEvents(), returning a common Event object. Each website gets its own adapter (RssEventAdapter, JsonApiEventAdapter, HtmlScraperAdapter) that converts that site's format. The restaurant site loops over a list of EventSource. A new vendor means a new adapter and nothing else changes.

A Facade (EventFeed) can then combine all sources into one list.

W5 Challenges → fix

  • Many adapters (one per vendor) → common Target, created by a Factory.
  • Format translation → a mapper inside the adapter; unit-test it.
  • Vendor API changes → only that adapter changes.
  • Adaptee is missing a feature → the adapter gives a default or throws a clear exception.
  • Extra layer → tiny overhead; worth it for stable legacy code.

Adapter: class adapter and two-way adapter

The other two kinds from the "three kinds" table, written out for the barcode scanner.
Structural
Variants

Class adapter adapter extends the adaptee and implements the target

// Target and Adaptee are the same as W3
public interface BarcodeScanner {
  String scanBook();
}
public class NewBarcodeScanner {      // vendor
  public String readBarcode() {
    return "978-0134685991"; }
}
// CLASS ADAPTER: inherits readBarcode()
public class ScannerClassAdapter
    extends NewBarcodeScanner
    implements BarcodeScanner {
  public String scanBook() {
    return readBarcode();   // inherited call
  }
}
// client: no adaptee object to pass in
BarcodeScanner sc = new ScannerClassAdapter();
String isbn = sc.scanBook();

Difference from the object adapter (W3): no scanner field and no constructor parameter. The adapter is a NewBarcodeScanner (inheritance) instead of having one (composition).

  • Works only if the adaptee is not final and Java allows one superclass.
  • Fixed to that one class: it can't adapt a subclass chosen at runtime.
  • readBarcode() is also public on the adapter, so the adaptee's interface leaks.

Two-way adapter one class implements both interfaces

Use when old and new code must both work during a migration. Example: the old desk software calls scanBook() but some desks now have new scanners; the new self-service kiosk calls readBarcode() but some desks still have old scanners. Assumption: the new subsystem's method is put behind its own interface, ModernScanner.

public interface BarcodeScanner {      // old side
  String scanBook(); }
public interface ModernScanner {       // new side
  String readBarcode(); }

public class TwoWayScannerAdapter
    implements BarcodeScanner, ModernScanner {
  private final ModernScanner modern;
  private final BarcodeScanner legacy;
  // wrap a NEW scanner for OLD code
  public TwoWayScannerAdapter(ModernScanner m) {
    modern = m; legacy = null; }
  // wrap an OLD scanner for NEW code
  public TwoWayScannerAdapter(BarcodeScanner l) {
    legacy = l; modern = null; }

  public String scanBook() {           // old call
    return modern != null ? modern.readBarcode()
                          : legacy.scanBook(); }
  public String readBarcode() {        // new call
    return legacy != null ? legacy.scanBook()
                          : modern.readBarcode(); }
}
// old code, new scanner
BarcodeScanner a =
  new TwoWayScannerAdapter(
    new NewBarcodeScanner());
a.scanBook();
// kiosk, old scanner
ModernScanner b =
  new TwoWayScannerAdapter(
    new OldDeskScanner());
b.readBarcode();

NewBarcodeScanner implements ModernScanner; OldDeskScanner implements BarcodeScanner. Cost: two translations to keep correct, and the adapter must be told which side it wraps.

The printer and payment-gateway code from the slides, and the Java library adapters.

Examples

Printer → ModernPrinter lecture

public interface Printer {    // Target
  void print(String text); }
public class ModernPrinter {  // Adaptee
  public void printPDF(String file) {
    System.out.println("Printing PDF : "
        + file); }
}
public class PrinterAdapter   // Adapter
    implements Printer {
  private ModernPrinter modernPrinter;
  public PrinterAdapter(ModernPrinter p) {
    this.modernPrinter = p; }
  @Override
  public void print(String text) {
    modernPrinter.printPDF(text); }
}
// Client
Printer printer =
    new PrinterAdapter(
        new ModernPrinter());
printer.print("Report.pdf");
// Printing PDF : Report.pdf

The slide's UML draws the adapter → adaptee link as composition (filled diamond at PrinterAdapter): the adapter owns its adaptee.

Old system → new payment gateway lecture

public interface PaymentGateway { // old

public class NewGateway {         // new

    implements PaymentGateway {

Quiz 1 legacy parking payment, all classes Quiz 1 Q5

// TARGET: what the parking system calls
public interface PaymentProcessor {
  boolean pay(double amount); }

// ADAPTEE: STUB of the vendor class.
// The real one drives the machine; its
// method name and codes are assumed.
public class LegacyPaymentMachine {
  // amount in cents; returns 0 = success
  public int makeTransaction(int cents) {
    return cents > 0 ? 0 : 1; }
}
public class LegacyPaymentAdapter
    implements PaymentProcessor {
  private final LegacyPaymentMachine m;
  public LegacyPaymentAdapter(
      LegacyPaymentMachine m) { this.m = m; }
  public boolean pay(double amount) {
    int cents =
        (int) Math.round(amount * 100);
    return m.makeTransaction(cents) == 0;
  }
}
// used by PaymentDueState (tab 09)
PaymentProcessor processor =
    new LegacyPaymentAdapter(
        new LegacyPaymentMachine());
