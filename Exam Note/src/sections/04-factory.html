Factory Method

One place decides which class to create. The rest of the code just asks for "a database" or "a book".
Creational
Understand

Spot it: the question says…

create different types of X depending on the user's requestdifferent types of accounts / books / payments supports MySQL, PostgreSQL and MongoDBtoo many if-else blocks to create objects without exposing the concrete classscalable, extensible product-based frameworkmodules created depending on the user's needs

The idea

When the program needs one of several related types, the code that uses the object shouldn't have to know which class to new. A factory takes the request ("MYSQL", "FICTION", "CARD") and hands back the right object, typed as the common interface.

Like ordering at a restaurant: you ask for "a pizza", and the kitchen decides how to make it. You never go into the kitchen.

The problem it removes

// BEFORE: copied all over the client
if (type.equals("MYSQL"))
    db = new MySQLDatabase();
else if (type.equals("MONGO"))
    db = new MongoDatabase();
// new database = edit every copy

// AFTER: one line, interface only
Database db =
    DatabaseFactory.getDatabase(type);

The parts name them in your answer

PartJobExample
Product «interface»The common type every product sharesDatabase, Book, Account
Concrete productsThe real classesMySQLDatabase, FictionBook, SavingAccount
Factory / CreatorDecides which concrete class to create and returns it as the ProductDatabaseFactory.getDatabase(type)
ClientAsks the factory, then uses the product through the interface onlyProductService

Don't mix it up

  • vs Singleton: Factory decides which type; Singleton decides how many (one). Often used together: the factory or the connection it creates is a Singleton.
  • vs Facade: Factory creates objects. Facade coordinates objects that already exist.
  • vs Abstract Factory: Abstract Factory creates whole families of related objects (e.g. a Windows button + Windows menu). Not taught in detail.

Why is new in the client bad?

It hard-codes the concrete class. Every new type forces a change in the client, which breaks Open/Closed, and the client depends on details instead of an abstraction, which breaks Dependency Inversion. The factory also separates creating from using (Single Responsibility).

W1 Name it and say why 2–5 marks

I would use the Factory Method pattern, which is a creational pattern. It defines an interface for creating an object but lets subclasses decide which class to instantiate, so the client never uses new on a concrete class.

The W2/W3 code on this page is the Simple Factory form (one class, one switch), which is what Quiz 2 and the 2025 BookFactory ask for. The GoF form, with Creator subclasses, is on the page "Factory Method: GoF version in full". Say which form you are writing.

Reasons: (1) loose coupling, because the client depends only on the Database interface, not on MySQL or MongoDB classes; (2) the creation logic is in one place instead of if-else copied across the code; (3) it is easy to extend (Open/Closed): a new type is one new class and one new case, and client code doesn't change.

Mapping: Product = Database «interface» · concrete products = MySQLDatabase, PostgreSQLDatabase, MongoDatabase · factory = DatabaseFactory.getDatabase(type) · client = ProductService.

dashed «create» arrows from the factory; dashed triangles to the interface
W3 · Java
// 1. PRODUCT
public interface Database {
    void connect();
    void create(Product p);
}
// 2. CONCRETE PRODUCTS
public class MySQLDatabase
        implements Database {
    public void connect() {
        /* open MySQL connection */ }
    public void create(Product p) {
        /* INSERT into MySQL */ }
}
// PostgreSQL, Mongo + Product class:
// "Factory Method: complete code"
// 3. FACTORY: the only place with "new"
public class DatabaseFactory {
  public static Database getDatabase(
          String type) {
    switch (type.toUpperCase()) {
      case "MYSQL": return new MySQLDatabase();
      case "POSTGRES":
          return new PostgreSQLDatabase();
      case "MONGO": return new MongoDatabase();
      default: throw new
        IllegalArgumentException(type);
    }
  }
}
// 4. CLIENT: knows only the interface
Database db =
    DatabaseFactory.getDatabase("MYSQL");
db.create(product);

Database objects Quiz 2 Q1–Q3

Role of the factoryIt takes object creation out of the client. The client asks DatabaseFactory.getDatabase("MYSQL") and receives a Database. The factory decides and creates MySQL, PostgreSQL or Mongo.
Two advantages(1) Loose coupling: switching from MySQL to PostgreSQL changes only the parameter or config, not the business code. (2) Easy to extend: adding Oracle is one new class and one new case, and the creation logic stays in one place.
Why the developer doesn't need to know the DBBecause of abstraction and polymorphism. The variable's type is the Database interface, and every database implements connect() and create(). The factory returns the right object at runtime, and db.create(product) runs the right version automatically.

Bank accounts 2023 Q4.2, 5m

Factory Method (Simple Factory form; full code on "Factory Method: complete code"). An Account abstract class with deposit(), withdraw() and calculateInterest(). CurrentAccount, SavingAccount and ChildrenAccount implement it with their own rules (overdraft, interest, withdrawal limit). AccountFactory.createAccount(type) returns the right one. The bank code only uses Account, so a new FixedDeposit account can be added without touching it.

Payment objects 2025 Q4.1(d)

Factory Method. PaymentFactory.create(method) returns CreditCardProcessor, PayPalProcessor or CODProcessor, all typed as PaymentProcessor. The customer picks the method at runtime, so the client needs no new and no if-else. Each processor then follows the Template Method handlePayment() (tab 07).

LMS modules / product framework 2022 Q4.2, Q4.5

Factory Method. A Module interface, implemented by Quiz, Forum, Assignment and VideoLecture. ModuleFactory.create(userNeed) builds what the user needs. New modules (new products) are new classes registered with the factory, so the framework grows without changing existing code. That is what "scalable, extensible product-based framework" is asking for.

"It avoids code duplication." Agree?

Yes. The creation logic (the if-else and the new calls) is written once in the factory instead of in every client. Shared behaviour can sit in an abstract creator. The cost is extra classes, so keep the factory parameterised rather than writing near-identical creators.

Mistakes: client still calls new MySQLDatabase(); factory returns the concrete type instead of the interface; missing «create» arrows.

W5 Challenges → fix

  • More classes → keep one parameterised factory, not a creator per type.
  • The switch is edited for each new type → register types in a Map or config.
  • Unknown type → validate input, throw a clear exception.
  • Need one shared factory or connection → make it a Singleton.

Complete code

Bank accounts in full 2023 Q4.2 · rates and limits are example values, not from the question

public abstract class Account {
  protected final String accountNo;
  protected double balance;
  protected Account(String no, double open) {
    accountNo = no; balance = open; }
  public void deposit(double amt) {
    if (amt <= 0)
      throw new IllegalArgumentException();
    balance += amt; }
  public abstract void withdraw(double amt);
  public abstract double interestRate();
  public double calculateInterest() {
    return balance * interestRate(); }
  public double getBalance() {
    return balance; }
}
public class CurrentAccount extends Account {
  private static final double
      OVERDRAFT = 50000;
  public CurrentAccount(String n, double o) {
    super(n, o); }
  public void withdraw(double amt) {
    if (balance - amt < -OVERDRAFT)
      throw new IllegalStateException(
          "Overdraft limit");
    balance -= amt; }
  public double interestRate() {
    return 0; }
}
public class SavingAccount extends Account {
  public SavingAccount(String n, double o) {
    super(n, o); }
  public void withdraw(double amt) {
    if (amt > balance)   // no overdraft
      throw new IllegalStateException(
          "Funds");
    balance -= amt; }
  public double interestRate() {
    return 0.04; }
}
public class ChildrenAccount extends Account {
  private static final double MAX_TX = 5000;
  public ChildrenAccount(String n,double o){
    super(n, o); }
  public void withdraw(double amt) {
    if (amt > MAX_TX || amt > balance)
      throw new IllegalStateException(
          "Limit");
    balance -= amt; }
  public double interestRate() {
    return 0.06; }
}
public class AccountFactory {
  public static Account createAccount(
      String type, String no, double o) {
    switch (type.toUpperCase()) {
      case "CURRENT":
        return new CurrentAccount(no, o);
      case "SAVING":
        return new SavingAccount(no, o);
      case "CHILDREN":
        return new ChildrenAccount(no, o);
      default: throw new
          IllegalArgumentException(type);
    }
  }
}

Factory Method: GoF version in full

The lecture's payment example: an abstract Creator, one ConcreteCreator per product. Then how it differs from a Simple Factory.
Creational
GoF form

Class diagram (GoF)

Creator «uses» Product; each ConcreteCreator «creates» its ConcreteProduct
// PRODUCT
public interface Payment {
  void pay(double amount);
}
// CONCRETE PRODUCTS
public class CreditCard
    implements Payment {
  public void pay(double amount) {
    System.out.println("Paid " + amount
        + " using Credit Card"); }
}
public class PayPal implements Payment {
  public void pay(double amount) {
    System.out.println("Paid " + amount
        + " using PayPal"); }
}
public class Crypto implements Payment {
  public void pay(double amount) {
    System.out.println("Paid " + amount
        + " using Crypto"); }
}
// CREATOR
public abstract class PaymentFactory {
  // the factory method: subclasses decide
  public abstract Payment createPayment();
  // someOperation(): uses the product
  // without knowing its concrete class
  public void processPayment(double amount) {
    Payment payment = createPayment();
    payment.pay(amount);
  }
}
// CONCRETE CREATORS
public class CreditCardFactory
    extends PaymentFactory {
  public Payment createPayment() {
    return new CreditCard(); }
}
public class PayPalFactory
    extends PaymentFactory {
  public Payment createPayment() {
    return new PayPal(); }
}
public class CryptoFactory
    extends PaymentFactory {
  public Payment createPayment() {
    return new Crypto(); }
}
// CLIENT (PaymentSystem)
PaymentFactory factory =
    new CreditCardFactory();
factory.processPayment(1000.00);
// Paid 1000.0 using Credit Card

Factory: Simple Factory vs Factory Method

Two different designs that are often given the same name. Know which one you are writing.
Creational
Theory

Simple Factory vs GoF Factory Method lecture comparison

Simple FactoryFactory Method (GoF)
StructureOne factory class, usually a static create(type) method (DatabaseFactory, BookFactory).A hierarchy: an abstract Creator declares factoryMethod(); one ConcreteCreator per product overrides it (CreditCardFactory…).
Who decidesAn if-else / switch on a parameter, inside the factory.The subclass, through inheritance and overriding. The client decides only which creator object to use.
Adding a typeNew product class and edit the switch. Clients stay closed; the factory itself is modified.New product class and new creator subclass. No existing class is edited (Open/Closed for the whole design).
Creator logicOnly creates.The Creator can also hold shared code that uses the product (processPayment(), scheduleTask()).
StatusA common idiom, not one of the 23 GoF patterns.One of the GoF creational patterns.
CostFew classes; the switch grows.More classes (a creator per product).

Which to write: if the question says "Factory Method", "let subclasses decide", or wants new types added without editing existing classes, write the GoF form. If it only asks to create different objects from one place by type (Quiz 2, 2025 BookFactory), a Simple Factory meets the requirement; call it a Simple Factory and, for extra marks, say how the GoF form would remove the switch.
