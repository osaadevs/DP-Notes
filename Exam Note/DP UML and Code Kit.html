How this kit is different from the note: the note explains each pattern with one scenario. This kit gives you the empty shape of each pattern, with the role names on the boxes, and tells you where in any question to find the word that goes in each box. You fill in the shape; you never have to invent it.

Where boxes go on the page

  1. Interface / abstract class: top middle.
  2. Concrete classes: one row underneath, triangles pointing up into the parent.
  3. The pattern's special box (decorator, adapter, proxy, context, factory): to the side, with its has-a arrow going sideways.
  4. Client: far left, one arrow to what it uses.

Why you lose track, and the fix

You already pick the right pattern. What breaks is doing four jobs in your head at the same time.
Method
Read first

The four jobs you are juggling

JOB 1NamingWhat do I call each class, field and method?
JOB 2ShapeWhich boxes does this pattern have, and which one is on top?
JOB 3SymbolsWhich arrow, which end, dashed or solid, + or −?
JOB 4AmountHow much code, which classes, where do I stop?

Doing all four while drawing is what makes you lose the thread: you invent a name, forget the arrow, change the name in the code, and the diagram and code stop matching. The fix is to do them one at a time, in a fixed order, and copy jobs 2 and 3 from this kit instead of remembering them.

The routine for every diagram or code question same 4 steps, any pattern

StepTimeWhat you do
1 · Slot table2 minOpen this kit at the pattern's page. In your rough-work space, copy the Role column. Next to each role, write the word from the question (the page tells you where to look). This little table is now the only place names come from.
2 · Draw4–6 minCopy the pattern's skeleton diagram box by box, writing your name from the slot table instead of the role name. The arrows are already decided by the skeleton, so just copy them.
3 · Code5–8 minWrite the classes in the order of the slot table, top to bottom. Use the code skeleton on the pattern page; change only the names.
4 · Check1 minRun the checklist at the bottom of the pattern page. Most lost marks are on that list.
The golden rule: diagram and code copy their names from the same slot table, so they always match, and you never have to remember a name halfway through.

How much to draw by marks

3–4 mThe pattern's core boxes only (interface + 2 concrete + the special box). Names and arrows correct; 1–2 methods each.
5–6 mFull skeleton from the pattern page, with fields and 2–3 methods in each box, plus the client.
8–10 mFull skeleton + every concrete class the question lists + stereotypes («interface», «abstract») + multiplicities on has-a links + a 1–2 line note under the diagram saying which box plays which role.

How much code by marks

2–3 mExactly what is asked (often just the interface or one class). Nothing extra.
4–5 mWhat is asked, in full (fields, constructor, methods), plus 3 lines of client code showing it used.
6+ mInterface/abstract class + the pattern class + two concrete classes + client with a comment showing the output.

Never needed unless asked: imports, getters/setters, main, full error handling.

Two methods are enough

For each interface, pick the one or two actions the question is about. A pricing question → getCost(), getDescription(). A states question → one method per event. An approval question → handle(request). Don't list every possible method; examiners mark the pattern, not completeness.

Step 2: the box and the arrow, decided by questions

You don't need to remember UML. Answer the yes/no questions and the symbol picks itself.
Method
Drawing

What goes inside one box

Box rules

  • Top: the name. Write «interface» above it for an interface. Write the name in italics (or «abstract» above it) for an abstract class.
  • Middle: fields, - name : Type. Only the 1–3 the pattern needs (the wrapped object, the next handler, the current state, the price).
  • Bottom: methods, + name(param : Type) : ReturnType. 2–3 is enough.
  • Interface: leave the middle box empty (interfaces have no fields).
  • + public · − private · # protected · underline = static · italic method = abstract

Which arrow? Ask in this order and stop at the first "yes"

Question about class A and class BDrawExample
1. Does A say implements B? (B is an interface)dashed line, hollow triangle at BBasicBurger → Burger
2. Does A say extends B? (B is a class / abstract class)solid line, hollow triangle at BCheese → BurgerDecorator
3. Does A have a field of type B? (A "has a" B)solid line, open arrow at B; add a hollow diamond at A if A wraps or collects Bdecorator ◇→ component, context ◇→ state, proxy → real subject
4. Does A only use or create B inside a method?dashed line, open arrow at B; label «create» for factoriesfactory ⇢ product; client ⇢ getInstance()

Memory trick: triangle = "is a" (it's a kind of that), and the triangle always touches the parent. Dashed triangle = interface parent, solid triangle = class parent. A plain arrow = "has a" or "uses". Note: a decorator has both a triangle (it is a Component) and a diamond arrow (it holds a Component). That's correct, not a mistake.

Step 3: writing the code, in order

Every pattern's code is built from the same seven small moves. Learn the moves once; the pattern pages just arrange them.
Method
Code

Write the classes in this order same order as your slot table

1Interface / abstractThe general word. Method headers only (or the final template method).
2One concrete classFields, constructor, every method. In full.
3The pattern classDecorator, adapter, proxy, factory, context, handler.
4More concretesOnly if marks allow. Same shape as #2.
5Client3–5 lines that use it, with // output.

Put a comment with the role above each class (// COMPONENT, // ADAPTER). It shows the examiner you know the parts, and it keeps you on track.

The seven moves

// MOVE 1: an interface = method headers
public interface Burger {
  double getCost();
  String getDescription();
}

// MOVE 2: implements = fill in every method
public class BasicBurger implements Burger {
  public double getCost() { return 500; }
  public String getDescription() {
    return "Basic burger"; }
}

// MOVE 3: has-a = field + constructor
public abstract class BurgerDecorator
    implements Burger {
  protected final Burger burger;   // field
  public BurgerDecorator(Burger b) {
    burger = b; }                  // set it
}

// MOVE 4: delegate = call the field, add
public double getCost() {
  return burger.getCost() + 150; }
// MOVE 5: extends + super(...)
public class Cheese extends BurgerDecorator {
  public Cheese(Burger b) { super(b); }
  // ... override getCost() with MOVE 4
}

// MOVE 6: a fixed order you can't change
public abstract class Process {
  public final void run() {   // final!
    stepOne(); stepTwo(); }
  protected abstract void stepTwo();
  private void stepOne() { }
}

// MOVE 7: only one object
public final class Logger {
  private static Logger instance;
  private Logger() { }        // private!
  public static synchronized Logger
      getInstance() {
    if (instance == null)
      instance = new Logger();
    return instance; }
}

Which moves each pattern uses

Singleton7Decorator1, 2, 3, 4, 5
Factory1, 2 + a switch that returns new …Template6, 5
Facade3 (several fields), 4 (call them in order)Chain3 (field next), 4 (pass to next), 5
Adapter1, 2, 3, 4 (call the adaptee's method)State1, 2, 3 (field state), 4 (state.event(this))
Proxy1, 2, 3, 4 (check first, then call)

// SINGLETON (rename: Singleton -> your class)
public final class Singleton {
  private static Singleton instance;  // one copy
  private final Map<String, String> data =
      new HashMap<>();                // shared

  private Singleton() { }             // no "new"

  public static synchronized Singleton
      getInstance() {
    if (instance == null)
      instance = new Singleton();
    return instance;
  }
  public synchronized void operation(String k,
                                     String v) {
    data.put(k, v); }
}
// CLIENT: never "new", always getInstance()
Singleton s = Singleton.getInstance();
s.operation("P01", "10:30");

"Maximum N" instead of one?

That's a Multiton: same three ingredients, but the static field is a List or Map, and the static method refuses (or reuses) once it holds N objects. Note tab 01 has the cricket version.

Check before moving on

☐ constructor private
☐ instance static and underlined in the diagram
☐ getInstance() static, underlined
☐ clients call getInstance(), never new
☐ said "thread-safe" (synchronized) in the text

// PRODUCT
public interface Product {
  void operation(String msg);
}
// CONCRETE PRODUCT (one per listed kind)
public class ProductA implements Product {
  public void operation(String msg) {
    System.out.println("A: " + msg); }

  public void operation(String msg) {
    System.out.println("B: " + msg); }
}
// FACTORY: the only place with "new"

      case "B": return new ProductB();

    }
  }
}

p.operation("Hello");    // A: Hello

RoleFind it in the question by…Example
Target «interface»what your system already calls (the old method) → make it an interfaceThermometer with getTemperature()
Adapteethe new / legacy / vendor class you can't change, with its different methodVendorSensor with readCelsius()

Test: Target method = old name. Adaptee method = new name. Inside the adapter, the old name calls the new name.

Skeleton diagram

adapter implements the target and holds the adaptee
// TARGET: what the client already uses
public interface Target {
  double oldMethod();
}
// ADAPTEE: vendor class, can't change it
public class Adaptee {
  public double newMethod() {
    return 24.5; }
}
// CLIENT: only the creation line changes
Target t = new Adapter(new Adaptee());
double v = t.oldMethod(); // old calls stay
// ADAPTER: is a Target, has an Adaptee
public class Adapter implements Target {
  private final Adaptee adaptee;
  public Adapter(Adaptee a) {
    this.adaptee = a; }

  public double oldMethod() {
    // translate: old call -> new call
    // (convert units / format here too)
    return adaptee.newMethod();
  }
}

Check

☐ adapter implements Target (dashed triangle) ☐ adapter has an Adaptee field (solid arrow) ☐ adaptee untouched ☐ the old method's body calls the new method ☐ named all four participants in words

Skeleton diagram

// SUBJECT
public interface Subject {
  void request(String user);
}
// REAL SUBJECT: the real / costly work
public class RealSubject implements Subject {
  public RealSubject() {
    System.out.println("Loading..."); }
  public void request(String user) {
    System.out.println("Serving " + user); }
}
// CLIENT: can't tell it's a proxy
Subject s = new Proxy();
s.request("S001");
// PROXY: same interface, check first
public class Proxy implements Subject {
  private RealSubject real;    // null at first

  public void request(String user) {
    if (!allowed(user)) {      // protection
      System.out.println("Denied");
      return; }
    if (real == null)          // virtual (lazy)
      real = new RealSubject();
    real.request(user);        // forward
  }
  private boolean allowed(String user) {
    return user.startsWith("S"); } // STUB
}

Check

☐ proxy and real both implement the same interface ☐ arrow proxy → real (never the other way) ☐ client holds the interface type ☐ named the proxy type (protection / virtual / logging) ☐ check happens before the forward

// ABSTRACT CLASS: owns the order
public abstract class AbstractClass {
  public final void templateMethod() {
    commonStep1();      // same for all

  }

  protected void varyingStep() {
    System.out.println("B's way"); }
}
// CLIENT: calls only the template method

the "next" link is ONE loop on the abstract handler, not arrows between concrete handlers
// HANDLER
public abstract class Handler {
  private Handler next;
  public Handler setNext(Handler n) {
    next = n; return n; } // lets you chain

  public void handle(Request r) {
    if (canHandle(r)) process(r);      // me
    else if (next != null) next.handle(r);
  }
  protected abstract boolean
      canHandle(Request r);
  protected abstract void process(Request r);
}
// Request: a class with the deciding value,
// e.g. LeaveRequest with an int days field
// CONCRETE HANDLER (one per level)
public class LevelOne extends Handler {
  protected boolean canHandle(Request r) {
    return r.getValue() <= 2; }
  protected void process(Request r) {
    System.out.println("Level one"); }
}
// LevelTwo: value <= 7 · LevelThree: true

// CLIENT: build once, send to the first
Handler h = new LevelOne();
h.setNext(new LevelTwo())
 .setNext(new LevelThree());
h.handle(new Request(5));  // Level two

"Checks in order" questions (validation, filters: every check must pass): make handle() return boolean: if (!check(r)) return false; return next == null || next.handle(r); with one abstract check(r). Levels / approvals / priorities: use the code above.

Check: ☐ next field on the abstract handler (self-loop in UML) ☐ next != null check ☐ last handler is a fallback ☐ client only calls the first handler ☐ concretes extend (solid triangle)

public interface State {
  void eventOne(Context c);
  void eventTwo(Context c);

public class Context {

Drawing rules

  1. Draw top to bottom: clients → gateway → services → databases → broker.
  2. Every client arrow goes into the gateway, never straight to a service.
  3. One database under each service. No database is joined to two services.
  4. Label the gateway with its jobs: auth check, routing, rate limiting.
  5. Label at least one event on the broker with a real name from the scenario.
  6. External systems in dashed boxes at the edge, joined to the one service that uses them.
  7. Shared infrastructure as a row of small boxes with "used by every service".

4 mClients, gateway, the services with their own DBs, broker.
5 m+ labelled event(s), auth service, the external systems, the infrastructure row.
