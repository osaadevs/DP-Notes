What these papers are built on

  • All four questions are case-based, and a single case asks about two or more patterns, spread across the whole question rather than saved for the last part (exam briefing).
  • The shape of the past papers: identify the patterns with reasons → diagram → short Java → a follow-up part (challenges, HA/DR, SOLID, how two patterns connect).
  • Question 2 is microservices in every paper, because 2023, 2024 and 2025 all had it.
  • Scenarios the past papers haven't used yet: food delivery, smart home, online exams, ride-hailing, insurance, banking, EV charging, airline, hotel, returns.

How to practise do it like the real thing

  1. Time it. 2½ hours for 4 questions. Give each question about 35 minutes and move on when the time is up, even mid-answer. The lecturer's biggest warning: students write long first answers and run out of time for the last ones.
  2. Use only what you'll take in: the printed exam note and the past-papers booklet. The point is to check whether you can find things fast. Mark any page you had to hunt for.
  3. Start from the case, not the theory. First sentence: what the case needs ("The kiosk behaves differently in each state, so…"). Then name the pattern and give reasons tied to the case. Don't write everything you know about the pattern.
  4. Write something for every part. A name plus one reason earns more than a blank.
  5. Mark yourself with the answers booklet. Note what you missed, not just whether the pattern name was right.

How to mark yourself

  1. Pattern named correctly with its group: about a third of the marks for an "identify" part.
  2. Reasons tied to the case (not general theory): most of the rest. "Each state is a class, so pay() is refused in Idle" scores; "State is a behavioural pattern from GoF" alone does not.
  3. Diagrams: correct arrows, stereotypes and +/−/# matter more than neatness.
  4. Code: the exact interface and method names from the question, and it must compile in spirit.
  5. Where another pattern is reasonable, the answer says so. If you chose it and justified it from the case, give yourself the marks.

QUESTION 1 · 25 MARKS QuickBite is a food delivery app. A customer's order moves through these stages: Placed → Confirmed by the restaurant → Preparing → Out for delivery → Delivered. An order can be Cancelled only before it is out for delivery. What a customer can do (cancel, track, rate) depends on the current stage.
QuickBite works with many restaurants. Each restaurant already uses its own point-of-sale system from a different vendor: one accepts orders through pushOrder(xml), another through createTicket(json). QuickBite cannot change these systems.
When a customer taps "Place order", the app must check the restaurant, take the payment, assign a rider and send notifications. The mobile team wants one simple call for this instead of talking to four services.
1.1Identify a suitable design pattern, with reasons, for each of: (a) the order stages, (b) sending orders to the restaurants' different systems, (c) the single "Place order" call.6 marks
(a) order stagesStateThe order behaves differently in each stage: cancel is allowed while Placed, Confirmed or Preparing but refused once out for delivery; rating only works after Delivered. Each stage becomes a class that knows its allowed actions and its next stage, so there are no if/else checks on a status field.
(b) restaurant systemsAdapterThe restaurants' systems have incompatible methods and can't be changed. One adapter per vendor converts QuickBite's sendOrder(order) into pushOrder(xml) or createTicket(json); a new vendor is just a new adapter.
(c) one "Place order"FacadeOrderFacade.placeOrder() calls restaurant check → payment → rider → notification in the right order, so the mobile app depends on one class instead of four services.
1.2Draw a state diagram for an order.5 marks

Marks: start dot, every state, each arrow labelled with its event, cancel only from the first three, end states shown.

1.5Give one challenge of the "Place order" design in (c) and how you would overcome it.3 marks

QUESTION 2 · 25 MARKS A private hospital group with five branches wants a new system built as microservices. Key functional requirements: Patient management (register patients, medical history, profiles) · Appointments (book, reschedule, cancel channelling sessions with doctors) · Doctors & staff (schedules, availability, specialities) · Pharmacy (prescriptions, stock, dispensing) · Laboratory (test orders and results) · Billing (invoices, insurance claims, payments) · Notifications (SMS reminders, results ready).
2.1Draw a diagram to depict the microservices scenario.5 marks
2.2How can the hospital implement and manage this architecture to achieve scalability, fault isolation and continuous deployment?5 marks
ScalabilityScale each service on its own: Appointments peaks in the morning when channelling opens, so it auto-scales; Lab and Pharmacy scale per branch; Billing stays small. Stateless services on Kubernetes with auto-scaling and caching of doctor schedules.
Fault isolationEach service has its own process and database. If Notification fails, appointments are still booked and SMS messages wait in the queue; if Billing is down, doctors still see patients. Circuit breakers, timeouts, retries, bulkheads.
Continuous deploymentA repository and CI/CD pipeline per service, automated tests, Docker images, blue-green releases at night, versioned APIs, so Pharmacy can be updated without touching Appointments.
Manage itAPI gateway, service registry, config server, central logging, metrics and tracing; one team per service.
2.3Propose a suitable microservices architecture.5 marks

One service per capability, each with its own database: Patient, Appointment, Doctor/Staff, Pharmacy, Laboratory, Billing (with an insurance adapter), Notification. Web portal, mobile app and branch counters go through an API gateway (authentication, routing). Services use REST when they need an answer now (Appointment asks Doctor "is Dr. Perera free at 10:00?") and publish events to a message broker otherwise ("LabResultReady" → Notification sends an SMS; "PrescriptionIssued" → Pharmacy prepares it). Containers on Kubernetes across the branches, plus a service registry, config server and monitoring.

2.4What methods can maintain data consistency across the services?5 marks
  • Database per service, so no shared transactions; accept eventual consistency where safe (notification history).
  • Saga for an appointment: reserve the doctor's slot → take the booking fee → confirm. If payment fails, a compensating action frees the slot.
  • Events through a broker with a transactional outbox and idempotent consumers, so a repeated "PrescriptionIssued" doesn't dispense twice.
  • CQRS read models for a patient's full history view; stronger consistency for medication stock and billing.
2.5How would you secure patient data and communication between services?5 marks
  • Users: OAuth2 / OpenID Connect at the gateway with JWT; strict roles (doctor, nurse, pharmacist, cashier, patient), so a cashier can't read lab results.
  • Patient data: encrypted at rest and in transit, access to records logged (audit trail), data kept to health-data privacy rules, secrets in a vault.
  • Service to service: mutual TLS (service mesh), short-lived tokens, least-privilege database users per service.
  • Rate limiting, input validation, a web application firewall, and alerts on unusual access (one user opening hundreds of records).
QUESTION 3 · 25 MARKS A company builds a smart home app. Homes have lights, door locks, air conditioners and cameras from different manufacturers; some speak Zigbee (zbSwitch(id, on)), others Bluetooth (btWrite(mac, cmd)), and the app can't change the devices' software.

3.3Write Java for the component that stops guests controlling anything except lights.5 marks
public interface Device {
  String getType();       // "LIGHT", "LOCK"…
  void turnOn();
  void turnOff();
}
public class DeviceProxy implements Device {
  private final Device real;
  private final User user;
  public DeviceProxy(Device d, User u) {
    real = d; user = u; }
  public String getType() {
    return real.getType(); }
  public void turnOn() {
    check();
    AuditLog.record(user, real, "ON");
    real.turnOn();
  }
  public void turnOff() {
    check();
    AuditLog.record(user, real, "OFF");
    real.turnOff();
  }
  private void check() {
    if (user.isGuest()
        && !real.getType().equals("LIGHT"))
      throw new AccessDeniedException(
          "Guests can only control lights");
  }
}
3.4Explain which SOLID principles your design follows.5 marks
  • Single Responsibility: each adapter only translates for one vendor; the proxy only checks access; the facade only coordinates.
  • Open/Closed: a new device brand is a new adapter, and a new scene ("Night mode") is a new facade method; existing classes don't change.
  • Liskov Substitution: a DeviceProxy or any adapter can be used anywhere a Device is expected.
  • Interface Segregation: Device is small; a camera-only action (arm()) goes in a separate Armable interface rather than forcing lights to implement it.
  • Dependency Inversion: the facade and hub depend on the Device abstraction, not on Zigbee or Bluetooth classes.
QUESTION 4 · 25 MARKS A university's online exam platform runs every exam through the same process: authenticate the student → load the paper → conduct the exam → evaluate → publish results. Evaluation differs by exam type: MCQ exams are auto-marked, essay exams are marked by a lecturer with a rubric, and programming exams run hidden test cases.
Question objects (MCQ, essay, coding) are created depending on what the lecturer adds. When a student submits, the answer script goes through checks in order: time limit → file format → plagiarism; more checks will be added later.
Departments may switch on optional proctoring features (webcam monitoring, screen recording, AI flagging) for any exam, in any combination.
4.1Identify suitable patterns, with reasons, for: (a) the common exam process, (b) creating question objects, (c) submission checks, (d) optional proctoring features.8 marks
(a) exam processTemplate MethodThe five steps are fixed in a final runExam(); only evaluate() differs, so the order is enforced and the common steps are written once.
(b) question objectsFactory MethodQuestionFactory.create(type) returns MCQ, Essay or Coding questions, so the editor never uses new and new types are easy to add.
(c) submission checksChain of ResponsibilityTime limit → format → plagiarism as linked handlers; any failure stops it; more checks are one class and one link each.
(d) proctoringDecoratorEach feature wraps the exam session and adds its monitoring, in any combination at runtime, without a subclass per mix.
4.2Write the abstract class for the exam process using the pattern from (a).5 marks
public abstract class ExamProcess {
    public final void runExam(Student s) {      // template method: order is fixed
        if (!authenticate(s)) return;
        Paper p = loadPaper();
        Script script = conduct(s, p);
        double mark = evaluate(script);             // the step that differs
        publish(s, mark);
    }
    private boolean authenticate(Student s) { return Auth.verify(s); }   // common
    private Paper loadPaper() { return PaperStore.current(); }       // common
    protected Script conduct(Student s, Paper p) { return Exam.run(s, p); } // hook
    protected abstract double evaluate(Script script);
    private void publish(Student s, double m) { Results.save(s, m); }  // common
}
4.3Write a ProgrammingExam subclass.3 marks
public class ProgrammingExam extends ExamProcess {
    protected double evaluate(Script script) {
        int passed = TestRunner.runHiddenTests(script.getCode());
        return passed * 100.0 / TestRunner.TOTAL;      // percentage of tests passed
    }
}
4.4Outline how the submission checks would be implemented so new checks can be added easily.5 marks

An abstract SubmissionCheck holds a next link and a check(script) method. TimeLimitCheck, FormatCheck and PlagiarismCheck each test one thing. The chain is built once (cheap checks first, the expensive plagiarism scan last) and every submission goes to the first check. A failure stops the chain with a reason ("submitted 3 minutes late"); passing all means the script is accepted. A new rule (e.g. WordCountCheck) is one new class added with one link; nothing else changes.

abstract class SubmissionCheck {
  private SubmissionCheck next;
  SubmissionCheck then(SubmissionCheck n) {
    next = n; return n; }
  boolean check(Script s) {
    if (!test(s)) return false;
    return next == null || next.check(s);
  }
  abstract boolean test(Script s);
}
SubmissionCheck c = new TimeLimitCheck();
c.then(new FormatCheck())
 .then(new PlagiarismCheck());
4.5Explain how the proctoring features can be added without changing the existing exam classes.4 marks

Use the Decorator pattern. An ExamSession interface (start(), end()) is implemented by BasicExamSession. An abstract ProctoringDecorator implements ExamSession and holds the session it wraps. WebcamMonitor, ScreenRecorder and AiFlagging each add their own behaviour in start()/end() and then call the wrapped session. A department that wants webcam + AI flagging gets new AiFlagging(new WebcamMonitor(new BasicExamSession())). No exam class changes, and a new feature is one new decorator (Open/Closed).

QUESTION 1 · 25 MARKS GoLanka is a ride-hailing app. A trip goes from Requested → Driver assigned → In progress → Completed. A trip can be Cancelled while Requested or Driver assigned, but not once it is in progress. 1.1Identify suitable design patterns, with reasons, for: (a) trip stages, (b) creating vehicle types, (c) fare extras, (d) the shared current rates.8 marks
(a) trip stagesStateCancel is allowed only in the first two stages, and "start trip" only after a driver is assigned. Each stage is a class with its own rules and next stage, so there is no if/else on a status field.

1.4Explain how the shared rates object is created and used safely when many requests arrive at the same time.6 marks

FareConfig is a Singleton: private constructor, a private static volatile instance, and a public static getInstance() using double-checked locking, so two threads arriving at once can't create two objects. The rates themselves are held in thread-safe fields (volatile, or an AtomicReference to an immutable Rates object), so a reader never sees half an update. The operations team updates the rates through update(), which swaps in a new object in one step. Every SurgeCharge and NightCharge decorator reads FareConfig.getInstance() when it calculates, so every fare uses the same current values.

public final class FareConfig {
  private static volatile FareConfig inst;
  private volatile Rates rates =
      Rates.loadFromDb();
  private FareConfig() { }
  public static FareConfig getInstance() {
    if (inst == null) {
      synchronized (FareConfig.class) {
        if (inst == null)
          inst = new FareConfig();
      }
    }
    return inst;
  }
  public double nightRate() {
    return rates.night; }
  public void update(Rates r) {
    rates = r; }     // one atomic swap
}
QUESTION 2 · 25 MARKS A bank is replacing its core online banking system with microservices. Key functional requirements: Customer management (KYC, profiles, login devices) · Accounts (savings, current, fixed deposits, balances) · Transactions (transfers between accounts and to other banks, bill payments) · Loans (applications, approvals, repayment schedules) · Fraud detection (real-time checks on transactions) · Notifications (SMS/email alerts for every transaction).
2.1Draw a diagram to depict the scenario.5 marks
2.2How can the bank implement and manage microservices to achieve scalability, fault isolation and continuous deployment?5 marks
ScalabilityTransactions and Fraud carry the load on salary day and month-end, so they auto-scale independently; Loans stays small. Stateless services on Kubernetes; balance reads cached.
Fault isolationOwn process and database per service. If Notification fails, transfers still work and alerts queue up; if the Loans service fails, payments are unaffected. Circuit breakers, timeouts, bulkheads; a fraud-check timeout falls back to a safe rule (hold large transfers).
Continuous deploymentPipeline per service with automated and security tests, canary releases to a small share of customers, versioned APIs, quick rollback. Changes are audited for regulators.

2.3Propose a suitable microservices architecture.5 marks

Services, each with its own database: Customer (KYC, devices), Account (balances, account types), Transaction (transfers, bill payments; talks to other banks through a CEFTS/SWIFT adapter), Loan, Fraud (real-time scoring, ML), Notification. Mobile and web banking go through an API gateway with strong authentication. Kubernetes, service mesh, registry, config and monitoring, deployed across two data centres.

2.4How would you maintain data consistency, especially for money transfers?5 marks
  • Database per service, so no distributed transactions across services by default.
  • Saga for a transfer: debit the sender → credit the receiver → record the transaction. If the credit fails, a compensating action reverses the debit. An orchestrator in the Transaction service tracks each step.
  • Idempotency keys on every transfer request, so a retried request never debits twice; a transactional outbox for events.
  • Money movements inside one account database use normal ACID transactions; balances are strongly consistent, while alerts and statements are eventually consistent.
  • Daily reconciliation jobs to catch any mismatch.
2.5How would you secure customer data and service-to-service communication?5 marks
  • Customers: OAuth2 / OpenID Connect with multi-factor authentication (OTP), device binding, short-lived JWTs, automatic logout.
  • Data: encryption at rest and in transit, card data to PCI-DSS, keys in a hardware security module or vault, data masking in logs.
  • Service to service: mutual TLS through a service mesh, least privilege per service (Notification can't read balances).
  • Monitoring: rate limits, a WAF, fraud alerts, full audit trail for regulators.

3.3Write Java showing how a claim of Rs. 750,000 is processed through the approval levels.6 marks
public abstract class Approver {
  protected Approver next;
  private final double limit;
  protected Approver(double limit) {
    this.limit = limit; }
  public Approver setNext(Approver n) {
    next = n; return n; }

  public void approve(Claim c) {
    if (c.getAmount() <= limit) {
      System.out.println(getClass()
        .getSimpleName() + " approved "
        + c.getAmount());
    } else if (next != null) {
      next.approve(c);     // pass it up
    }
  }
}
class Agent extends Approver {
  Agent() { super(50_000); } }
class Supervisor extends Approver {
  Supervisor() { super(500_000); } }
class Manager extends Approver {
  Manager() { super(2_000_000); } }
class ClaimsBoard extends Approver {
  ClaimsBoard() {
    super(Double.MAX_VALUE); } } // fallback

// client
Approver chain = new Agent();
chain.setNext(new Supervisor())
     .setNext(new Manager())
     .setNext(new ClaimsBoard());
chain.approve(new Claim(750_000));
// Agent: no → Supervisor: no
// → "Manager approved 750000.0"
3.4Every approval level must log the claim, record its decision and log the result. How would you enforce this?3 marks

Combine Template Method with the chain: make approve() in Approver final and have it call logReceived() → decide(c) (abstract, written by each level) → logResult(), then pass the claim on if not approved. Levels only write decide(), so none can skip the logging.

3.5Show how the claims system can pay through the mainframe without changing either system.4 marks

Adapter. PaymentService is the target interface the claims system already uses. MainframePaymentAdapter implements it, holds the mainframe client (adaptee), and translates: rupees → cents, claim → account number and reference code, and the mainframe's return code → an exception on failure. The pay() step in the template calls paymentService.pay(c) and never sees the mainframe.

class MainframePaymentAdapter
      implements PaymentService {
  private final Mainframe mf;
  public void pay(Claim c) {
    long cents =
      Math.round(c.getAmount() * 100);
    int rc = mf.TRNPAY(c.getAccountNo(),
                       cents, c.getRef());
    if (rc != 0) throw new
      PaymentException("code " + rc);
  }
}
QUESTION 4 · 25 MARKSFor each case, explain the design pattern you would suggest and why, and give a simple class diagram or code outline.
4.1A hospital system: patient records must only be opened by doctors and nurses assigned to that patient, and every access must be recorded.5 marks

Protection Proxy (structural). PatientRecordProxy implements the same PatientRecord interface as the real record. view() first checks the user's role and whether they are assigned to the patient, writes an audit entry, and only then forwards to the real record; otherwise it refuses. Reasons: sensitive data is never reached directly; the security rule is in one place; the record class stays free of security code.

4.2A reporting module exports the same report as PDF, Excel or CSV, depending on what the user selects; more formats will be added.5 marks

Factory Method (creational). A ReportExporter interface with export(report); PdfExporter, ExcelExporter and CsvExporter implement it. ExporterFactory.create(format) returns the right one from the user's choice. Reasons: the report screen depends only on the interface, creation logic is in one place, and a new format (JSON) is one new class.

class ExporterFactory {
  static ReportExporter create(String f) {
    switch (f) {
      case "PDF":   return new PdfExporter();
      case "EXCEL":
        return new ExcelExporter();
      case "CSV":   return new CsvExporter();
      default: throw new
        IllegalArgumentException(f);
    }
  }
}
4.3A vending machine behaves differently when it is idle, has a coin inserted, is dispensing, or is out of stock.5 marks

State (behavioural). VendingMachine (context) holds a MachineState; IdleState, HasCoinState, DispensingState and OutOfStockState implement insertCoin(), selectItem(), dispense() and refund(). Inserting a coin in Idle moves to HasCoin; in OutOfStock the coin is refunded. Reasons: the same button behaves differently by state, the if/else on a status flag disappears, and each state controls its own transitions. Stateless states can be shared Singletons.

4.3Outline how the return checks would be implemented.5 marks

An abstract ReturnCheck holds a link to the next check and a check(request) that returns a failure reason or passes the request on. ReceiptCheck, WithinDaysCheck, ConditionCheck and RefundLimitCheck each test one thing. The chain is built once (the order can come from configuration) and every request goes to the first check. If all pass, the refund process from 4.2 starts. A new rule, such as SerialNumberCheck for electronics, is one new class with one link.

abstract class ReturnCheck {
  private ReturnCheck next;
  ReturnCheck then(ReturnCheck n) {
    next = n; return n; }
  String check(ReturnRequest r) {
    String fail = test(r);
    if (fail != null) return fail;
    return next == null ? null
                        : next.check(r);
  }
  abstract String test(ReturnRequest r);
}
class WithinDaysCheck extends ReturnCheck {
  String test(ReturnRequest r) {
    return r.daysSincePurchase() <= 14
        ? null : "Older than 14 days"; }
}
4.4Write the audit log class and explain why it prevents duplicate or out-of-order entries.4 marks
public final class AuditLogger {
  private static final AuditLogger
      INSTANCE = new AuditLogger();
  private final AtomicLong seq =
      new AtomicLong();
  private AuditLogger() { }
  public static AuditLogger getInstance() {
    return INSTANCE; }
  public synchronized void log(String e) {
    AuditStore.append(
        seq.incrementAndGet(), e);
  }
}

The private constructor means no other logger object can exist; every refund calls the same getInstance(). Because there is one object, there is one writer and one sequence counter, and log() is synchronized, so two refunds at the same moment are written one after the other with increasing sequence numbers, never twice and never interleaved. (For several servers, AuditStore is a replicated, append-only store.)

4.5How would you extend the design for High Availability and Disaster Recovery?5 marks

HA: the check chain and refund classes keep no state, so the returns service runs as several copies behind a load balancer, with health checks and automatic restart (Kubernetes). Requests go through a message queue so none are lost if a copy dies. The database is replicated with automatic failover. Each server's Singleton logger writes to a shared, replicated audit store, so the logger isn't a single point of failure, and a refund is made idempotent (refund ID checked) so a retry never pays twice. DR: regular backups, the database and audit log replicated to a second region, agreed RPO/RTO, automated failover, infrastructure-as-code to rebuild, and regular DR drills.
