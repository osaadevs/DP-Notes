Decorator

Add optional extras by wrapping the object — no subclass per combination.
Structural · Understand
Spot it — the question says…
optional add-ons / extras / toppingswithout subclasses for every combinationprice depends on base + selected additionsinstead of modifying the classstudents may optionally addbloated class with optional features

The idea in one picture

Why not just use subclasses?

Every combination needs its own class (EspressoWithMilkAndSugar ✗) = class explosion:

3 add-ons → 8 · 10 → 1,024 · 15 → 32,768 (2ⁿ)

Decorator builds the combination at runtime with objects, not at compile time with classes.

The 4th part, the abstract Decorator, is always <Component>Decorator — it is-a and has-a Component.

Don't confuse it

  • vs Proxy — same interface, but Proxy controls (1 layer); Decorator adds (many layers).
  • vs Adapter — Adapter changes the interface; Decorator keeps it.
  • vs Inheritance — compile time, rigid vs runtime, flexible.

Common mistakes lose marks

  • Decorator does not implement the Component interface
  • Decorator creates its own base instead of receiving it in the constructor
  • Forgets to delegate → loses earlier add-ons
  • Draws inheritance instead of has-a (◇) to the Component

Decorator — Write

Copy-ready blocks. Swap the bold names for the ones in your question.
Structural · Write

W1 Name it + why 2–6 marks

The Decorator design pattern (structural) is suitable. It attaches additional responsibilities to an object dynamically by wrapping it, giving a flexible alternative to subclassing.
Reasons (pick 2–4):
  • No class explosion — n add-ons would need 2ⁿ subclasses; here, one class per add-on.
  • Runtime flexibility — the customer chooses add-ons while ordering; any mix, any order.
  • Open/Closed — a new add-on is a new class; the base and existing add-ons stay unchanged.
  • Single Responsibility — each decorator adds one thing (price + description).
Map it to the scenario (where the marks are):
  • Component = Coffee «interface»
  • Concrete component = BasicCoffee
  • Decorator = CoffeeDecorator «abstract»
  • Concrete decorators = Milk, Sugar, Chocolate

W2 Class diagram 5–8 marks · draw exactly this shape

W3 · Java — copy in this order · 5 + 5 marks 
// 1. COMPONENT — the interface they ask you to "define"
public interface Coffee {
    String getDescription();
    double getCost();
}
// 2. CONCRETE COMPONENT — the "basic" class
public class BasicCoffee implements Coffee {
    public String getDescription() { return "Basic coffee"; }
    public double getCost() { return 200.0; }
}
// 3. ABSTRACT DECORATOR — is-a AND has-a Coffee
public abstract class CoffeeDecorator implements Coffee {
    protected Coffee coffee;              // wrapped
    public CoffeeDecorator(Coffee c) { coffee = c; }
    public String getDescription() { return coffee.getDescription(); }
    public double getCost() { return coffee.getCost(); }
}
// 4. CONCRETE DECORATOR — add, then delegate
public class Milk extends CoffeeDecorator {
    public Milk(Coffee c) { super(c); }
    public String getDescription() {
        return coffee.getDescription() + ", Milk"; }
    public double getCost() { return coffee.getCost() + 80; }
}   // Sugar (+20), Chocolate (+120): same shape

// 5. CLIENT — wrap at runtime
Coffee c = new BasicCoffee();
c = new Milk(c);
c = new Sugar(c);
System.out.println(c.getDescription()); // Basic coffee, Milk, Sugar
System.out.println(c.getCost());        // 300.0

W4 "Different profit?" 5m

A — add getProfit() to the interface; each class adds its margin.
B (better, OCP) — a new decorator; nothing existing changes:

class ProfitMargin
    extends CoffeeDecorator {
  double rate;
  ProfitMargin(Coffee c, double r)
    { super(c); rate = r; }
  public double getCost() {
    return coffee.getCost()
           * (1 + rate); }
}

W5 Challenges → fix 3–4m

  • Complexity (many small classes) → one decorator = one job; a builder assembles common combos.
  • Debugging through layers → log in each decorator; unit-test each alone.
  • Order matters (discount→tax ≠ tax→discount) → fix the wrapping order in the builder.
  • Performance (extra objects) → negligible for short chains; cache the cost.
  • Readability (new A(new B(x))) → builder, clear names, docs.

2 Scalability · fault isolation · CD 5m

  • Scalability — each service scales independently (horizontal pods, auto-scale on CPU/requests). Scale the busy one (e.g. Content / Search), not Billing. Stateless services; cache/CDN.
  • Fault isolation — own process + own DB; circuit breaker, timeouts, retries with back-off, bulkheads; graceful degradation (Recommendations down → show popular list).
  • Continuous deployment — own repo + CI/CD pipeline per service, automated tests, Docker images, blue-green / canary, versioned APIs; one team per service.

3 Propose the architecture 4–5m

  • One service per business capability (list yours from the table) — own codebase, own DB, own deployment.
  • API Gateway as single entry; service registry for discovery.
  • Sync: REST/gRPC. Async: events through the message broker.
  • Containers on Kubernetes; central config, logging, monitoring.

4 Data consistency 4–5m

  • Database per service ⇒ no shared transactions ⇒ eventual consistency.
  • Saga pattern — local transactions + compensating actions (e.g. payment fails → cancel borrow). Choreography (events) or orchestration.
  • Transactional outbox + idempotent consumers; CQRS for read models (search).
  • Two-phase commit only where strong consistency is critical (rare).

5 Security 4–5m

  • Users: OAuth2 / OpenID Connect at the gateway, JWT tokens, role-based access (RBAC).
  • Service-to-service: mutual TLS, service mesh, short-lived tokens.
  • Data: HTTPS everywhere, encrypt at rest (PCI-DSS for payments), secrets vault, least-privilege DB access.
  • Rate limiting, input validation, WAF, audit logging.
2023 extra — "Why same hardware/config for each platform?" Consistent environments (containers / infrastructure-as-code) ⇒ predictable deployment, scaling and failover; any node runs any service; easier capacity planning, monitoring, troubleshooting and DR rebuild. Exception: GPU nodes for ML services.
