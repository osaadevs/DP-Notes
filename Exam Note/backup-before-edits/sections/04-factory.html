Factory Method

One place decides which class to create. The rest of the code just asks for "a database" or "a book".
Creational
Understand

Spot it: the question says…

create different types of X depending on the user's requestdifferent types of accounts / books / payments supports MySQL, PostgreSQL and MongoDBtoo many if-else blocks to create objects without exposing the concrete classscalable, extensible product-based frameworkmodules created depending on the user's needs

The idea

When the program needs one of several related types, the code that uses the object shouldn't have to know which class to new. A factory takes the request ("MYSQL", "FICTION", "CARD") and hands back the right object, typed as the common interface.

Like ordering at a restaurant: you ask for "a pizza", and the kitchen decides how to make it. You never go into the kitchen.

The problem it removes

// BEFORE: copied all over the client
if (type.equals("MYSQL"))
    db = new MySQLDatabase();
else if (type.equals("MONGO"))
    db = new MongoDatabase();
// new database = edit every copy

// AFTER: one line, interface only
Database db =
    DatabaseFactory.getDatabase(type);

Don't mix it up

  • vs Singleton: Factory decides which type; Singleton decides how many (one). Often used together: the factory or the connection it creates is a Singleton.
  • vs Facade: Factory creates objects. Facade coordinates objects that already exist.
  • vs Abstract Factory: Abstract Factory creates whole families of related objects (e.g. a Windows button + Windows menu). Not taught in detail.

Why is new in the client bad?

It hard-codes the concrete class. Every new type forces a change in the client, which breaks Open/Closed, and the client depends on details instead of an abstraction, which breaks Dependency Inversion. The factory also separates creating from using (Single Responsibility).

W1 Name it and say why 2–5 marks

I would use the Factory Method pattern, which is a creational pattern. It defines an interface for creating an object but lets the factory (or a subclass) decide which class to instantiate, so the client never uses new on a concrete class.

Reasons: (1) loose coupling, because the client depends only on the Database interface, not on MySQL or MongoDB classes; (2) the creation logic is in one place instead of if-else copied across the code; (3) it is easy to extend (Open/Closed): a new type is one new class and one new case, and client code doesn't change.

Mapping: Product = Database «interface» · concrete products = MySQLDatabase, PostgreSQLDatabase, MongoDatabase · factory = DatabaseFactory.getDatabase(type) · client = ProductService.

W2 Class diagram

dashed «create» arrows from the factory; dashed triangles to the interface
W3 · Java
// 1. PRODUCT
public interface Database {
    void connect();
    void create(Product p);
}
// 2. CONCRETE PRODUCTS
public class MySQLDatabase
        implements Database {
    public void connect() {
        /* open MySQL connection */ }
    public void create(Product p) {
        /* INSERT into MySQL */ }
}
// PostgreSQLDatabase, MongoDatabase:
// same shape
// 3. FACTORY: the only place with "new"
public class DatabaseFactory {
  public static Database getDatabase(
          String type) {
    switch (type.toUpperCase()) {
      case "MYSQL": return new MySQLDatabase();
      case "POSTGRES":
          return new PostgreSQLDatabase();
      case "MONGO": return new MongoDatabase();
      default: throw new
        IllegalArgumentException(type);
    }
  }
}
// 4. CLIENT: knows only the interface
Database db =
    DatabaseFactory.getDatabase("MYSQL");
db.create(product);

Database objects Quiz 2 Q1–Q3

Role of the factoryIt takes object creation out of the client. The client asks DatabaseFactory.getDatabase("MYSQL") and receives a Database. The factory decides and creates MySQL, PostgreSQL or Mongo.
Two advantages(1) Loose coupling: switching from MySQL to PostgreSQL changes only the parameter or config, not the business code. (2) Easy to extend: adding Oracle is one new class and one new case, and the creation logic stays in one place.
Why the developer doesn't need to know the DBBecause of abstraction and polymorphism. The variable's type is the Database interface, and every database implements connect() and create(). The factory returns the right object at runtime, and db.create(product) runs the right version automatically.

Library book types: Book interface + BookFactory 2025 Q3.2–3.3, 7m

public interface Book {
    String getTitle();
    String getCategory();
}
public class FictionBook implements Book {
    private String title;
    public FictionBook(String t) {
        title = t; }
    public String getTitle() {
        return title; }
    public String getCategory() {
        return "Fiction"; }
}
// ResearchBook, Magazine: same shape
public class BookFactory {
  public static Book createBook(
          String type, String title) {
    switch (type) {
      case "FICTION":
          return new FictionBook(title);
      case "RESEARCH":
          return new ResearchBook(title);
      case "MAGAZINE":
          return new Magazine(title);
      default: throw new
          IllegalArgumentException(type);
    }
  }
}
// client
Book b = BookFactory.createBook(
        "RESEARCH", "AI Ethics");

Bank accounts 2023 Q4.2, 5m

Factory Method. An Account interface (or abstract class) with deposit(), withdraw() and calculateInterest(). CurrentAccount, SavingAccount and ChildrenAccount implement it with their own rules (overdraft, interest, withdrawal limit). AccountFactory.createAccount(type) returns the right one. The bank code only uses Account, so a new FixedDeposit account can be added without touching it.

Payment objects 2025 Q4.1(d)

Factory Method. PaymentFactory.create(method) returns CreditCardProcessor, PayPalProcessor or CODProcessor, all typed as PaymentProcessor. The customer picks the method at runtime, so the client needs no new and no if-else. Each processor then follows the Template Method handlePayment() (tab 07).

LMS modules / product framework 2022 Q4.2, Q4.5

Factory Method. A Module interface, implemented by Quiz, Forum, Assignment and VideoLecture. ModuleFactory.create(userNeed) builds what the user needs. New modules (new products) are new classes registered with the factory, so the framework grows without changing existing code. That is what "scalable, extensible product-based framework" is asking for.

"It avoids code duplication." Agree?

Yes. The creation logic (the if-else and the new calls) is written once in the factory instead of in every client. Shared behaviour can sit in an abstract creator. The cost is extra classes, so keep the factory parameterised rather than writing near-identical creators.

Mistakes: client still calls new MySQLDatabase(); factory returns the concrete type instead of the interface; missing «create» arrows.

W5 Challenges → fix

  • More classes → keep one parameterised factory, not a creator per type.
  • The switch is edited for each new type → register types in a Map or config.
  • Unknown type → validate input, throw a clear exception.
  • Need one shared factory or connection → make it a Singleton.

The strict GoF version

subclasses decide

Two forms

Simple factory (what the lectures and past answers use): one class with a static create(type) method and a switch.

GoF Factory Method: an abstract Creator declares factoryMethod(), and each ConcreteCreator subclass returns its own product.

Either is accepted. Use the simple one unless the question says "let subclasses decide".
