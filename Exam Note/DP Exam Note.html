Design pattern basics

Lecture 1 theory, for "explain" questions and for opening an answer.
Basics
Theory

What is a design pattern?

A design pattern is a proven, reusable solution to a problem that keeps coming up in software design. It is not finished code. It is a template for how to arrange classes and objects, which you adapt to your own situation.

Every pattern has four elements: a name (so developers can talk about it), the problem and its context (when to use it), the solution (the classes, their roles and how they relate), and the consequences (the benefits and the costs).

Where they came from

  • The idea started in building architecture. Christopher Alexander wrote about reusable patterns for towns and buildings.
  • In 1995, four authors (Gamma, Helm, Johnson and Vlissides, the "Gang of Four" or GoF) published Design Patterns: Elements of Reusable Object-Oriented Software.
  • The book describes 23 patterns in three groups. These are the "GoF patterns".

Why use them

  • They give the team a shared vocabulary: "use a Factory here" says a lot in three words.
  • They make code flexible and reusable, with loose coupling.
  • They are easier to maintain and extend, because changes stay in one place.
  • They avoid repeating design mistakes that others have already solved.

The three groups bold = taught in this module

GroupWhat it deals withPatterns
CreationalHow objects are created, and who creates themSingleton, Factory Method, Abstract Factory, Builder, Prototype
StructuralHow classes and objects are put together into bigger structuresAdapter, Facade, Proxy, Decorator, Composite, Bridge, Flyweight
BehaviouralHow objects talk to each other and share responsibilitiesTemplate Method, Chain of Responsibility, State, Strategy, Observer, Command, Iterator

What patterns are not

  • Not ready-made code you can paste anywhere.
  • Not guaranteed to be correct, and not rules you must always follow.
  • Not something to force on a simple problem. Using one where it isn't needed is over-engineering.

Anti-patterns

An anti-pattern is a common solution that looks good now but causes problems later. It's a poor answer to a recurring problem.

Why they happen: time pressure, poor planning, overconfidence, using new technology just to impress, no design thinking, ignoring maintenance.

Examples: a God class that does everything, copy-pasted code, long if/else chains on a type field.

Patterns, frameworks and libraries the "Frameworks" in the module name

PatternAn idea for solving a design problem. No code of its own. You implement it yourself.
LibraryReusable code that your code calls when it needs something (e.g. a JSON parser).
FrameworkReusable infrastructure that calls your code ("don't call us, we'll call you", called Inversion of Control). Frameworks are built from patterns: Spring uses Dependency Injection and Proxy, JUnit uses Template Method, Java I/O uses Decorator and Adapter.

Singleton

Only one object of the class can exist, and everyone uses that same object.
Creational
Understand

Spot it: the question says…

only one instancea single global tax calculatorone logger, all logs in the same file every order gets a unique IDonly one user can run the payrollonly one DB connection active a new object is created every time → duplicates, wrong ordermaximum of N → Multiton

The idea

Some things should exist only once in a system: the print queue for the one printer, the logger, the configuration, the tax calculator. If every part of the program creates its own copy, each copy has its own data, and they disagree.

Singleton stops that. The class creates its one object itself and hands the same object to anyone who asks. Think of an airport control tower: every plane talks to the same tower.

What goes wrong without it Quiz 4

  • Inconsistent data: each object has its own queue or status, so departments see different printer statuses.
  • Resource conflicts: several objects send jobs at once, so jobs print in the wrong order, get duplicated, or the printer freezes.
  • Wasted memory and no central control.

The three ingredients name all three in your answer

1Private constructorNo other class can write new PrinterManager().
2Private static fieldHolds the one instance. Static means it belongs to the class, so there is only one copy.
3Public static getInstance()Creates the object the first time, then always returns the same one.

Also make the class final so no subclass can get around the private constructor.

How many objects do you need?

exactly 1Singleton (DB manager, logger)N reusableObject pool (10 DB connections)
at most NMultiton, "extended Singleton" (3 printers, 5 batsmen)unlimiteda normal class (customers)

W1 Name it and say why 2–5 marks

I would use the Singleton pattern, which is a creational pattern. It makes sure a class has only one instance and provides one global point of access to it.
Reasons (pick two or three)
  • Everyone works with the same object, so there is one queue / one status, and the data stays consistent.
  • No duplicate objects fighting over the same resource, so no duplicated or out-of-order jobs.
  • Saves memory, because the object is created once and reused.
Map it to the scenario
  • PrinterManager is the Singleton class.
  • The lab, library, engineering and staff room modules are the clients.
  • Each client calls PrinterManager.getInstance() instead of new, so all print jobs go into one queue.

W2 Class diagram

underline the static field and method
W3 · Java (lazy and thread-safe)
public final class PrinterManager {
    // the one shared object (volatile for threads)
    private static volatile PrinterManager instance;
    private final Queue<String> jobs = new LinkedList<>();

    // private: nobody outside can call "new"
    private PrinterManager() { }

    // the global access point
    public static PrinterManager getInstance() {
        if (instance == null) {             // check 1
            synchronized (PrinterManager.class) {
                if (instance == null) {     // check 2
                    instance = new PrinterManager();
                }
            }
        }
        return instance;
    }

    public synchronized void submitJob(String job) {
        jobs.add(job);
    }
}

// client: every department gets the same object
PrinterManager p1 = PrinterManager.getInstance();
PrinterManager p2 = PrinterManager.getInstance();
System.out.println(p1 == p2);    // true

One DB connection at a time Quiz 2 Q4

Make a DatabaseConnectionManager Singleton. Its constructor is private and it keeps one static connection. getConnection() opens the connection only if it is null and otherwise returns the one that exists. The method is synchronized. The Factory picks the database type once, and everyone reuses that single connection.

Logger, all logs in one file 2024 Q1.5 5m

Use a Singleton Logger. The one instance owns the only FileWriter, and every class calls Logger.getInstance().log(msg). So there is one file handle (no corrupted or duplicate lines), one format, one order, and less memory. log() is synchronized so lines from different threads don't mix.

2023 Q3.4 "implement logging": the same answer works. You can add that a logging Proxy could add logging around existing services without changing them.

Payroll runs for one user only 2022 Q4.3 · 2023 Q1.6, 4–5m

A Singleton alone does not give exclusive access. It only guarantees there is one PayrollEngine object, and therefore one lock that every caller shares. The exclusion comes from that lock. Two behaviours are possible, and the question decides which: reject immediately (tryLock() returns false at once, "payroll is running, try later") or wait (lock() blocks until the current run finishes). Ownership is released in finally, so an exception during the calculation can't leave the system locked forever.

public final class PayrollEngine {
  private static final PayrollEngine INSTANCE =
      new PayrollEngine();
  private final ReentrantLock lock =
      new ReentrantLock(); // j.u.concurrent
  private PayrollEngine() { }
  public static PayrollEngine getInstance() {
    return INSTANCE; }

  // option 1: refuse at once if busy
  public boolean tryRunPayroll(String user) {
    if (!lock.tryLock()) return false;
    try { calculateAll(user); return true; }
    finally { lock.unlock(); } // release
  }
  // option 2: wait for the run to end
  public void runPayrollWhenFree(String user) {
    lock.lock();
    try { calculateAll(user); }
    finally { lock.unlock(); }
  }
  public boolean isRunning() {
    return lock.isLocked(); }
  private void calculateAll(String user) {
    /* calculate every employee's salary */ }
}

// every OTHER entry point checks it
if (PayrollEngine.getInstance().isRunning())
  throw new IllegalStateException(
      "Payroll running, try later");

Coordinated access checks: "no other user logged in, no other process running" (2023 Q1.6) is only true if the login service, data-entry screens and batch jobs all check the same lock before they start (last snippet). Anything that skips the check is not blocked. The lock lives inside one running program (JVM). If the system runs on several servers, each has its own Singleton, so use a shared lock instead, such as a database row lock (SELECT … FOR UPDATE on a payroll_run row) checked by every server.

OrderID generator 2025 Q4, 5m

Use an eager Singleton with an AtomicLong counter, so two threads asking at the same moment never get the same ID. The first step of the template method handlePayment() is OrderIdGenerator.getInstance().nextId(), then validate → process → send receipt. All payment types share the one generator.

public final class OrderIdGenerator {
  private static final OrderIdGenerator
      INSTANCE = new OrderIdGenerator();
  private final AtomicLong counter =
      new AtomicLong(1000);
  private OrderIdGenerator() { }
  public static OrderIdGenerator
      getInstance() { return INSTANCE; }
  public String nextId() {
    return "ORD-"
        + counter.incrementAndGet();
  }
}

Scope of "unique": only within one running program. After a restart the counter starts at 1000 again, and two servers each have their own Singleton and counter, so both would repeat IDs. For real uniqueness, start the counter from the last saved ID, or take IDs from a database sequence (or a central ID service, or a server prefix such as ORD-S2-1001).

Fantasy cricket with an "extended Singleton" 2023 Q4.1, 5m

Use a Multiton: a Singleton that allows a fixed maximum number of objects per key. Player objects can only be created through addPlayer(role, name), which counts how many of each role exist and refuses once the limit is reached: 5 batsmen, 5 bowlers, 1 wicketkeeper. The captain is a plain Singleton, because there must be exactly one; appointing a new captain replaces the old one instead of adding a second.

public final class Player {
  private static final Map<String,Integer> LIMIT =
    Map.of("BATSMAN",5, "BOWLER",5, "KEEPER",1);
  private static final Map<String,List<Player>> team
    = new HashMap<>();
  private final String role, name;
  private Player(String role, String name) {
    this.role = role; this.name = name; }

  public static synchronized Player addPlayer(
      String role, String name) {
    if (!LIMIT.containsKey(role))
      throw new IllegalArgumentException(role);
    team.putIfAbsent(role, new ArrayList<>());
    if (team.get(role).size() >= LIMIT.get(role))
      throw new IllegalStateException("Max reached");
    Player p = new Player(role, name);
    team.get(role).add(p);
    return p;
  }
}
public final class Captain {
  private static Captain instance;
  private Player player;
  private Captain() { }
  public static synchronized Captain
      getInstance() {
    if (instance == null)
      instance = new Captain();
    return instance; }
  public void appoint(Player p) {
    player = p; }  // replaces, never adds
}

Factory Method

One place decides which class to create. The rest of the code just asks for "a database" or "a book".
Creational
Understand

Spot it: the question says…

create different types of X depending on the user's requestdifferent types of accounts / books / payments supports MySQL, PostgreSQL and MongoDBtoo many if-else blocks to create objects without exposing the concrete classscalable, extensible product-based frameworkmodules created depending on the user's needs

The idea

When the program needs one of several related types, the code that uses the object shouldn't have to know which class to new. A factory takes the request ("MYSQL", "FICTION", "CARD") and hands back the right object, typed as the common interface.

Like ordering at a restaurant: you ask for "a pizza", and the kitchen decides how to make it. You never go into the kitchen.

The problem it removes

// BEFORE: copied all over the client
if (type.equals("MYSQL"))
    db = new MySQLDatabase();
else if (type.equals("MONGO"))
    db = new MongoDatabase();
// new database = edit every copy

// AFTER: one line, interface only
Database db =
    DatabaseFactory.getDatabase(type);

The parts name them in your answer

PartJobExample
Product «interface»The common type every product sharesDatabase, Book, Account
Concrete productsThe real classesMySQLDatabase, FictionBook, SavingAccount

Don't mix it up

  • vs Singleton: Factory decides which type; Singleton decides how many (one). Often used together: the factory or the connection it creates is a Singleton.
  • vs Facade: Factory creates objects. Facade coordinates objects that already exist.
  • vs Abstract Factory: Abstract Factory creates whole families of related objects (e.g. a Windows button + Windows menu). Not taught in detail.

Why is new in the client bad?

It hard-codes the concrete class. Every new type forces a change in the client, which breaks Open/Closed, and the client depends on details instead of an abstraction, which breaks Dependency Inversion. The factory also separates creating from using (Single Responsibility).

A stand-in with the same interface as the real object. It decides if, when and how the real object is reached.
Structural
Understand

Spot it: the question says…

The idea

Sometimes the client shouldn't reach the real object straight away. It may be too heavy to load, the user may not be allowed, or it may be on another server.

A proxy has exactly the same interface, so the client can't tell the difference. The proxy does its check first (permission, cache, lazy load, log) and only then forwards the call to the real object. Like a security guard at a door: same building, but you go through the guard.

How a call goes through

  1. The client calls getPage(5) on the Subject (it's really the proxy).
  2. The proxy checks first: access, cache, validation, log.
  3. If allowed, it creates the real object if needed and forwards the call.
  4. The real object does the work and returns.
  5. The proxy can cache or log the result, then returns it.

Template Method

The parent class fixes the steps and their order. Each subclass fills in only the steps that are different for it.
Behavioural
Understand

Spot it: the question says…

all types follow the same overall processhowever, step 2 is different for each type standardise the common workflow while allowing custom behaviourevery level must follow the same procedure enforce the proceduresalary components with a few deviationscopy-pasted algorithm with small differences

The idea

Card, PayPal and cash-on-delivery payments all do the same three things in the same order: validate, process, send a receipt. Only "process" really differs.

So you write the order once, in a final method in an abstract parent class. The common steps are written there too. The step that differs is left abstract, and each subclass writes only that step. Like a recipe card: same steps for every cake, only the filling changes.

This is the Hollywood principle: "don't call us, we'll call you". The parent calls the child's steps.

The four kinds of method know these

KindModifierJob
Template methodpublic finalCalls the steps in a fixed order. Final, so no subclass can change the order.
Common stepprivate or concreteWritten once, shared by all.
Primitive stepprotected abstractEach subclass must write it.
Hookprotected with a defaultSubclass may override it if it wants (e.g. wantsEmail() returns true).

OOP ideas used "explain how abstract classes are used"

Inheritance (subclasses extend the parent) · abstract class and abstract methods (the parent can't be created on its own and forces subclasses to write the varying steps) · method overriding · final (locks the order) · access modifiers (protected steps, private common steps) · polymorphism (the parent calls whichever subclass version exists).

Why an abstract class and not an interface? The base has to hold real code (the common steps and the fixed order) as well as abstract steps. An interface can't enforce the order or share that code.

Don't mix it up

  • vs Strategy: Template varies some steps using inheritance, fixed at compile time. Strategy swaps the whole algorithm as an object at runtime.
  • vs Factory Method: a factory method is often just one step inside a template method.
  • vs Chain: Template is one object running fixed steps. Chain passes a request between objects.

Mistakes that lose marks

  • Template method not marked final.
  • Making every step abstract (then nothing is shared).
  • Using an interface for the base class.
  • The client calling the steps one by one.
  • Drawing dashed (implements) arrows. Subclasses extend, so solid lines.

Chain of Responsibility

A request is passed along a line of handlers. Each one either deals with it or hands it to the next.
Behavioural
Understand

Spot it: the question says…

several levels of support / escalationapproval limits: team leader, manager, director, CEO a sequence of checks that must occur in order and be easy to extendmultiple sub-filters handle different prioritiesexception handlingmultiple handlers hard-coded in sequence

The idea

Without the pattern, the sender has a long if-else: "if it's a password issue send it to L1, else if it's an install issue send it to L2…". The sender knows every handler, and adding a level means editing it.

With the chain, each handler only knows the next one. The sender gives the request to the first handler and doesn't care who finally deals with it. Like a hospital: nurse → doctor → specialist, each passing on what they can't treat. Java's try/catch works the same way.

Two ways a chain runs

1. Escalation: the first handler that can handle the request does, and the chain stops. Support levels, expense approval, exceptions by priority.

2. Pipeline of checks: every handler checks the request; any failure stops it, and passing all means accepted. Membership → availability → fines; inventory → fraud → delivery area; spam sub-filters.

The chain ends when a handler deals with the request, or when the end is reached. Add a fallback handler at the end so nothing goes unhandled.

The parts

PartJobSupport desk (Quiz 7)
Handler «abstract»Holds a next link, has setNext() and handle()SupportHandler
Concrete handlersDeal with the request if they can, otherwise pass it onL1Support, L2Support, L3Support, SpecialistSupport
RequestThe data being passed (type, level, amount)SupportRequest
ClientBuilds the chain once, sends every request to the first handlerSupportDesk

How to order the chain asked as "prioritise"

  • Cost / speed: cheap, fast checks first, so expensive ones run less often.
  • Rejection rate: checks that catch the most go early.
  • Severity / security: dangerous cases first (e.g. a malware attachment).
  • Accuracy: low false-positive checks before risky ones.
  • Business priority and availability of the handler.

Don't mix it up

  • vs State: Chain asks "who will handle this request?" and the request moves along handlers. State asks "how should I behave now?" and the object hands work to its current state.
  • vs Decorator: decorators all run and add to the result. In a chain, usually one handler takes the request.

Q1 Why State is appropriate 4m

A parking session has a fixed set of well-defined states (Available, Reserved, Occupied, Payment Due, Closed), and the same action behaves differently in each: enter() is allowed when Reserved but refused when Closed, and pay() only works in Payment Due. Principles

L: Liskov Substitution

// VIOLATION: Square extends Rectangle
Rectangle r = new Square();
r.setWidth(5);
r.setHeight(10);
r.getArea();   // expected 50, got 100

// VIOLATION: Penguin extends Bird

}
// FIX: model the right abstraction
interface Shape { double getArea(); }
class Rectangle implements Shape { ... }

abstract class Bird { abstract void eat(); }

class Sparrow extends Bird
              implements Flyable { ... }

Don't only ask "is it a kind of?" Ask "can the child keep every promise the parent makes?" No stricter inputs, no weaker results, no surprise exceptions.

I: Interface Segregation

// BAD: a fat interface
interface Worker {
  void work(); void eat(); void sleep();
}
// Robot must throw on eat() and sleep()

// GOOD: small role interfaces
interface Workable  { void work(); }
interface Eatable   { void eat(); }
interface Sleepable { void sleep(); }
class Human implements Workable,
    Eatable, Sleepable { ... }
class Robot implements Workable { ... }

Java's own examples: Comparable, Runnable, Iterable, AutoCloseable.

D: Dependency Inversion

// BAD: tied to MySQL, can't mock it
class UserService {
  private MySQLDatabase db =
      new MySQLDatabase();
}

// GOOD: depend on an interface,
// inject it through the constructor
class UserService {
  private final UserRepository repo;
  UserService(UserRepository r) {
    repo = r; }
}
new UserService(new PostgresUserRepo());

Dependency Inversion is the principle. Dependency Injection is the technique (pass dependencies in from outside; Spring does it for you).

Add one SOLID line to any pattern answer cheap extra marks

Decorator, Factory, Strategy, State, Chain"…which follows the Open/Closed principle: new types are new classes, existing code is not modified."
Facade, Chain handlers, Decorator"…each class has a single responsibility."

SOLID vs patterns vs frameworks: SOLID are principles ("how should I design classes?"), patterns are proven solutions to recurring problems, frameworks are reusable infrastructure (Spring applies Dependency Inversion through injection). Using a pattern doesn't guarantee SOLID; it depends on how you apply it. And SOLID isn't "more interfaces everywhere": adding abstraction to a 2-line calculator is over-engineering (YAGNI).

Microservices: the other parts

Architecture

2.3 Propose the architecture 4–5m

  • One service per business capability (list yours from the table), each with its own codebase, own database and own deployment.
  • API Gateway as the single entry point for web and mobile clients: routing, authentication, rate limiting.
  • Service registry so services can find each other; config server for settings.
  • Services talk synchronously with REST or gRPC when they need an answer now, and asynchronously with events on a message broker (Kafka / RabbitMQ) for everything else (e.g. "BookBorrowed" → Notification).
  • Everything runs in Docker containers on Kubernetes, with central monitoring.

2.4 Keeping data consistent 4–5m

With a database per service there are no shared transactions, so we accept eventual consistency and use:

  • Saga pattern: a business action is a series of local transactions. If one step fails, earlier steps are undone with compensating actions (payment fails → cancel the borrow / release the stock). It can be coordinated by events (choreography) or by one orchestrator service.
  • Event-driven updates: a service publishes an event when its data changes; others update their own copy.
  • Transactional outbox so the database change and the event are never out of step, and idempotent consumers so a repeated event does no harm.
  • CQRS for read-heavy views (catalog search) built from events.
  • Two-phase commit only where strong consistency is essential (rare, because it is slow and couples services).

2.5 Security 4–5m

UsersLogin through OAuth2 / OpenID Connect at the gateway, which issues JWT tokens. Role-based access (RBAC): e.g. only librarians can add books.
Service to serviceMutual TLS (a service mesh such as Istio), short-lived tokens, and each service only allowed to call what it needs.
DataHTTPS everywhere, encryption at rest, card data handled to PCI-DSS, secrets in a vault, each service's DB user has least privilege.
AttacksRate limiting, input validation, a web application firewall, audit logs and monitoring for unusual activity.
2023 Q2.6: "Why give every microservice platform the same hardware and configuration?" Identical environments (containers and infrastructure-as-code) make deployment, scaling and failover predictable: any node can run any service, performance is the same everywhere, capacity planning, automation and troubleshooting are simpler, and a failed node can be rebuilt exactly (DR). It avoids "works on my machine". Exception: GPU nodes for ML services.

"How can you extend this design to achieve High Availability and Disaster Recovery?" 2022 Q3.5 · 2023 Q3.5, 5m

High Availability = the system keeps running when a part fails (little or no downtime).

  • Run each component as several stateless copies behind a load balancer, with health checks and automatic restart (Kubernetes).
  • No single point of failure: a Singleton or Facade on one server becomes replicas.
  • Database replication / clusters with automatic failover.
  • Timeouts, retries and circuit breakers; a fallback handler at the end of a Chain.

Disaster Recovery = getting back after a big failure (data centre lost).

  • Regular backups, and the database replicated to a second region.
  • Agreed RPO (how much data we can lose) and RTO (how fast we must be back).
  • Automated failover to the DR site; infrastructure-as-code to rebuild quickly.
  • DR drills to test it regularly.

Tie it to the pattern: "Because each filter / handler / service is stateless, extra copies can run on several servers…" makes the answer fit the question.

"Many parameters change over time. Improve configurability." 2023 Q1.5, 4m

Move every rate, limit and threshold out of the code into external configuration (a database table or a properties / YAML file). A Singleton ConfigManager loads it and every class reads from there. An admin screen changes values; changes are versioned and audited with an "effective from" date; no recompiling or redeploying. Example settings: epf.employee=0.08, tax.threshold=100000. "Why not just use inheritance for everything?"

Inheritance fixes behaviour at compile time. Every combination needs its own subclass (class explosion), the hierarchy becomes rigid, and a change in the parent ripples into every child. So prefer composition: Decorator, State, Strategy and Adapter all hold another object instead of inheriting from it, and can change at runtime.
